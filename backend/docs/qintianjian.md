## 一句话定位

钦天监是重大任务的前置参谋机制：先把大事问清楚，把风险照出来，把选项摆上桌，再决定是否执行。
它不替代蜂群执行，而是在执行前把方向、风险、选项和验证方式定清楚。

它的目标不是考用户，而是降低用户决策负担。用户不需要一次答对所有问题；系统要先给可选答案、推荐项和验证方式。

## 主要功能

1. **问题收窄**：把"重大决策"翻译成最多 3 个"现在必须定"的问题，其余放进"稍后再定"，不让用户一次性回答一整套架构问题。
2. **选择题化**：每个问题给 2-3 个选项，标一个推荐项，说明"选这个会让系统怎么做"；答不上来时用户可以直接回复"按推荐来"。
3. **双大神视角**：每个问题由 2 位相关领域大神给出不同角度的建议，不是装饰，每位必须给出会影响执行的具体判断。
4. **不可逆闸门**：涉及客户承诺、烧钱、生产、数据安全等不可逆动作时，必须有具名人类签字才放行，钦天监本身只进言、不代签。
5. **简报封装**：把用户的选择整理成结构化简报（`SEALED_BRIEF`），带上执行边界，交给下游蜂群/任务执行，避免"讨论完就散了没人记住选了什么"。

## 价值

- **对用户**：不用先看懂系统设计就能做出关键决策，决策负担从"回答一整套问题"降到"挑 1-3 个选项"。
- **对协作本身**：把"我们刚才到底决定了什么"变成可追溯的简报对象，而不是散落在聊天记录里，减少下次对话重新对齐的成本。
- **对不可逆动作**：强制显式签字点，防止"顺着聊天惯性就把生产/客户承诺的事定了"这种隐性滑坡。

## 什么时候触发

**显式触发**（用户直接说）：
- `开钦天监`
- `钦天监参谋`
- `先问钦天监`

**自动建议触发**（场景命中，但不强行拦截，只提示）：
- 架构分叉：会影响后续大量代码或流程。
- 不可逆决策：会影响客户、合同、报价、生产、现场、数据安全、烧钱。
- 多蜂群治理：涉及评分、归档、记忆、自动执行、签字熔断。
- 上线发布：会影响真实用户或生产服务。
- 客户承诺：对外报价、交付期、合同条款。
- 长周期项目：目标模糊、容易偏移，需要先定反馈闭环。

**自动触发的处理方式**：命中场景不等于直接拦截执行，只提示"这件事风险较高，建议先开钦天监，先定 3 个关键选择"，是否真的开由用户决定。**这条是本次合并时明确下来的**——旧版两份文档一份只给触发词、一份只给场景列表，两者优先级关系没写清楚，现在统一成：触发词=立即执行协议；场景命中=提示但不强制。

## 输出原则

- 问题要通俗，不要像审讯，也不要堆术语。
- 每次最多先问 3 个"现在必须定"的问题，其余放入"稍后再定"。
- 每个问题都要说明"为什么问这个"。
- 用户可能答不上来时，先给 2-3 个选项。
- 每个选项必须说明会改变什么后续动作。
- 由 2 位相关大神给出不同视角，并标注推荐选项；大神不是为了装饰，没有影响执行的建议就删掉。
- 必须包含验证方式，避免只做抽象讨论。
- 对不可逆动作必须指出人类签字点。
- 审问结束后必须给出下一步最小行动，不让讨论悬空。

## 输出格式（结构化简报版，供程序/下游消费）

```json
{
  "mode": "qintianjian",
  "status": "SEALED_BRIEF",
  "original_goal": "...",
  "must_decide_now": [
    {
      "question": "...",
      "recommended_option": "A",
      "user_choice": "A",
      "decision_effect": "...",
      "validation": "..."
    }
  ],
  "defer": ["..."],
  "personas": ["...", "..."],
  "human_signoff_required": true,
  "execution_boundary": "...",
  "target_swarm": "..."
}
```

`SEALED_BRIEF` 是人类可读模板讨论完之后的落地对象——文本模板负责跟用户对话收敛问题，这份 JSON 负责把收敛结果交给下游执行，两者是同一件事的两个面孔，不是两套设计。

## 朝堂接入规则（状态机）

钦天监在朝堂里不是一个普通聊天模式，而是重大任务进入蜂群前的"参谋闸门"。

状态建议：
- `OBSERVING`：正在生成 1-3 个关键问题和选项。
- `AWAITING_CHOICE`：等待用户选择推荐项或改方向。
- `SEALED_BRIEF`：形成钦天监简报，可交给蜂群执行。
- `EXECUTING`：蜂群按简报执行。
- `REVIEWING`：裁判评分、熔断、人类签字。

钦天监简报至少包含：
- 用户原始目标
- 3 个以内当前必须定的问题
- 用户选择
- 两位大神建议摘要
- 验证方式
- 人类签字点
- 交给蜂群的执行边界

## 接入朝堂飞轮（完整链路）

```text
用户目标
→ 钦天监参谋
→ 用户选择 / 按推荐
→ 钦天监简报（SEALED_BRIEF）
→ 蜂群执行
→ 独立裁判评分
→ 不可逆风险熔断
→ 人类签字
→ 成功归档 / 失败入 must_not
→ 下一轮改进
```

**现状诚实标注**：这条完整链路目前是**协议层面的设计目标**，不是已经被代码强制执行的路径——本仓已验证过的上书房蜂群链路（`/api/shangshufang/draft-edict` → `confirm-edict` → `decision`）并**没有**在执行前先产出一份 `SEALED_BRIEF` 并校验它存在。也就是说"正线/红线任务必须先形成钦天监简报"目前是治理意图，还没有代码门禁去强制它。详见 [`docs/qintianjian_mainline_recovery.md`](qintianjian_mainline_recovery.md) 的现状标注。

## 第一阶段最小实现（如果要落地成代码门禁）

先不要做复杂 UI。第一阶段只做三件事：

1. 文本触发：用户说 `开钦天监` 时，按本文模板输出参谋。
2. 简报结构：把用户选择整理成 `SEALED_BRIEF`。
3. 执行边界：蜂群执行时带上简报，明确哪些能做、哪些必须签字。

## 不做什么

- 不默认拦截每个小任务。
- 不问 10 个问题逼用户答。
- 不让大神输出空泛名言。
- 不把未确认选项当成事实。
- 不绕过人类签字做不可逆执行。

## 优缺点（2026-07-04 会审结论）

**优点**：
- 触发场景具体、不泛化，"降低决策负担"这条产品原则贯彻得彻底（选择题而非问答题）。
- 大神配对表把"该找谁参谋"这一步的选择成本提前定好，不用每次现场想。
- 显式区分"触发词=立即执行"与"场景命中=提示不强制"，避免过度打扰又不至于完全静默。

**缺点（本次会审新发现，未修复，如实记录）**：
- **零强制力**：这套协议依赖执行者（Claude/Codex）主动记得并遵守，没有任何自动化检查能验证某次对话该触发而没触发。跟 `scripts/yushi_drift_monitor.py` 检查代码/提交层面的偏移不同，这里没有对应的"协议合规检查"。
- **完整链路仍是意图，不是门禁**：见上文"接入朝堂飞轮"现状标注，正线/红线任务目前可以绕过 `SEALED_BRIEF` 直接执行，代码里没有强制校验。
- 这两条缺点如果要修，成本不是文档层面能解决的，需要在实际执行入口（如 `chaotang_orchestrator.py`/`shangshufang.py`）加一道"高风险任务必须先有 SEALED_BRIEF 记录"的门禁，属于代码改动，本次收敛只处理文档层，不在这轮做。
