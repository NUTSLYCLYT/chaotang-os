## 一句话结论

workflow 的真正价值不是“把多个 agent 串起来”，而是把老板的一句话变成一条可追踪的经营判断链：

`意图 -> 分歧 -> 证据 -> 决策 -> 执行 -> 结果 -> 复盘 -> 下次更准`

如果某个蜂群不能改变下一步决策、不能留下证据、不能让下次路由或判断更好，它就只是慢一点的聊天，不是操作系统。

## 大神审视

- 张小龙：用户不想管理 17 个蜂群。用户只想知道“现在我该做什么”。蜂群应隐藏复杂性，只把一个好默认动作送到眼前。
- Marty Cagan：每个蜂群都要回答一个客户问题和一个业务结果。功能不是目标，机会才是目标。
- Deming：不要用一次高分骗自己。看变异，看失败类型，看结果是否反哺系统。
- Charity Majors：每次蜂群运行必须可观测。没有 run_id、输入、证据、模型、延迟、成本、质门、用户裁决，就不能说它上线了。

## Workflow 真价值

### 当前形态

系统已有三层能力：

- 治理层：`court` 三省六部，负责收旨、审议、派单、复核。
- 执行层：`swarm_orchestrator.yaml` 注册业务蜂群，并通过事件绑定串联。
- 专家层：`manor_groups.yaml` 把 11 个朝堂 agent 聚成 6 个能力组。

当前主要缺口：

- 事件绑定存在，但很多 `min_quality_score` 为 0，无法防止低质量结果自动流转。
- 蜂群有步骤，但缺少统一的“用户价值契约”：谁用、何时用、输出后去哪。
- 质量分存在，但缺少 outcome 对账：最后客户是否接受、报价是否成交、法律风险是否减少、研发 gate 是否通过。
- 多蜂群联动更像流水线，还没有把“分歧”变成产品体验里的核心价值。

### 升级原则

1. 每个蜂群必须有一个唯一产品 job，不做万能助手。
2. 每个蜂群输出必须包含：结论、证据、风险、下一步、质门、归档字段。
3. 每次自动触发必须经过质量门；高风险任务必须有人类圣裁。
4. 每个蜂群都要留下 wide event：`user/task/swarm/input_hash/evidence_count/conflicts/score/cost/latency/outcome`。
5. 史馆不是存档页，而是学习回路；归档结果必须改变未来 briefing、路由或质门阈值。

## 全局天才设计

### 1. 一道圣旨，多路分奏

上书房只展示一个结果：圣旨。后台可召多个蜂群，但前台不让用户选择蜂群。

圣旨结构固定：

- 圣裁：当前判断，准奏/补证/复核/驳回。
- 分奏：哪些蜂群参与，各自结论和置信度。
- 证据：来源、时间、材料、假设。
- 风险：不可逆风险、缺证风险、成本风险。
- 后令：下一步唯一主动作。
- 质门：是否允许进入军机处、报价、合同、研发 gate 或史馆。

### 2. 分歧优先，而非平均合成

蜂群最大价值不是“大家都同意”，而是找出老板没看到的分歧。

必须显式展示：

- 户部 vs 兵部：利润和增长冲突。
- 工部 vs 户部：可交付性和预算冲突。
- 刑部 vs 礼部：合规边界和对外表达冲突。
- 锦衣卫 vs 钦天监：事实情报和趋势推演冲突。

### 3. 质门即产品，不是后台评分

每个蜂群输出都必须能被质门阻断。质门失败时，不显示“失败”，而显示一个最小补救动作：

- 缺证：去锦衣卫补情报。
- 数字冲突：去户部/工部对账。
- 法务风险：进刑部审签。
- 执行不可落地：回军机处拆解。
- 没有复盘价值：不进史馆。

### 4. Outcome 反哺

每个用户裁决都要写回：

- 用户采纳/驳回了哪个蜂群意见。
- 哪个风险后来发生。
- 哪个报价/方案成交或失败。
- 哪个 agent 的建议被证明有效。

下一次同类任务时，圣旨要显示“历史镜鉴”，但不能自动代替用户决策。

## 分阶段升级路线

### Phase 1：圣旨统一输出

目标：所有入口先统一成 `edict`。

- 给每个 swarm 定义 `edict_adapter`：把现有 final_output 转成圣裁、分奏、证据、风险、后令、质门。
- `study/run` 先接真实 run/memorial，再接 orchestrator 事件。
- 上书房只显示一个圣旨，不让用户理解底层蜂群数量。

验证：

- 每个 swarm 至少一条 golden case 能生成 edict。
- `quality_gate.status` 必须能是 `passed/needs_review/blocked`。

### Phase 2：质门和分歧产品化

目标：自动触发前先判断，不让低质量结果乱流转。

- 把 `swarm_orchestrator.yaml` 中关键 `min_quality_score: 0` 改成有业务含义的阈值。
- 每个高风险蜂群增加 `block_reason` 和 `repair_action`。
- 分歧进入圣旨，而不是被合成掉。

验证：

- 低分 product 不触发 quotation。
- pack_rd 冲突未清不触发 battery_stage_gate。
- legal blocked 不允许礼部对外发布。

### Phase 3：史馆反哺

目标：workflow 从闭环升级到自改进。

- 每个 swarm 输出 outcome schema：采纳、驳回、成交、失败、返工、复用。
- 史馆生成 `memory_card`，写回上书房 briefing 和路由先验。
- AI ops 每日显示最坏蜂群、失败类型、回滚建议。

验证：

- 同类任务第二次运行时，圣旨能显示历史镜鉴。
- 被用户驳回的路径在下一次降权。
- 失败案例能被检索并影响风险提示。

## 最小可发版本

先不要全量改 17 个 flow。最小可发版本只做 4 个链路点：

1. `study/run` 从 fallback memorial 升级为真实 run edict adapter。
2. `opc -> product -> quotation` 增加质量门和分歧字段。
3. `quotation -> shiguan_archive` 记录用户采纳/驳回 outcome。
4. `ai_ops` 每日输出最坏蜂群和下一步修复建议。

这个版本能让用户第一次感受到：不是“AI 回答我”，而是“朝堂替我发现机会、分歧、红线，并且下次更懂我”。
