# Codex 能力地图

这份地图用于把 Codex 当成朝堂开发系统的一部分，而不是只当聊天助手。目标是让用户知道什么时候该让 Codex 直接做、什么时候该开钦天监、什么时候必须人工签字。

## 一句话原则

用户给方向和裁断，Codex 负责把目标变成代码、测试、验证、提交收口和规则沉淀。

## 最强能力区

1. 读仓库现状：理解目录、依赖、脚本、测试、git 状态。
2. 改代码：按现有风格做小步实现，不额外发明架构。
3. 写测试：把 bug、红线、边界条件固化进 pytest 或项目测试。
4. 跑验证：执行单测、静态校验、构建、评分脚本，并解释结果。
5. Git 收口：精确 `git add <path>`、提交、推送、说明回滚。
6. 脏码分拣：区分源码改动、运行产物、环境漂移、质量基线。
7. 文档化流程：把临时经验写成 AGENTS 规则、模板、协议。
8. 自动化重复动作：写脚本、检查器、harness、golden case。
9. 多视角审视：用大神视角做风险、产品、可靠性、安全取舍。
10. 飞轮建设：把失败变成测试，把测试变成门控，把门控变成习惯。

## 边界和禁区

- 不能替用户签不可逆商业承诺：报价、交期、合同、客户承诺必须人工签字。
- 不能凭空知道真实外部事实：市场价、法规、供应商状态、API 最新变更需要来源或联网验证。
- 不能保证模型评判永远正确：LLM-as-judge 只能辅助，关键 gate 要有确定性检查。
- 不能访问未授权系统：Gitee、API、服务器、浏览器、数据库都需要已有权限或用户批准。
- 不能长期记住口头经验：重要规则必须写入仓库、脚本、测试或数据。
- 不能把脏工作区自动清干净：除非用户明确要求，不回退用户改动。

## 能力上线等级

| 等级 | 能力 | Codex 可自动做 | 人工签字点 |
|---|---|---|---|
| L0 | 问答/解释 | 解释概念、读代码、列风险 | 无 |
| L1 | 小修 | 改单点代码、补测试、跑验证 | 提交前确认范围 |
| L2 | 功能闭环 | 实现、测试、文档、收口、推送 | 影响生产前确认 |
| L3 | 系统改造 | 开钦天监、拆阶段、建 harness | 架构分叉确认 |
| L4 | 自动执行 | 批量执行、外部系统写入、客户动作 | 必须人工签字 |

默认开发效率最高的是 L2：一次任务完成实现、测试、收口、推送。

## 十个榨干方式

1. 先让 Codex 读现状，再实现。
2. 每个任务要求实现、测试、收口三件套。
3. 大决策触发 `开钦天监`，小任务直接做。
4. 每次混乱都固化成 AGENTS 规则、脚本或测试。
5. 大神视角只用于决策镜片，不用于装饰。
6. 维护能力地图，别靠猜边界。
7. 把朝堂拆成可评测蜂群：输入、输出、评分、失败样例。
8. 任务开始先问“本轮不做什么”。
9. 用真实失败喂 golden case 和 must_not。
10. 优先自动化最痛的 20%：收口、质量、脏码、签字、回滚。

## 顶级大神建议

- Deming：把质量放进流程，不要放在最后验收。
- Charity Majors：没有可观测性，就没有开发效率；每个失败要能定位。
- Karpathy：所有高频任务都应该有 harness，不要靠感觉评价模型输出。
- Bruce Schneier：自动化越强，权限边界越要硬。
- 张小龙：用户只需要下一步，不需要看见系统全部复杂性。
- Munger：防偏移比追速度更重要；速度快但方向错是负效率。
- Jobs：每次新增入口都要问能不能砍掉两个旧入口。
- Drucker：先定义朝堂到底服务谁、产出什么结果，再谈功能。
