# 朝堂全院回奏流水线契约

目标：把用户一句圣旨转成可审计、可下载、可复盘的综合回奏。所有部门按同一条流水线工作：各司产证据，部门写回奏，军机处审核，丞相给建议，用户看可决策内容。

## 标准链路

```text
用户下旨
-> 丞相拟旨
-> 军机处派单
-> 各司提交报告和附件
-> 部门整理标准回奏
-> 军机处审核证据、冲突和红线
-> 丞相综合分析并给建议
-> 递交用户：综合回奏 + 附件下载
```

## 分层职责

| 层级 | 职责 | 不得做 |
|---|---|---|
| 各司 | 提交事实、证据、附件、专业判断、下一步 | 不写最终圣裁，不替其他司背书 |
| 部门 | 把各司材料压成标准七段回奏 | 不软化各司红灯，不编造缺失数据 |
| 军机处 | 审核证据、冲突、红线、缺口、签字要求 | 不美化结论，不替部门承诺 |
| 丞相 | 综合排序，给用户建议和下一步 | 不改写部门原始结论和红线 |
| 用户 | 看结论、建议、今日要事、风险红线、附件 | 不需要读所有原始材料才能决策 |

## 各司报告字段

各司上传报告必须能转换为结构化 payload：

- `office`
- `task_id`
- `summary`
- `facts`
- `evidence`
- `attachments`
- `risks`
- `next_action`
- `source_label`

没有证据或附件来源的内容，只能写成“待确认”，不能写成事实。

## 附件字段

附件必须可下载、可追溯：

- `attachment_id`
- `title`
- `source_office`
- `source_label`
- `generated_at`
- `summary`
- `download_path`

附件可以是 JSON、Markdown、HTML、CSV、PDF 或原始客户材料索引。正式对外前，敏感信息必须先脱敏。

## 部门标准回奏

部门整理各司材料时，统一写成七段：

1. 圣裁：本部门结论，绿/黄/红/黑灯。
2. 分奏：各司主要发现。
3. 证据：引用了哪些报告和附件。
4. 风险：阻塞、冲突、红线、缺口。
5. 后令：下一步谁负责、做什么、何时回报。
6. 质门：是否通过审核，是否需要人工签字。
7. 来源：数据来源、附件编号、置信状态。

## 军机处审核

军机处审核必须覆盖：

- `evidence_present`
- `attachment_traceable`
- `cross_office_conflict`
- `forbidden_commitment`
- `human_signoff_required`
- `source_label_consistent`

涉及报价、交期、安全、合同、付款、生产、权限、对外发布的内容，默认触发红线或人工签字检查。

## 用户首屏

用户最有价值的是决策内容，不是系统过程。首屏只放五块：

- 当前结论
- 丞相建议
- 今日要办
- 风险红线
- 附件下载

详细各司报告、军机处审核记录和史馆归档作为附件展开。

## 铁律

1. 附件先于结论：没有附件或证据来源的内容，只能标为待确认。
2. 部门不能自审：部门回奏必须过军机处审核。
3. 丞相不能软化红灯：只排序和建议，不改写部门原始风险。
4. 用户不读流水账：首屏必须回答“能不能做、为什么、谁去办、什么不能承诺”。
