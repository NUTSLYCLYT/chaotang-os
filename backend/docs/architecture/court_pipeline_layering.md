# 朝堂管线架构:四层分工 + 复杂度分档(court_doc ↔ 蜂群 收口)

> 定稿 2026-07-01。回答两件事:① court_doc / 判决引擎 / 大神律师 与**蜂群**如何分工不打架;
> ② 不是每件事都该上全套——**管线按复杂度分 4 档**,默认最简,按需升级(向 Claude Code 学:结构是挣来的)。
> 落地分两步:本文档(B,架构定稿)→ 焊代码(A,court_doc 接成蜂群装配末段 + 分档路由)。

## 一、四层分工(谁干什么,不互抢)

依据 `config/advisor_protocols.yaml` 的 `global_contract`:**"大神不是证据,也不是放行人;大神只提供警示、天才建议、失败路径和证据缺口。"**

| 层 | 角色 | 是谁 | 产物 | 边界 |
|---|---|---|---|---|
| **手·执行** | 干活 | 蜂群(`swarm_execution_loop`,33 swarm) | `SwarmOutputV1`(单 swarm 内层) | 只执行,不定灯 |
| **嘴·参谋** | 出主意 | 大神 + 律师(`persona_registry`) | 警示/天才建议/失败路径/**法条接地** | 只供料,**不执行不放行**;观点席 RAG 强制(`gate_conclusion`) |
| **闸·裁决** | 定输赢 | 御史 / harness(`yushi_global_gate`/`guard_rails`) | 灯(绿黄红黑) | 唯一放行人 |
| **脸·呈现** | 给客户看 | **court_doc**(`schemas/court_doc.json`) | 一张判决/奏报 | 聚合上三层,**不产生新结论** |

**结论:court_doc 是"脸",不是和蜂群抢活的对手。** 蜂群是发动机,court_doc 是仪表盘 + 出厂合格证。

## 二、收口三决断(让它物理上不可能变两套)

1. **court_doc 是聚合外壳,不是第三种输出**:`SwarmOutputV1`(单 swarm) → 装配成 `court_doc`(部门对客)。
   已有的 `SwarmBriefForJunjichuV1` 与 court_doc 职责重叠 → **退役/并入 court_doc,只留一个聚合标准**(否则每加一部门维护两份拼装逻辑 = 技术债)。
2. **判决引擎 = 蜂群装配末段,不是旁路**:`xingbu_verdict.build_verdict` 消费蜂群输出(`SwarmOutput.risks → court_doc.items`)。
   现 `/api/legal/verdict` 直连路**降级为无 LLM 的确定性 MVP/测试短路**;生产真实路必须 `蜂群 → 大神参谋 → 御史灯 → 装配 court_doc`,**直连不得绕过御史闸**(否则护身符=没盖章的废纸)。
3. **大神/律师只从"嘴"喂进蜂群推理**:进 `provenance.advisors` + 喂 findings,永不进执行、永不定灯。

## 三、复杂度分 4 档(核心:别对琐碎任务上全套)

不是每件事都开四层。路由器按 **风险 × 不确定 × 不可逆 × 范围** 选档(复用并向上扩展已有 `select_orchestration_tier`):

| 档 | 任务 | 走几层 | 成本 | 类比 Claude Code |
|---|---|---|---|---|
| **P0 直答** | 琐碎/事实/低风险 | 单模型答,**不开蜂群/大神/court_doc** | 1 次 | 默认直答 |
| **P1 单参谋** | 需一个视角 | 1 大神/模型 + 轻输出 | 几次 | 单 agent + 工具 |
| **P2 部门蜂群** | 真活(报价审/合同审) | 蜂群 + 大神参谋 + 御史闸 + court_doc | 重 | 派并行子 agent |
| **P3 会审/钦天监** | 不可逆/高风险/跨部门 | 全院会审 + 对抗验证 + **人工签字** | 最重 | 关键岔口问人 + 多视角 |

**默认 P0,任务"挣到"才升档。** 另一刀:P0/P1 的"大神"用**单模型多视角提示**(便宜),P2+ 才升级真蜂群多 agent —— 别为一句话开 12 个 agent。

## 四、向 Claude Code 学到的(刻进路由原则)

1. **简单优先**:默认最便宜的路;结构是挣来的,不是默认开。
2. **单 agent + 工具 > 议会**,直到真需要并行/多视角才升级。
3. **决策岔口问人**(P3 人工签字),而不是预先堆满仪式。
4. **大神议会是 P2+ 的特例,不是每次的默认**——当前最大风险就是把 P2/P3 当默认。

## 五、是 2026 最佳架构吗(诚实)

- 四层分工 + 证据接地 + 护栏门 + 自我进化飞轮:**是当下主流且是护城河**(多数系统没有治理/证据/eval)。
- 但"最佳"≠"对每件事上最重":**最佳 = 自适应**——能多简单就多简单,该多严才多严。
- **加上第三节的"管线分档"路由,这套才从"强但重"变成 2026 最佳。** 不加,默认全开 = 过度工程。

### 优缺点

| 优点 | 缺点 / 风险 |
|---|---|
| 可治理、可审计、证据接地、能自进化、扛高风险 B2B | 重(延迟/成本/复杂);琐碎任务灾难;两套聚合层技术债;**仪式默认全开**的过度工程风险 |

## 六、落地(A 阶段焊缝)

1. 加 **管线分档路由**(扩 `select_orchestration_tier` → 返回 P0–P3),决定开几层。
2. court_doc 接成 **蜂群装配末段**(swarm→参谋→御史灯→拼 court_doc);`SwarmBriefForJunjichuV1` 并入。
3. `/api/legal/verdict` 直连降级为 MVP 短路,生产强制走蜂群 + 御史。
4. `rag_hit` 必须由系统检索律师法条库(`knowledge_rag`)得出,**不接受客户端自报**(安全闭环)。
