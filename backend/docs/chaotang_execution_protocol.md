# 朝堂开发执行协议

这份协议回答一个问题：用户怎样发令，Codex 怎样执行，朝堂怎样越来越快。

## 标准发令模板

```text
目标：我要解决什么问题。
成功标准：做到什么算完成。
边界：本轮不做什么。
模式：直接做 / 开钦天监 / 先审查 / 只解释。
收口：实现 + 测试 + 验证 + 提交 + 推送。
```

用户也可以只说短句，Codex 需要自动补边界：

```text
把这个问题修了，按推荐来，最后收口推送。
```

## 四种执行模式

### 1. 直接做

适合：小 bug、单文件修复、测试补充、文档补充、脚本小改。

Codex 默认动作：
- 读相关文件。
- 精确修改。
- 跑最小验证。
- 用 `python scripts/commit_closeout_check.py` 分拣。
- 提交并在用户要求时推送。

### 2. 先审查

适合：用户不确定问题在哪、怀疑效率低、怀疑架构乱。

Codex 默认动作：
- 读代码和 git 状态。
- 列出最高风险和最小修复路径。
- 如果用户已说“按推荐来”，直接执行最小修复。

### 3. 开钦天监

适合：架构分叉、上线、客户承诺、自动执行、花钱 API、多蜂群治理。

Codex 默认动作：
- 先问最多 3 个必须现在定的问题。
- 由两位相关大神给 2-3 个选项和推荐项。
- 用户可回复 `按推荐来`。
- 形成钦天监简报后再执行。

### 4. 只解释

适合：学习 git、理解架构、概念扫盲。

Codex 默认动作：
- 用小白能懂的话解释。
- 给例子。
- 不改代码，除非用户追加“顺手落地”。

## 提效飞轮

每次任务结束必须问：

1. 这次有没有重复劳动？
2. 这次有没有脏码混入风险？
3. 这次有没有模型乱编、数字乱来、承诺越权？
4. 这次失败能否变成测试？
5. 这次经验能否写进 AGENTS 或脚本？

如果答案为“有”，优先落成：

- 规则：`AGENTS.md`
- 脚本：`scripts/*`
- 测试：`tests/*`
- 模板：`docs/*`
- golden case：`scripts/golden_cases/*`

## 每日开发节奏

1. 开工：`git status --short --branch`
2. 定目标：本轮只做一件事。
3. 执行：读代码、改代码、补测试。
4. 验证：跑最小测试和相关门控。
5. 收口：`python scripts/commit_closeout_check.py`
6. 暂存：只 `git add <path>`
7. 闸门：`python scripts/commit_closeout_check.py --staged-only`
8. 提交：一个 commit 表达一件事。
9. 推送：需要上传时 `git push origin <branch>`
10. 复盘：把新教训固化。

## 开发效率低时的优先修复顺序

1. 先砍范围：本轮只定义一个成功标准。
2. 再加观测：失败要能知道在哪一步。
3. 再加测试：高频失败必须进测试。
4. 再加脚本：重复 3 次的动作自动化。
5. 最后才加功能：没有收口能力，不扩功能面。

## 人类签字点

以下动作不能让 Codex 静默自动做：

- 删除或回退大量文件。
- 改生产端口、生产鉴权、生产数据库。
- 对外报价、承诺交期、承诺性能。
- 花钱调用新服务或安装未知依赖。
- 把失败质量基线提交为正式 gate。
