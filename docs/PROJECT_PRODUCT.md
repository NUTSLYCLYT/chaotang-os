# 朝堂 OS 项目产品文档

本文件整合历史归档中仍然有价值的产品描述。旧归档中的技术实现、部署、接口、代码路径、运行命令和历史排障内容不再作为项目级文档保留。

## 1. 产品定位

朝堂 OS 的产品主体不是某个客户定制项目，也不是古风界面演示。

朝堂 OS 是一套面向企业老板和经营负责人的 **AI 决策执行操作系统**：

```text
用户提出真实经营问题
  -> 系统识别关键前提、缺口和风险
  -> 拆成可执行路径、预算、责任和验收
  -> 多专业视角会审
  -> 形成可裁决奏折
  -> 用户采纳、打回、追问或派遣
  -> 史馆沉淀证据链和复盘
```

对外一句话：

```text
老板提一个真实问题，AI 内阁替你分析、拆路径、控风险、出奏折，你只做最终裁决。
```

## 2. 不是什么

| 误区 | 正确认知 |
| --- | --- |
| 企业 BI 工具 | BI 看数据，朝堂 OS 帮用户做经营判断。 |
| 通用 AI 助手 | 通用助手对话即忘，朝堂 OS 需要沉淀证据、裁决和复盘。 |
| 流程自动化工具 | 自动化工具执行流程，朝堂 OS 先判断该不该做、怎么做、风险在哪。 |
| ERP 系统 | ERP 管资源，朝堂 OS 管经营问题、专业会审和裁决闭环。 |
| 古风控制台 | 三省六部是治理框架，不是装饰皮肤。 |

## 3. 北极星

当前唯一北极星：

```text
让 1 个真实老板，用朝堂 OS 真做成 1 件经营决策，并愿意说：“这帮我了。”
```

所有产品路线都必须服务这个目标。页面、部门、视觉、蜂群、知识库和商业化动作都只是手段。

可验收标准：

- 用户提出一个真实经营问题。
- 系统指出关键前提、缺口、风险和下一步。
- 专业视角形成可读、可裁、可追溯的结果。
- 用户能采纳、打回、追问或派遣。
- 史馆留下证据链和复盘，下一次建议能引用。

## 4. 当前样板与通用化关系

铭硕电池是第一批真实样板，不是产品主业。

正确关系：

```text
朝堂 OS（通用 AI 决策执行 OS）
  -> 三省六部治理框架
    -> 铭硕电池 / 储能 / 合同审查 / 财务诊断等样板场景
```

铭硕样板的价值：

- 证明客户自有业务场景可以接入朝堂 OS。
- 证明多专业会审能落到真实行业问题。
- 形成可复制案例：从电池售后、产品、市场、项目管理复制到第二个客户。

产品叙事不能写成“铭硕专用系统”；销售对象也不能被锁死在单个客户。

## 5. 核心产品闭环

朝堂 OS 的主链路：

```text
大殿看全局
上书房发起事项
诸司查证风险
六部给专业判断
军机处统筹会审与执行
史馆归档复盘
```

最小有用交付：

```text
老板一句话
  -> 上书房整理成事项
  -> 丞相给初判和路径
  -> 军机处召集专业视角
  -> 六部 / 诸司给判断和风险
  -> 形成一份奏折
  -> 老板裁决
  -> 史馆留痕
```

产品验收不看“页面是否很多”，而看用户是否真的完成一次判断。

## 6. 产品模块

| 模块 | 产品职责 | 用户问题 |
| --- | --- | --- |
| 大殿 | 全局态势、今日事项、风险和入口总览 | 今天最重要的事是什么？ |
| 上书房 | 事项发起、拟旨、证据缺口和去向推荐 | 我该从哪里开始？ |
| 军机处 | 跨部门会审、冲突对齐、执行路线和结果汇总 | 这件事卡在哪，谁负责，能不能推进？ |
| 六部 | 专业判断层 | 钱、人、话术、销售、合同、产品分别怎么看？ |
| 诸司 | 风险、情报、预测、辅助判断 | 有什么外部信号、隐患和证据？ |
| 史馆 | 归档、复盘、旧案召回和结果回填 | 过去怎么判的，结果如何，这次能借鉴什么？ |

## 7. 六部产品定义

每个部门不是介绍页，而是 AI 部门作战台。用户进入部门时应看到正在处理的工作、产出、质量、阻塞和下一步。

| 部门 | 替代对象 | 核心职责 | 老板最关心的问题 |
| --- | --- | --- | --- |
| 户部 | 财务、预算、经营分析、投资评估、报价负责人 | 成本、预算、ROI、现金流、报价和投资判断 | 值不值得花钱？最坏损失是多少？ |
| 工部 | 产品、研发、方案、交付负责人 | 产品方案、可交付性、实施路径和验收 | 这事能不能做成，怎么交付？ |
| 兵部 | 销售、运营、客户战情、竞争攻防负责人 | 商机推进、客户下一步、竞争与资源取舍 | 怎么赢客户，下一步谁办？ |
| 刑部 | 法务、风控、合规负责人 | 合同、承诺、责任、合规和不可逆风险 | 能不能签，必须改哪几条？ |
| 礼部 | 品牌、市场、公关、对外表达负责人 | 客户话术、对外材料、发布边界和品牌一致性 | 能不能对外说，怎么说才可信？ |
| 吏部 | 人事、组织、招聘和权限负责人 | 岗位画像、招聘必要性、组织职责和人员安排 | 要不要招人，谁该负责？ |

部门输出必须能被老板裁决，不能停留在说明性文案。

## 8. 首发商业切片

历史归档中出现过多个首发方向：经营决策闭环、户部财务诊断、刑部合同审查、储能 PACK 评审。当前统一口径如下：

朝堂 OS 是总产品；首发商业切片必须选择 **最容易让真实客户付费的窄场景**。

优先级判断：

1. 是否能用一个真实材料在 3 分钟内产出可读结果。
2. 是否能明显降低老板风险、时间或沟通成本。
3. 是否天然需要证据、留痕和人工裁决。
4. 是否能复用到第二个客户。
5. 是否有人愿意为它付第一笔真钱。

当前可选首发切片：

| 切片 | 适合客户 | 价值主张 |
| --- | --- | --- |
| 刑部合同审查 | 储能、能源、制造业 B2B 老板 | 每份合同快速识别能不能签、改哪里、出事是否有据。 |
| 户部财务诊断 | 中小企业老板、财务负责人 | 上传经营材料后得到现金跑道、风险、行动建议和缺证提示。 |
| 储能 PACK 评审 | EPC、保险、认证、PACK 采购评审方 | 用统一评审格式降低供应商方案评审成本和事故追溯风险。 |
| 经营决策奏折 | 老板、总经理、项目负责人 | 把复杂事项变成多视角会审、风险和下一步。 |

收敛原则：

- 没有付费信号前，不同时推进多个垂直。
- 谁先让客户掏钱，谁就是首发商业切片。
- 其他方向冷藏，不删除认知，但不投入主线资源。

## 9. 目标客户

首批客户画像：

| 维度 | 描述 |
| --- | --- |
| 行业 | 制造业、储能、新能源、贸易、工程项目、产业服务企业 |
| 规模 | 100-500 人，年营收 3000 万到 5 亿优先 |
| 角色 | 老板、总经理、运营负责人、财务负责人、法务/合同负责人、项目负责人 |
| 痛点 | 决策慢、信息散、人才贵、跨部门沟通成本高、风险无人兜底 |
| 购买动机 | 提高决策速度和质量，降低合同/报价/项目风险，留证据可复盘 |

优先获客对象：

- 商会企业家。
- 制造业老板。
- 储能 / 新能源供应链企业。
- EPC 总包方、保险承保方、认证机构。
- 有合同、报价、采购、交付和合规压力的 B2B 企业。

## 10. 商业模式

阶段性建议：

| 阶段 | 模式 | 目标 |
| --- | --- | --- |
| 0-6 个月 | 高接触实施 + POC + 年费授权 | 签下 3-5 个付费客户，拿到真实案例。 |
| 6-18 个月 | 实施继续 + 行业模板化 + 轻 SaaS | 将实施经验沉淀成模板，开始规模化试用。 |
| 18 个月后 | SaaS 规模化 + 私有化部署 | 扩大客户数，并服务数据敏感的大客户。 |

推荐定价锚点：

- POC：3 个月，1.5 万到 3 万，用真实材料跑出价值。
- 企业标准版：每年 3.6 万到 8 万。
- 企业专业版：每年 8 万到 20 万。
- 私有化 / 定制版：20 万起，按数据安全、定制深度和服务范围报价。
- 单份轻决策：99 到 299 元，用于验证某些高频切片是否有低价入口。

定价纪律：

- 先收第一笔真钱，再谈估值和大规模增长。
- 不卖“多智能体系统”，卖“老板能更快更稳做决策”。
- 不承诺未落地能力，不把演示包装成生产可用。

## 11. GTM 与内测

第一阶段不要面向所有人泛泛推广，要围绕真实老板和真实问题。

内测分层：

| 类型 | 人数 | 目标 |
| --- | ---: | --- |
| 核心共创客户 | 5-10 | 深访、试真实材料、打磨付费切片。 |
| 商会体验客户 | 30-50 | 演示、收反馈、识别高意向客户。 |
| 候补名单 | 100-300 | 留资，等待邀请和场景匹配。 |

演示只跑一条链：

```text
老板输入一句真实问题
  -> 系统生成预案
  -> 多专业视角会审
  -> 输出奏折
  -> 老板裁决
  -> 史馆归档
```

不要展示所有页面，不要讲技术名词。

每个内测用户至少收集：

- 是否 10 秒内看懂第一步。
- 哪一步最有价值。
- 哪一步不可信。
- 是否愿意带真实问题再试一次。
- 是否愿意付费。
- 最担心什么。
- 愿意推荐给谁。

## 12. 产品红线

1. 不把 DEMO、FALLBACK 或样例包装成 LIVE。
2. 不为了扩部门、扩页面牺牲第一条真实闭环。
3. 不让 AI 自动执行不可逆动作；高风险事项必须人工裁决。
4. 不做没有证据来源的判断；缺证必须明确降级。
5. 不把客户私有数据沉淀为公共知识。
6. 不用“多智能体系统”等技术词作为主卖点。
7. 不承诺报价、交期、合同、合规和安全结果，除非有证据和签字。
8. 不同时追多个垂直，优先让一个客户说“有用”并付费。

## 13. 阶段路线

### 阶段 0：证明一个真实闭环

目标：一个真实老板用一个真实材料完成一次判断，并说“这帮我了”。

输出：

- 一条可演示链路。
- 一个真实案例。
- 一次归档复盘。
- 一个明确付费意向或第一笔付款。

### 阶段 1：形成首发商业切片

目标：从合同审查、财务诊断、储能评审或经营决策奏折中，选出最有付费信号的一条。

输出：

- 场景单页。
- 标准演示脚本。
- POC 交付边界。
- 报价和试用机制。

### 阶段 2：沉淀可复制模板

目标：将首发切片复制到第二个客户。

输出：

- 可复用客户 onboarding。
- 场景资料清单。
- 标准奏折结构。
- 反馈与复盘闭环。

### 阶段 3：扩展行业模板

目标：在保持主引擎不变的前提下，扩展第二、第三个垂直方向。

候选方向：

- 直播合规御史台。
- 外贸全链路决策 agent。
- 招投标合规与成本会审。
- 跨境合规 / 数据出境。
- 一人公司 CEO 副驾。
- AI 数字员工市场。

解冻规则：小成本试，谁先付钱，谁先进入主线。

## 14. 当前最重要动作

1. 选一个真实客户和一份真实材料。
2. 用一个首发切片跑出可读、可信、可裁决结果。
3. 让客户判断是否“有用”。
4. 争取第一笔 POC 或单份付费。
5. 把这次过程归档为第一个真实案例。

一句话收口：

```text
先别证明朝堂什么都能做，先证明它能帮一个老板做成一件真事。
```
