## 1. 执行摘要：最终裁决

### 1.1 最终产品形态

朝堂 OS 不是 Agent 商店、六部聊天集合或古风管理后台，而是：

> 面向个人与团队的可信复杂任务超级助手。

第一条商业 Offer 是：

> 中文、中国大陆法域、制造业/B2B 合同决策专业包。

R1 合同客户只需要理解四个界面：

1. 上书房工作台：提交材料、补充背景、查看进度。
2. 刑部决策单：查看风险、原文证据和修改建议。
3. 圣裁确认：采纳、补证、复核或驳回。
4. 史馆档案：查看追加式证据链、裁决和后续结果。

大殿、军机处、六部、专署和蜂群是后台治理与可解释能力，不应成为客户完成任务的认知负担。世界杯只作为跨域 benchmark；41 司只作为目标能力目录。

### 1.2 唯一业务主线

```text
用户提出真实问题
  -> 上书房拟旨并确认
  -> 丞相形成唯一版本化路由
  -> 军机处生成计划并可靠派单
  -> 六部 / 专署 / 蜂群产生带来源的分奏
  -> 军机处汇总候选奏折
  -> 御史执行证据、质量和来源门
  -> 唯一 FinalMemorial
  -> 用户或团队授权人裁决
  -> 史馆追加式归档与结果反馈
```

所有页面、Agent、swarm 和工具必须接入这条链；任何模块都不得建立第二套任务、第二套路由、第二份正式奏折或第二个裁决事实源。

### 1.3 当前最大问题（2026-07-14 快照）

本节不是实时状态源；证据以 [`Step 0 baseline`](../../.harness/changes/chore-shangshufang-step0-contract-baseline-20260714/baseline.md) 和[生产化蓝图现状](../../.harness/changes/chore-evidence-driven-shangshufang-workflow-20260714/blueprint.md)为准。

当前不是缺少功能，而是：

> 功能扩张速度超过了唯一主线收敛和真实验证速度。

具体表现为：

- 新正式主线与旧内存任务/旧接口仍可能并存。
- 前端部分流程仍可能本地合成业务结论。
- direct、复杂会办、失败恢复和人工等待的完整语义尚未全部冻结。
- 有事件账本和正式奏折纵切，但常驻 worker、持久化 DAG、全量迁移、浏览器 E2E 和生产演练尚未完整通过。
- 局部测试通过与“整体可上线”之间仍存在证据缺口。

因此当前策略必须从“继续建设更多功能”切换为“关闭旁路、完成一条生产级黄金闭环”。

## 2. 不可违反的十二条原则

1. **一个任务**：正式业务事项只有一个 `DecisionTask`。
2. **一个路由**：丞相路由是参与部门和处理等级的唯一事实源。
3. **一个正式主线**：所有正式入口最终调用同一种正式命令和状态机；D0 咨询遵守第 3.1 节隔离边界。
4. **一份正式奏折**：一旨最多一条当前有效的 `FinalMemorial`。
5. **模型负责想，代码负责管，人负责批**。
6. **简单任务短路径，复杂任务深治理，但不复制业务内核**。
7. **候选不等于事实**：Agent 输出、候选奏折、正式奏折和人工裁决严格分层。
8. **前端不推测成功**：所有 LIVE 状态和可执行动作来自后端读模型。
9. **没有证据就降级**：缺证、FALLBACK、DEMO 和未知来源不能晋升为正式结论。
10. **失败必须可恢复**：重试、取消、超时、晚到结果、部分失败和重启都必须有确定语义。
11. **交付声明受证据约束**：代码完成、局部测试完成、闭环验证和可以上线是四个不同状态。
12. **目录不等于发布**：R1 合同门通过前不增加第二 Offer；非合同能力可以登记、沙箱评测，但不得冒充上线。

## 3. 简单任务简单办，复杂任务复杂办

### 3.1 为什么采用三级而不是二级

简单/复杂二分类会在边界产生跳变，也容易把普通咨询误建为正式事项。最终采用三级处理深度：

| 等级 | 名称 | 适用场景 | 结果形态 |
| --- | --- | --- | --- |
| D0 | 咨询 | 解释、查询、起草；无高风险工具和外部写操作 | 带来源的回答，不声称已执行 |
| D1 | 直办 | 单部门、证据完整、低风险、可逆的正式任务 | 执行回执或简式决策单 |
| D2 | 会办 | 多部门、高风险、缺证、冲突、长任务或需人工批准 | 唯一正式奏折 + 人工裁决 |

D0/D1/D2 中的 `D` 表示 `processing_depth`，避免与发布环境等级混淆。D0 不是正式下旨。D1 和 D2 都使用 `DecisionTask`；两者只是处理深度不同，不是两套系统。

D0 虽不建立正式 `DecisionTask`，仍必须共用 canonical ingress、身份/租户校验、来源标签、审计与限流；不得写业务事实、执行有副作用工具或声称 LIVE。用户选择“转为正式事项”时，必须把原上下文快照升级为一个新的 canonical command，并记录来源关联。是否未来采用 lightweight task 必须另写 ADR，不能由前端自行实现第二条咨询业务链。

### 3.2 确定性分级机制

最终等级使用：

```text
最终等级 = max（业务复杂度分，风险硬门等级，用户指定等级）
```

参考评分：

| 条件 | 分值 |
| --- | ---: |
| 每增加一个参与部门 | +1 |
| 缺少关键证据 | +2 |
| 存在外部写操作 | +2 |
| 涉及金额、合同、安全或人事 | +3 |
| 存在不可逆动作 | +3 |
| 需要人工审批 | +2 |
| 预计运行超过 5 分钟 | +1 |
| 部门意见冲突 | +2 |

建议起始阈值：

- `0–1`：D0 咨询。
- `2–4`：D1 直办。
- `>=5`：D2 会办。
- 命中法律、资金、安全、人事、对外承诺、不可逆操作等硬门：无条件 D2。

模型可以推荐等级和理由，但风险硬门、最终等级和状态转换必须由确定性策略裁决。

### 3.3 动态升级，不重新建案

D1 执行中发现缺证、风险、冲突或越权时：

```text
记录 escalation.requested
  -> 冻结原结果为候选材料
  -> 原 DecisionTask 升级为 D2
  -> 丞相重新版本化路由
  -> 军机处生成会办计划
```

禁止为了升级而创建第二个任务。降级必须更谨慎：已经命中硬门或产生不可逆影响的任务不得自动降级。

### 3.4 direct 的最终语义

“直办”不得再等于“生成一段看起来完成的回执”。它必须二选一并由 ADR 冻结：

- **真实执行型**：有真实 provider/agent/tool 执行凭证才能标记完成。
- **草案确认型**：只生成草案时停在 `awaiting_execution_confirmation`，不得标记 `completed/LIVE`。

首发建议：只读分析和低风险内部产出采用真实执行型；任何外部写操作或业务承诺即使简单，也必须增加人工确认。

## 4. 唯一事实源与职责边界

### 4.1 正式业务对象

```text
DecisionTask
├── ChancellorRouteDecision   唯一路由
├── JunjichuPlan              军机处计划
├── DepartmentAssignment      部门节点任务
├── OutboxEvent               可靠派单
├── DecreeExecutionEvent      追加式过程账本
├── CourtReview               候选奏折
├── FinalMemorial             唯一正式奏折
├── EmperorDecision           人工裁决
└── ShiguanArchive            追加式归档
```

这里的“追加式”是业务语义：历史记录只新增事件或补偿，不原地改写。只有实际验证了 hash/签名防篡改或 WORM 存储，才能对外宣称相应等级的不可篡改能力。

### 4.2 六类产品界面

| 界面 | 可以做什么 | 明确禁止 |
| --- | --- | --- |
| 大殿 | 查看优先级、风险和待办 | 生成第二份结论 |
| 上书房 | 唯一正式发起、确认和裁决入口 | 本地伪造 LIVE 会审/圣裁 |
| 军机处 | 展示计划、节点、冲突、重试和阻断 | 另建一次性 swarm 业务闭环 |
| 六部 | 完成专业分奏 | 直接发布最终奏折 |
| 专署 | 补证、审计、预测和风险检查 | 把降级结果升级为正式事实 |
| 史馆 | 保存当时证据、裁决和后续结果 | 回写篡改历史奏折 |

### 4.3 蜂群与框架的边界

Swarm、Agents SDK、LangGraph、Temporal 或未来任何框架只能充当：

- 节点执行器；
- 工作流基础设施；
- 追踪和恢复工具；
- provider/tool 适配器。

它们不能拥有朝堂业务最终状态，不能绕过 `DecisionTask`，不能自行产生正式奏折，也不能代替人工裁决。

## 5. 企业治理机制

### 5.1 单线程负责人 + DACI

每项正式任务必须有明确责任结构：

| 角色 | 朝堂映射 | 责任 |
| --- | --- | --- |
| Driver | 丞相/任务负责人 | 推进任务、处理阻塞、对交付负责 |
| Approver | 老板/授权裁决人 | 对高风险和最终决策签字 |
| Contributors | 六部/专署 | 提供专业分析、证据和建议 |
| Informed | 史馆/相关观察者 | 接收状态与结果，不改写事实 |

一个任务只能有一个 Driver。多部门参与不等于多人共同兜底。

### 5.2 按价值流组织团队

参考 Team Topologies 与 Amazon 单线程所有权机制，项目团队应按价值流组织：

| 团队类型 | 朝堂 OS 责任 |
| --- | --- |
| 主线价值流团队 | 端到端拥有“合同建案到归档”客户结果 |
| 平台团队 | 负责军机处、worker、事件账本、权限、可观测与发布能力 |
| 专业子系统团队 | 负责刑部法律、户部财务、工部技术等高认知负荷能力 |
| 赋能/审查团队 | 负责御史质量、安全、评测规范，帮助而不接管主线 |

主线团队遵守“you build it, you run it”：开发者同时承担测试、运行、告警和客户结果责任，减少跨团队交接。

### 5.3 会议与决策节奏

- **每日 15 分钟阻塞会**：只回答主线卡在哪里、谁负责、何时解除。
- **每周 WBR**：只看主线指标、黄金案例、错误预算和客户反馈，不汇报页面数量。
- **双周质量评审**：复盘误放、误拦、无证据结论和人工驳回原因。
- **每月技术雷达**：只决定 ADOPT/TRIAL/ASSESS/HOLD，不在会上直接安装框架。
- **单向门决策**：认证、租户、数据迁移、工作流引擎更换必须写 ADR；可逆参数走 feature flag。

### 5.4 SLO 与错误预算

以下是需要在 canonical Step 0/Step 7B 由 owner、样本量和统计窗口正式批准的候选指标，不是本文件另设的发布门：

| 指标 | 首发目标 |
| --- | ---: |
| 正式主线成功率 | 候选起点 `>=95%` |
| 状态漂移率 | `0` |
| 重复正式奏折数 | `0` |
| 越权裁决数 | `0` |
| 重启后可恢复率 | `100%` |
| 无证据高风险结论 | `0` |
| 30 条工作流黄金旨意回归 | 发布候选必须 `30/30`；这不是领域质量统计阈值 |

错误预算耗尽时，冻结新功能，优先恢复可靠性。指标必须来自数据库、事件、真实浏览器和运行监控，不接受人工汇报替代。

## 6. 六部专业管理机制

本节是长期能力治理模板。41 司可以登记、定义契约和沙箱评测；R0/R1 的实现与完成定义只包含合同纵切必需能力。其他能力不得进入当前发布门或外部承诺。

### 6.1 部门不是提示词，而是版本化能力契约

每个部门必须拥有：

```text
DepartmentCapability
├── jurisdiction          职权范围与禁止事项
├── input_schema          最低输入要求
├── output_schema         结构化输出契约
├── evidence_policy       证据等级与引用要求
├── quality_rubric        可计算质量规则
├── tool_permissions      工具与数据权限
├── escalation_rules      升级条件
├── sla_slo               时限与可靠性目标
├── budget_policy         成本与 Token 预算
├── golden_cases          正反黄金案例
└── version               能力版本和变更记录
```

### 6.2 各部门首要专业门

| 部门 | 专业门 | 必须升级的情况 |
| --- | --- | --- |
| 刑部 | 原文条款、位置、法域、责任和修改建议 | 不支持法域、缺失原文、重大责任不明确 |
| 户部 | 可复算数字、口径、假设、现金流和敏感性 | 关键数字无法核对、金额超阈值 |
| 工部 | 可行性、依赖、验收、故障和回滚 | 安全关键、不可恢复、缺少验收条件 |
| 兵部 | 客户事实、竞争依据、下一动作和负责人 | 对外承诺、价格/交期未授权 |
| 礼部 | 受众、事实核验、品牌与合规边界 | 公开发布、敏感声明、无法证明的宣传 |
| 吏部 | 职责、权限、能力、隐私和劳动边界 | 解雇、薪酬、敏感个人数据、歧视风险 |

### 6.3 御史独立性

产生结论的 Agent 不得独立批准自己的结论。御史质量门至少检查：

- 输入是否完整；
- 证据是否存在并可定位；
- 结论是否超出证据；
- 来源等级是否允许正式化；
- 部门结论是否冲突；
- 是否触发人工硬门；
- 输出契约是否完整；
- 是否包含敏感信息或越权动作。

质量门先 shadow、再标注、再灰度 enforce；不得未经误放/误拦评估直接全量阻断。

## 7. 功能整合和淘汰机制

### 7.1 功能五问

任何功能进入主线前必须回答：

1. 是否服务当前 release contract；若不服务，是否明确留在目录、benchmark 或实验层？
2. 是否对应一个明确主线阶段？
3. 是否只读写唯一事实源？
4. 是否产生可审计证据和事件？
5. 是否有黄金案例和失败恢复证明？

两个及以上回答“否”，则进入隐藏、实验或退役清单，不进入首发。

### 7.2 六类处置

| 类型 | 处置 |
| --- | --- |
| 核心主线 | 优先建设和验证 |
| 内部控制面 | 后台保留，不抢客户导航 |
| 观察视图 | 只读统一投影 |
| 执行适配器 | 接入主线，无业务最终状态 |
| 实验功能 | feature flag 默认关闭 |
| 重复/旁路功能 | 适配迁移、监测调用、归零后删除 |

### 7.3 绞杀式迁移

1. 盘点所有建案、派单、查询、奏折、裁决和归档入口。
2. 为每个入口标记 `KEEP / ADAPT / READ_ONLY / RETIRE`。
3. 旧入口先改为 canonical API 适配器，停止写旧业务状态。
4. 使用 feature flag 灰度切流并记录调用量。
5. 达到兼容 SLA、遥测无调用、内部脚本与外部消费者均完成证明且有正式替代后，才进入删除候选；观察窗口由退役 ADR 决定，14 天只能作为候选值。
6. 删除前保留兼容、回滚和审计证据；不得恢复不安全旧写路径。

### 7.4 立即冻结项

在主线达到发布门前，暂停：

- 新部门页面；
- 新独立 swarm 入口；
- 新 Agent 人设和角色数量扩张；
- 与首发无关的视觉重构；
- 多垂直同时商业化；
- 没有黄金案例的新框架接入。

允许的工作只有：唯一状态机、权限与迁移、可靠 worker、持久化 DAG、部门契约、质量门、统一读模型、旧入口退役、黄金案例和生产验证。

### 8.1 Temporal 评估触发阈值

- P95 正式任务时长超过 10 分钟；
- 常见会办超过 5 个持久化节点；
- 人工等待超过 1 小时；
- worker 恢复故障每周超过 2 次；
- 自研重试/补偿代码超过核心编排代码的 30%；

禁止自动安装。所有新框架必须在隔离 PoC 中与当前实现比较成功率、恢复率、延迟、成本、复杂度和运维负担。

## 10. 每个子 change 的统一模板

每个任务开始前必须写清：

1. 用户价值和主线位置；
2. 当前已确认事实、推测和未知；
3. 允许修改和禁止修改范围；
4. 前置依赖；
5. 状态、数据、API 和权限变化；
6. 至少一个先失败的验收案例；
7. 正常、失败、重复、并发和回滚验证；
8. 运行证据和退出码；
9. 未验证项；
10. 完成后是否解锁下一阶段。

连续三次修补仍无法通过同一验收时，停止叠加补丁，回到调查阶段重新判断根因。

### 10.1 计划变更协议

执行中允许调整计划，但必须使用以下规则：

- **拆分**：阶段过大时可以拆成更小 change，原验收不得丢失。
- **插入**：发现新的安全、数据或契约硬依赖时，可在当前阶段前插入阻塞步骤，并更新依赖图。
- **重排**：只有证明没有共享事实源和硬依赖时才能重排；必须记录理由和风险。
- **跳过**：只能因为已有等价证据；必须链接证据，不能因为困难或赶时间跳过。
- **放弃**：实验无价值或成本过高时，记录结果、清理 feature flag/数据/依赖并保留学习。
- **状态诚实**：计划变化不能把历史失败改写成成功，也不能用新计划追认旧实现为已验证。

任何影响产品范围、权限、数据迁移、正式状态或外部引擎的一次性门变更都需要 ADR 和明确批准人。

### 10.2 反模式清单

- 先选热门框架，再为它寻找问题。
- 为 D0、D1、D2 建三套任务系统。
- 页面根据多个接口自行推断业务状态。
- 让生成结论的同一个 Agent 批准自己的质量。
- 长期双写两个事实源而没有退役日期。
- 用排除失败测试后的局部绿色代替发布门。
- 把 shadow 质量门宣传为已经 enforce。
- 一个巨型 PR 同时修改状态机、权限、数据库和前端。
- 用更多文档掩盖未回答的运行未知项。
- 为了赶进度恢复已经判定不安全的旧写路径。

## 13. 大神会审结论

### 产品判断

用户不应该先理解六部和蜂群。产品是一个可信复杂任务助手；第一 Offer 只卖一个清晰结果：更快发现合同风险、明确必须修改什么，并留下可追溯证据。

### 组织判断

多部门提供专业能力，但必须由一个单线程负责人端到端拥有客户结果。御史提供独立质量门，平台团队提供可靠底座，所有角色都不能另建主线。

### 架构判断

Agent 可以并行思考，不能并行拥有业务真相。不确定性留在节点内容，确定性放在状态机、权限、幂等、证据门、人工裁决和归档中。

### 投资判断

当前最值钱的工作不是增加功能，而是关闭旁路、完成 30 条黄金旨意、拿到第一位真实客户的有用和付费证据。

最终收口：

> 前台是一个简单的超级助手，后台是一套严格的朝堂协作内核；能力目录可以很大，每单班子必须很小，所有能力只服务同一正式任务和一份可裁决成果。
