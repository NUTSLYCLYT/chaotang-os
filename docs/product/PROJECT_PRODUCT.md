## 1. 产品身份

朝堂 OS 是面向个人与团队的 **可信复杂任务超级助手**：

> 用户只需说出目标，系统只召集当前已验证且完成该任务所必需的最小能力，交付一份有证据、有附件、有下一步、可授权、可恢复、可复盘的完整成果。

对外一句话：

> 把复杂目标交给朝堂 OS：确认一次计划，收到一个可信成果包；每个关键结论有据，现实动作仍由你批准。

三省六部是内部治理模型，不是要求用户学习的操作手册。用户始终只面对一个入口、一个计划、一条真实进度线和一个成果包。

### 1.1 产品野心与首发承诺分层

| 层级 | 冻结结论 |
| --- | --- |
| 长期产品 | 可承接跨领域复杂任务的可信超级助手 |
| 统一内核 | 理解、计划、组阁、采证、审查、成果、授权、归档、结果复盘 |
| 能力宇宙 | 六部 41 司与横向专署的版本化能力目录 |
| 首个商业 Offer | 中文、中国大陆法域、制造业/B2B 日常采购、销售、服务合同决策包 |
| 跨域基准 | “去美国看世界杯决赛”只读研究任务，用于验证跨域组合与成果一致性 |

“长期覆盖”不等于“当前可用”。目录登记、已有提示词、页面存在、测试通过和生产可用是五种不同状态，必须分别标识。

## 2. 产品不是什么

| 误区 | 冻结边界 |
| --- | --- |
| 无边界聊天机器人 | 对话不是完成；系统必须形成可验证成果和可终止状态。 |
| Agent 商店或 41 司展厅 | Agent 数量和部门齐全不是用户价值，也不是发布证据。 |
| 自动替用户做主 | 计划确认、正式奏折裁决和现实副作用授权是三个独立的人类决定。 |
| ERP、BI 或普通流程自动化 | 朝堂 OS 处理跨专业判断与成果交付，不替代业务事实系统。 |
| 法律意见或自动签约服务 | 合同包只做 AI 辅助风险决策，不替代律师，不批准签约。 |
| 古风界面演示 | 朝堂语言可切换；底层必须是严肃、可审计的任务系统。 |

## 3. 用户、JTBD 与北极星

### 3.1 产品核心用户

核心用户是有高价值复杂任务、需要跨领域协调，但不想管理多个 Agent 的个人与团队。典型任务包括旅行研究、商业判断、合同、招聘、预算、产品方案和项目交付。

核心 JTBD：

> 当一件事复杂到需要多种专业能力、外部证据和可下载成果时，替我组织最小合适的班子，把不确定性、方案、风险和下一步整理成一份我能直接使用并最终裁决的成果。

### 3.2 第一 GTM ICP

R1 只服务中国大陆制造业/B2B 企业的合同团队：

- 经济购买者：老板、总经理、业务或法务负责人；
- 日常操作者：采购、销售、合同、项目人员；
- 典型痛点：合同原文分散、审查慢、业务与法务反复沟通、风险无证据留痕；
- 购买结果：更快定位风险、明确必须修改或补充什么，并留下可复核的决策链。

这个 ICP 决定第一条销售航线，不反向缩小长期产品身份。

### 3.3 北极星

产品级北极星：

> 每个活跃账户在一个统计周期内形成的“可信价值任务”数量，以及这些任务中后来结果已结算的比例。

一项“可信价值任务”至少满足：用户确认当前计划、关键结论有可核验证据、必需成果可取回、正式结果经过人工裁决、任务未伪造完成。

辅助指标：

- 首次有用结果时间，而不是首段文字时间；
- 30 天内再次委托高价值任务的比例；
- 有效人工裁决率和成果包取回率；
- `SETTLED / eligible SETTLED` 的真实结果率；
- 每任务贡献毛利与人工复核成本；
- 伪证据、错完成、越权动作和跨租户事件必须为零。

页面停留、Agent 数量、token 消耗、下载次数和模型自评分不能单独证明价值。

## 4. 唯一用户旅程

```text
一旨：用户说出目标并提供材料
  → 一卡：系统复述目标、假设、计划、预算、读取范围和交付物
  → 用户确认本次任务
  → 稀疏组阁：只激活满足硬能力需求的最小班子
  → 并行采证、分析、冲突处理和独立审查
  → 一包：结论、证据、附件、缺口、备选方案和下一步
  → 用户对正式奏折采纳 / 补证 / 复核 / 驳回
  → 需要现实动作时另行逐项授权
  → 史馆追加式归档，并在约定时点回填真实结果
```

默认每轮只问一个真正会改变方案的问题。失败也必须交付可用状态：说明卡在哪里、已完成什么、什么仍不可信，以及用户下一步能做什么。

## 5. 一位助手、一条主链、六类观察面

### 5.1 唯一事实链

```text
上书房建案
  → 丞相形成版本化路由与计划
  → 门下省审议任务是否可办
  → 军机处可靠派单
  → 六部 / 专署 / 蜂群形成带来源分奏
  → 御史执行证据、质量和来源门
  → 唯一 FinalMemorial
  → 用户人工裁决
  → 史馆归档与 outcome
```

当前 canonical 对象边界：

| 语义 | 唯一事实源 |
| --- | --- |
| 正式任务 | `DecisionTask` |
| 路由决定 | `ChancellorRouteDecision` |
| 可靠派单 | `OutboxEvent` |
| 执行过程 | `DecreeExecutionEvent` |
| 候选会审结果 | `CourtReview.memorial_json` |
| 唯一可裁决结果 | `FinalMemorial` |
| 人工裁决 | `EmperorDecision` |
| 不可变案卷 | `ShiguanArchive` |

新协议只能成为这些对象的版本化输入、快照或投影；不得另建第二套 Mission、完成状态或正式奏折。

### 5.2 六类观察面

| 界面 | 用户或运营目的 | 不得做什么 |
| --- | --- | --- |
| 上书房 | 唯一建案、补充、确认和裁决入口 | 在浏览器伪造 LIVE 会审或完成 |
| 丞相对话 | 复述目标、追问、呈计划、解释结果 | 代替用户批准任务或现实动作 |
| 军机处 | 显示路由、参与者、阻塞、重试和冲突 | 绕过正式任务另建蜂群会话 |
| 六部 / 专署 | 查看与处理专业分奏 | 自己发布最终奏折 |
| 御史 / 门下 | 独立质量、来源与安全门 | 因达到最大轮次而自动放行 |
| 史馆 | 归档、版本、裁决、结果和复盘 | 覆盖或改写历史证据 |

普通用户默认只见上书房、丞相、一条状态线和成果页；组织拓扑按需下钻。

## 6. 六部 41 司能力目录

目录代号：`TARGET_DIRECTORY_V1`。它是能力治理和长期产品导航，不是任何 release 的完成清单。

| 部 | 目标司 | 主要能力域 |
| --- | --- | --- |
| 吏部 | 官制司、选才司、考功司、薪酬司、人事司、劳关司、行政司 | 组织、招聘、绩效、薪酬、劳动关系与行政 |
| 户部 | 度支司、金库司、计簿司、价本司、投审司、稽核司 | 预算、资金、核算、成本、投资与财务审计 |
| 礼部 | 品牌司、客群司、文宣司、招商司、公关司、传播司、审辞司 | 品牌、用户、内容、合作、公关、渠道与表达审查 |
| 兵部 | 布阵司、商机司、攻坚司、价策司、渠道司、销运司、客成司 | 战略、销售、定价、渠道、销售运营与客户成功 |
| 刑部 | 契约司、公司司、合规司、争讼司、劳法司、知产司、法运司 | 合同、公司、合规、争议、劳动法、知识产权与法务运营 |
| 工部 | 方案司、物料司、进度司、质量司、现场司、交付司、承诺司 | 方案、供应、项目、质量、现场、交付与承诺管理 |

钦天监、御史台、锦衣卫、太医院、翰林院、史馆等是横向专署或治理角色，不计入 41 司。

每项能力必须单独记录：

- `DIRECTORY_ONLY`：只有归属和契约草案；
- `SANDBOX`：可在隔离环境运行；
- `INTERNAL`：内部黄金任务达标；
- `PILOT`：命名客户、人工保护、可退出；
- `PRODUCTION`：通过质量、安全、运营和商业门；
- `RETIRED`：不可再路由。

注册、实现、Beta、生产四者不得互相替代。每次任务只激活当前 release 允许且覆盖硬需求的最小能力集合。

## 7. 第一商业 Offer：合同决策专业包

### 7.1 支持范围

R1 `ContractReviewPack` 只支持：

- 中文；
- 中华人民共和国大陆法域；
- 制造业/B2B 日常采购、销售和服务合同；
- 原文风险定位、严重度、缺证、建议修改、谈判与内部确认问题；
- PDF、DOCX、JSON 和证据索引组成的成果包；
- 用户或企业授权人作最终裁决。

明确不支持：跨境、劳动、证券金融、强监管专项合同、法域不明材料、自动签约、付款、发信、删除或任何未经单独授权的现实动作。超范围任务必须 `NEED_LEGAL_REVIEW`，不得给出“可签”结论。

### 7.2 五种保守裁决

| 枚举 | 用户含义 |
| --- | --- |
| `NEED_INFO` | 缺少会改变判断的材料或背景 |
| `REVISE_BEFORE_PROCEED` | 存在必须先修改或谈判的问题 |
| `PROCEED_TO_HUMAN_APPROVAL` | 在已声明范围和证据下，可提交授权人继续裁决 |
| `BLOCKED` | 支持范围内存在当前不可接受或无法消解的阻塞 |
| `NEED_LEGAL_REVIEW` | 超范围或需要执业律师判断 |

`PROCEED_TO_HUMAN_APPROVAL` 不得简写为“可签”“安全”或“AI 批准”。

### 7.3 最小风险项与成果包

每个风险项至少包含：合同版本、`riskLevel`、页码/条款号、原文 `evidence`、`explanation`、`missingEvidence`、`recommendedRevision`、`sourceLabel` 和 `engineTier`。合同 `riskLevel` 只使用 `critical / high / medium / low`；精确定义和统计口径由 R0/R1 PRD 第 8.0 节拥有，不得借用 release-severity P0/P1。

完整成果包至少包含：

1. 一页裁决摘要；
2. 必须先处理的 3–5 项问题；
3. 完整风险表与原文锚点；
4. 必须改 / 建议改 / 可接受清单；
5. 建议修订文本和谈判话术；
6. 需要业务负责人或律师确认的问题；
7. PDF 报告、DOCX 建议稿、JSON 结果与 `ArtifactManifest`；
8. 版本、来源层级、质量门、人工裁决与审计摘要。

必需附件缺失时只能显示 `PARTIAL`，不能显示“已交付”。

### 7.4 R1 用户角色

| 角色 | 可做 | 不可做 |
| --- | --- | --- |
| 客户成员 | 建案、补证、查看、导出授权对象 | 查看无授权任务或内部节点 |
| 客户裁决人 | 采纳、补证、复核、驳回并记录理由 | 改写质量门或历史证据 |
| 租户管理员 | 管理本租户成员、审计、导出和删除请求 | 跨租户访问 |
| 内部运营 | 在脱敏控制面重试、升级事故 | 默认读取正文或替客户裁决 |
| 平台管理员 | 按受控流程冻结、恢复、发布 | 绕过上书房写业务事实 |
| 法律复核者 | 按 Pilot 协议复核指定结果 | 冒充系统自动能力或隐瞒责任主体 |

合同正文、附件、OCR、分析结果和评论默认为租户机密数据。R1 接收真实材料前，DPA、保密、用途、处理者、保留/删除、人工复核和退出条款必须生效。

## 8. 世界杯旗舰 Benchmark

`WorldCupTravelMission` 验证的是同一内核能否组合赛事、入境、机票、酒店、当地交通、预算、保险、Plan B 与多附件，并保持时间、地点、价格和来源一致。

当前定位：

- 只读研究与内部/受控 Beta benchmark；
- 不代购球票、机票或酒店；
- 不作为 R1 销售 Offer；
- 不因生成攻略就宣称旅行服务生产可用；
- 通过它发现的通用能力，仍须经过对应专业包的独立 release gate。

## 9. 发布层级

| 层级 | 产品目的 | 对外边界 | 退出门归属 |
| --- | --- | --- | --- |
| R0 `INTERNAL_TRUSTED_KERNEL` | 用合同纵切证明不伪证据、不伪完成、可恢复的可信内核 | 内部账号；仅限合成材料，或经合法性复核且不可重新识别的去标识测试材料；不得接收客户原件或可重新识别材料 | R0/R1 PRD |
| R1 `PAID_DESIGN_PILOT` | 与最多 5 家命名客户验证合同价值和责任边界 | 有配额、有人审、可退出；不称 GA | R0/R1 PRD |
| R2 `INVITATION_PRODUCTION` | 朝堂 OS 1.0 邀请制生产版，以合同包为首个稳定 Offer | 通过准入的邀请客户；不开放公众自助 | 后续 R2 release PRD |
| R3+ `EVIDENCE_GATED_EXPANSION` | 逐个解冻第二 Offer、世界杯 Beta 与更多能力 | 每项能力独立证据门 | 各 Solution Pack PRD |

发布顺序固定为：

```text
R0 内部可信内核
→ R1 合同 Paid Design Pilot
→ R2 邀请制生产
→ R3+ 按证据扩展六部宽度
```

这取代“先把六部全部做到 L3，再决定发布范围”的旧顺序。41 司可以继续做目录、契约和沙箱治理，但不能阻塞合同纵切，也不能据此获得生产承诺。

## 10. 商业与扩张纪律

R1 的配额、周期、价格和支持时限都是 `OFFER_HYPOTHESIS`，必须通过至少一份有边界、有人审、可退出的真实付费共创合同验证，不能提前写成成熟年费产品。

R1 的 5/3/1/1 使用同一冻结 cohort：只计算不同的外部目标客户组织，同一实际购买组织只计一次，内部账号、关联测试账号、DEMO 和无真实任务的 Design Partner 不计。3 家复用、1 家付费和 1 条证言都必须来自最初 5 家，条件可由同一家客户同时满足。

R1 至少验证：

- 5 家目标客户各完成至少 1 个合格 Pilot 任务：成果达到 `DELIVERED`，且客户对精确奏折留下有效人工裁决；
- 其中 3 家在首单 `DELIVERED` 后 30 个自然日内，由客户主动发起并完成第 2 个合格任务；内部代操作、自动重放、失败重试和同任务版本刷新不算复用；
- 其中 1 家依据已签 Pilot 协议完成至少 1 笔已清算且未退款的外部付款；赠送额度、内部转账和未支付发票不计；
- 其中 1 家就已完成的合格任务出具获客户书面授权、可公开使用且可核验的客户证言；私下反馈、内部 outcome 或未经授权的引语不计；
- 质量、安全、人工复核、成本和退出门持续成立。

完成、复用、付款和证言的精确证据字段由 R0/R1 PRD 第 8.3.1 节拥有。5/3/1/1 是商业信号，不是 GA 充分条件。第二个收费专业包必须另有自己的支持矩阵、黄金集、专家 holdout、真实 pilot、成本证据和 stop-ship；不得继承合同包的质量证明。

## 11. 产品红线与 stop-ship

任何一项发生，停止扩流并阻止发布：

1. DEMO、FALLBACK、模型自述或非空字符串被包装成 LIVE 证据；
2. 门下仍有否决理由，却因达到最大轮次自动放行；
3. 接单回执、部分文本或部分附件被标记为完成；
4. 关键风险没有原文锚点，或伪造条款、来源、执行成功；
5. 未授权的购买、付款、签约、发送、发布、删除或分享；
6. 计划确认、奏折裁决和现实动作授权被合并为一次点击；
7. 客户私有数据自动进入共享知识库、训练、Skill 或跨租户上下文；
8. 跨租户/跨用户泄露，或平台人员默认可读合同正文；
9. benchmark、目录或页面存在被宣传为正式 Offer；
10. release HEAD、artifact、schema、运行身份或验证证据不一致；
11. 删除、恢复、回滚或事故通知无法验证；
12. 未关闭的 release-severity P0/P1。
