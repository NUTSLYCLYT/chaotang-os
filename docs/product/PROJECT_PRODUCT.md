# 朝堂 OS 项目产品文档

本文件整合历史归档中仍然有价值的产品描述。旧归档中的技术实现、部署、接口、代码路径、运行命令和历史排障内容不再作为项目级文档保留。

## 1. 产品定位

朝堂 OS 的产品主体不是某个客户定制项目，也不是古风界面演示。

朝堂 OS 是一套面向企业老板和经营负责人的 **AI 决策执行操作系统**：

```text
用户提出真实经营问题
  -> 系统识别关键前提、缺口和风险
  -> 拆成可执行路径、预算、责任和验收
  -> 多专业视角会审
  -> 形成可裁决奏折
  -> 用户采纳、打回、追问或派遣
  -> 史馆沉淀证据链和复盘
```

对外一句话：

```text
老板提一个真实问题，AI 内阁替你分析、拆路径、控风险、出奏折，你只做最终裁决。
```

## 2. 不是什么

| 误区 | 正确认知 |
| --- | --- |
| 企业 BI 工具 | BI 看数据，朝堂 OS 帮用户做经营判断。 |
| 通用 AI 助手 | 通用助手对话即忘，朝堂 OS 需要沉淀证据、裁决和复盘。 |
| 流程自动化工具 | 自动化工具执行流程，朝堂 OS 先判断该不该做、怎么做、风险在哪。 |
| ERP 系统 | ERP 管资源，朝堂 OS 管经营问题、专业会审和裁决闭环。 |
| 古风控制台 | 三省六部是治理框架，不是装饰皮肤。 |

## 3. 北极星

当前唯一北极星：

```text
让 1 个真实老板，用朝堂 OS 真做成 1 件经营决策，并愿意说：“这帮我了。”
```

所有产品路线都必须服务这个目标。页面、部门、视觉、蜂群、知识库和商业化动作都只是手段。

可验收标准：

- 用户提出一个真实经营问题。
- 系统指出关键前提、缺口、风险和下一步。
- 专业视角形成可读、可裁、可追溯的结果。
- 用户能采纳、打回、追问或派遣。
- 史馆留下证据链和复盘，下一次建议能引用。

## 4. 当前样板与通用化关系

铭硕电池是第一批真实样板，不是产品主业。

正确关系：

```text
朝堂 OS（通用 AI 决策执行 OS）
  -> 三省六部治理框架
    -> 铭硕电池 / 储能 / 合同审查 / 财务诊断等样板场景
```

铭硕样板的价值：

- 证明客户自有业务场景可以接入朝堂 OS。
- 证明多专业会审能落到真实行业问题。
- 形成可复制案例：从电池售后、产品、市场、项目管理复制到第二个客户。

产品叙事不能写成“铭硕专用系统”；销售对象也不能被锁死在单个客户。

## 5. 核心产品闭环

朝堂 OS 的主链路：

```text
大殿看全局
上书房发起事项
专署查证风险
六部给专业判断
军机处统筹会审与执行
史馆归档复盘
```

最小有用交付：

```text
老板一句话
  -> 上书房整理成事项
  -> 丞相给初判和路径
  -> 军机处召集专业视角
  -> 六部 / 专署给判断和风险
  -> 形成一份奏折
  -> 老板裁决
  -> 史馆留痕
```

产品验收不看“页面是否很多”，而看用户是否真的完成一次判断。

### 5.1 最终产品形态：一条决策主线，六类观察面

朝堂 OS 1.0 最终形态冻结为 **老板决策工作台**，不是 Agent 商店，也不是六个各自回答问题的聊天页面。所有入口最终汇入同一个正式任务聚合：

```text
老板提出真实问题
  -> 上书房拟旨并由老板确认
  -> 丞相生成唯一版本化路由
  -> 军机处通过可靠 outbox 派单
  -> 六部 / 专署 / 蜂群产生带来源的分奏
  -> 军机处汇总为候选奏折
  -> 御史检查质量、证据和来源等级
  -> 通过后唯一晋升为正式奏折
  -> 老板人工采纳 / 补证 / 复核 / 驳回
  -> 史馆保存奏折、裁决、证据链和后续结果
```

六类产品界面不是六套执行链，而是同一任务的不同观察面：

| 界面 | 最终职责 | 禁止行为 |
| --- | --- | --- |
| 大殿 | 只看全局优先级、风险和待办 | 自己生成第二份决策结论 |
| 上书房 | 唯一正式发起、确认和人工裁决入口 | 在浏览器本地伪造 LIVE 会审或圣裁 |
| 军机处 | 查看路由、参与者、节点状态、冲突与重试 | 绕过正式任务另建一次性蜂群会话 |
| 六部 | 查看和处理自己收到的专业分奏 | 直接发布“最终奏折”或代替老板裁决 |
| 专署 | 补证、审计、风险和预测 | 把 FALLBACK/DEMO 升级为可裁决事实 |
| 史馆 | 归档不可变过程、裁决和结果反馈 | 回写篡改当时的奏折与证据 |

后台事实源固定为：`DecisionTask` 管正式任务，`ChancellorRouteDecision` 管路由，`OutboxEvent` 管可靠派单，`DecreeExecutionEvent` 管过程事件，`CourtReview.memorial_json` 只代表候选奏折，`FinalMemorial` 代表唯一可裁决正式奏折，`EmperorDecision` 管人工裁决，`ShiguanArchive` 管归档。任何页面不得再建立同语义的本地事实源。

正式奏折必须同时满足：确定性质量门通过、来源不为 `FALLBACK/DEMO`、候选内容有效、一旨最多一条正式记录。采纳、准奏和归档还必须有明确人工确认；未满足时只能补证、复核或驳回。

1.0 首发商业演示只展示这一条链。首个付费切片优先使用“刑部合同审查”，因为它天然需要证据、风险红线、人工签字和可追溯归档；其他部门能力作为同一内核的扩展，不另起产品主线。

#### 5.1.1 首发客户看到的产品

首发产品名义上仍是朝堂 OS，客户实际购买和每天使用的是 **合同审查决策工作台**。首屏只有一个主动作：“上传或粘贴合同，开始审查”。部门、Agent 数量、路由算法和蜂群拓扑属于系统内部能力，不作为客户理解产品的前置条件。

客户可见的稳定界面限定为四个：

| 客户界面 | 唯一目的 | 核心内容 |
| --- | --- | --- |
| 上书房工作台 | 建案并查看当前进度 | 合同、业务背景、缺失材料、唯一状态线、待人工动作 |
| 刑部决策单 | 判断能否签以及必须改什么 | 原文证据、风险等级、解释、缺证、建议修订、责任人 |
| 圣裁确认 | 记录人的最终决定 | 采纳、补证、复核、驳回及理由，不允许 AI 代签 |
| 史馆档案 | 追溯和复盘 | 输入版本、路由、分奏、正式奏折、裁决、导出与后续结果 |

大殿、军机处和其他部门在首发阶段是运营与可解释性界面：只有客户任务需要或管理员排障时才展开，不能抢占主导航，也不能要求客户先理解组织结构再完成合同审查。

角色权限固定如下；所有角色都只能在自己租户的数据范围内操作：

| 角色 | 默认可见界面 | 可执行动作 | 明确禁止 |
| --- | --- | --- | --- |
| 客户成员 | 上书房、刑部决策单、史馆自己的任务 | 建案、补证、查看、导出 | 查看其他成员无授权任务、操作内部节点 |
| 客户裁决人 | 客户成员界面 + 圣裁 | 采纳、补证、复核、驳回 | 伪造质量门或改写历史证据 |
| 租户管理员 | 本租户任务总览与成员授权 | 管理本租户权限、审计和数据请求 | 查看其他租户、修改平台运行状态 |
| 内部运营 | 军机处运行视图、脱敏故障信息 | 重试可恢复节点、升级事故 | 从内部页面另建或裁决客户任务 |
| 平台管理员 | 跨租户运行指标和受控事故工具 | 按审计流程恢复、冻结、发布 | 默认读取合同正文、绕过上书房写业务事实 |

#### 5.1.2 合同决策单的最小稳定契约

每个风险项至少包含：`riskLevel`、原合同 `evidence` 与位置、`explanation`、`missingEvidence`、`recommendedRevision`、`sourceLabel` 和 `engineTier`。整份决策单还必须包含合同版本、生成时间、任务/奏折标识、质量门结果和人工裁决状态。

首发价值承诺是“更快发现风险、明确必须改什么，并留下可追溯证据”，不是替代律师出具法律意见，也不是保证合同绝对安全。没有原文证据的高风险结论不得晋升为正式奏折；证据不足必须明确标记并进入补证流程。

首发法律范围冻结为中文、中华人民共和国大陆法域、制造业/B2B 日常采购、销售和服务合同。跨境、劳动、证券金融、强监管行业专项合同以及无法确定适用法的材料必须 fail closed：可以抽取和提示范围不支持，但不得给出“可签”结论，必须升级到人工法律审查。质量指标按合同类型分层报告，不允许把不同法域或不支持类型混入总分母。

#### 5.1.3 扩张解冻门

六部扩张不是按页面完成度解冻，而是按客户证据解冻。刑部主线在至少 5 家真实客户中达到 3 家复用、1 家付费、1 条可公开证言，并持续满足黄金案例质量门后，才允许投入第二条付费切片。否则所有新部门能力保持实验或隐藏状态。

## 7. 六部产品定义

每个部门不是介绍页，而是 AI 部门作战台。用户进入部门时应看到正在处理的工作、产出、质量、阻塞和下一步。

| 部门 | 替代对象 | 核心职责 | 老板最关心的问题 |
| --- | --- | --- | --- |
| 户部 | 财务、预算、经营分析、投资评估、报价负责人 | 成本、预算、ROI、现金流、报价和投资判断 | 值不值得花钱？最坏损失是多少？ |
| 工部 | 产品、研发、方案、交付负责人 | 产品方案、可交付性、实施路径和验收 | 这事能不能做成，怎么交付？ |
| 兵部 | 销售、运营、客户战情、竞争攻防负责人 | 商机推进、客户下一步、竞争与资源取舍 | 怎么赢客户，下一步谁办？ |
| 刑部 | 法务、风控、合规负责人 | 合同、承诺、责任、合规和不可逆风险 | 能不能签，必须改哪几条？ |
| 礼部 | 品牌、市场、公关、对外表达负责人 | 客户话术、对外材料、发布边界和品牌一致性 | 能不能对外说，怎么说才可信？ |
| 吏部 | 人事、组织、招聘和权限负责人 | 岗位画像、招聘必要性、组织职责和人员安排 | 要不要招人，谁该负责？ |

部门输出必须能被老板裁决，不能停留在说明性文案。

## 8. 首发商业切片

历史归档中出现过多个首发方向：经营决策闭环、户部财务诊断、刑部合同审查、储能 PACK 评审。当前统一口径如下：

朝堂 OS 是总产品；历史比较已经完成，当前首发商业切片冻结为 **刑部合同审查决策工作台**。

优先级判断：

1. 是否能用一个真实材料在 3 分钟内产出可读结果。
2. 是否能明显降低老板风险、时间或沟通成本。
3. 是否天然需要证据、留痕和人工裁决。
4. 是否能复用到第二个客户。
5. 是否有人愿意为它付第一笔真钱。

历史候选与当前裁决：

| 切片 | 适合客户 | 价值主张 |
| --- | --- | --- |
| 刑部合同审查 | 储能、能源、制造业 B2B 老板 | **已选首发**：每份合同快速识别能不能签、改哪里、出事是否有据。 |
| 户部财务诊断 | 中小企业老板、财务负责人 | 冻结为第二切片候选；当前不投入主线。 |
| 储能 PACK 评审 | EPC、保险、认证、PACK 采购评审方 | 冻结为第二切片候选；当前不投入主线。 |
| 经营决策奏折 | 老板、总经理、项目负责人 | 作为长期通用能力，不与合同首发并行销售。 |

收敛原则：

- 刑部合同主线未达到 5/3/1/1 客户证据门前，不同时推进多个垂直。
- 其他方向冷藏，不删除认知，但不投入主线资源。
- 达到解冻门后，第二切片仍需单独的客户发现、质量基线和 Go/No-Go 决策，不能自动进入主线。

## 10. 商业模式

阶段性建议：

| 阶段 | 模式 | 目标 |
| --- | --- | --- |
| 0-6 个月 | 高接触实施 + POC + 年费授权 | 签下 3-5 个付费客户，拿到真实案例。 |
| 6-18 个月 | 实施继续 + 行业模板化 + 轻 SaaS | 将实施经验沉淀成模板，开始规模化试用。 |
| 18 个月后 | SaaS 规模化 + 私有化部署 | 扩大客户数，并服务数据敏感的大客户。 |

推荐定价锚点：

- POC：3 个月，1.5 万到 3 万，用真实材料跑出价值。
- 企业标准版：每年 3.6 万到 8 万。
- 企业专业版：每年 8 万到 20 万。
- 私有化 / 定制版：20 万起，按数据安全、定制深度和服务范围报价。
- 单份轻决策：99 到 299 元，用于验证某些高频切片是否有低价入口。

定价纪律：

- 先收第一笔真钱，再谈估值和大规模增长。
- 不卖“多智能体系统”，卖“老板能更快更稳做决策”。
- 不承诺未落地能力，不把演示包装成生产可用。

## 11. GTM 与内测

第一阶段不要面向所有人泛泛推广，要围绕真实老板和真实问题。

内测分层：

| 类型 | 人数 | 目标 |
| --- | ---: | --- |
| 核心共创客户 | 5-10 | 深访、试真实材料、打磨付费切片。 |
| 商会体验客户 | 30-50 | 演示、收反馈、识别高意向客户。 |
| 候补名单 | 100-300 | 留资，等待邀请和场景匹配。 |

演示只跑一条链：

```text
老板输入一句真实问题
  -> 系统生成预案
  -> 多专业视角会审
  -> 输出奏折
  -> 老板裁决
  -> 史馆归档
```

不要展示所有页面，不要讲技术名词。

每个内测用户至少收集：

- 是否 10 秒内看懂第一步。
- 哪一步最有价值。
- 哪一步不可信。
- 是否愿意带真实问题再试一次。
- 是否愿意付费。
- 最担心什么。
- 愿意推荐给谁。

## 12. 产品红线

1. 不把 DEMO、FALLBACK 或样例包装成 LIVE。
2. 不为了扩部门、扩页面牺牲第一条真实闭环。
3. 不让 AI 自动执行不可逆动作；高风险事项必须人工裁决。
4. 不做没有证据来源的判断；缺证必须明确降级。
5. 不把客户私有数据沉淀为公共知识。
6. 不用“多智能体系统”等技术词作为主卖点。
7. 不承诺报价、交期、合同、合规和安全结果，除非有证据和签字。
8. 不同时追多个垂直，优先让一个客户说“有用”并付费。

## 13. 阶段路线

### 阶段 0：证明一个真实闭环

目标：一个真实老板用一个真实材料完成一次判断，并说“这帮我了”。

输出：

- 一条可演示链路。
- 一个真实案例。
- 一次归档复盘。
- 一个明确付费意向或第一笔付款。

### 阶段 1：验证已冻结的首发商业切片

目标：用刑部合同审查决策工作台获得真实复用与首笔付费；不再重新进行四选一。

输出：

- 场景单页。
- 标准演示脚本。
- POC 交付边界。
- 报价和试用机制。

### 阶段 2：沉淀可复制模板

目标：将首发切片复制到第二个客户。

输出：

- 可复用客户 onboarding。
- 场景资料清单。
- 标准奏折结构。
- 反馈与复盘闭环。

### 阶段 3：扩展行业模板

目标：在保持主引擎不变的前提下，扩展第二、第三个垂直方向。

候选方向：

- 直播合规御史台。
- 外贸全链路决策 agent。
- 招投标合规与成本会审。
- 跨境合规 / 数据出境。
- 一人公司 CEO 副驾。
- AI 数字员工市场。

解冻规则：只有刑部主线先达到 5/3/1/1 客户证据门和持续质量门，才允许对一个候选方向做小成本发现；候选仍须独立通过立项决策。

## 14. 当前最重要动作

1. 选一个真实客户和一份真实材料。
2. 用刑部合同审查主线跑出可读、可信、可裁决结果。
3. 让客户判断是否“有用”。
4. 争取第一笔 POC 或单份付费。
5. 把这次过程归档为第一个真实案例。

一句话收口：

```text
先别证明朝堂什么都能做，先证明它能帮一个老板做成一件真事。
```
