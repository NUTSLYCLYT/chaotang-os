# 朝堂 OS 2026 高质量上线开发路线图

> 文档状态：执行中路线图  
> 更新日期：2026-07-12  
> 适用范围：`chaotang-os` 根项目、前端体验线、后端运行线与产品内测  
> 编写时快照：`feature-chaotang-ext` / `cd4edf9`，执行时必须重新采集基线，不得把此 SHA 当作持续当前事实  
> 产品事实源：后端运行服务；前端只展示契约，不复制裁决逻辑  
> 核心原则：在原有项目上做最小修复，先上线一条真实闭环，再扩完整朝堂

> 已批准决策（2026-07-12）：用户批准“最小 diff 修通生产链，首发阶段默认拒绝重构”，并批准“每个候选提交后运行一次验证闭环，正式发布前再完整运行一次”。

## 1. 文档目的

本路线图指导朝堂 OS 从“功能较完整的发布候选”进入“安全、可信、可收费的封闭内测”。它解决四个问题：

1. 后续开发先做什么、后做什么。
2. 每个阶段如何证明完成，而不是只声称完成。
3. 如何同时守住用户价值、租户安全、运行质量和产品减法。
4. 何时允许扩展六部，何时必须继续聚焦首发切片。

本路线图不是愿望清单。任何阶段未达到退出条件，不得越过门禁进入下一阶段。

### 1.1 上线优先、最小改动原则

后续工作默认采用“修通现有链路”，不是“借机重建系统”。每个实现方案必须先回答：能否通过修正现有路由、查询条件、adapter、配置、测试或错误处理完成？只有答案明确为不能，才允许讨论新服务或新抽象。

允许优先修改：

- 现有文件中的局部 bug、权限过滤和状态处理。
- 已有 API 与前端 adapter 的接线。
- 现有 production rewrite、启动配置和发布脚本。
- 防止回归所需的最小测试、日志和门禁。
- 不改变用户主流程的数据迁移和兼容处理。

默认禁止：

- 迁移框架、替换数据库或重写 flow engine。
- 重做页面、导航体系或视觉系统。
- 为“未来可能需要”新增通用平台、服务、BFF 或抽象层。
- 同时改造多个部门或统一所有历史接口。
- 把低风险技术债包装成上线阻塞项。
- 在功能提交中顺手清理无关代码。

若预计修改超过一个既有业务域、引入新的运行组件、改变公共契约或需要大规模数据迁移，执行者必须先停止，给出“最小修复 / 中等修复 / 重构”三个方案，由用户批准后再行动。

本原则已由用户批准，不再作为可选建议。后续 Agent 若希望偏离，必须提供现有实现无法安全修复的代码证据、迁移与回滚方案，并重新取得用户批准。

### 1.2 已批准的验证闭环

每个候选提交后必须运行一次与变更范围成比例的 `verification-loop`；正式发布前必须运行完整 production 验证。验证失败时停止推进，不得以“与本次关系不大”为由直接越过，必须先完成归因和阻塞等级判断。

候选提交后的最小闭环：

```text
受影响测试
  -> 类型/构建检查
  -> 相关 API 或 Harness
  -> diff review
  -> 记录命令、exit code、commit SHA
```

正式发布前的完整闭环：

```text
production build
  -> 全量关键测试
  -> production browser 主链
  -> tenant/user 隔离
  -> release gate / true-chain / final harness
  -> migration / backup / rollback
  -> 独立 review
```

## 2. 产品定义

### 2.1 一句话定位

> 老板提交一个真实经营问题，AI 内阁给出有证据、有风险边界、有下一步的决策单，老板作最终裁决，史馆保存结果并反哺下一次判断。

### 2.2 2026 年目标

到 2026 年底，朝堂 OS 应成为中国制造业和产业 B2B 老板处理高风险经营决策时，最可信、最快、最容易形成裁决证据链的 AI 产品之一。

“最好”不用页面数、Agent 数或模型参数衡量，而用以下结果衡量：

- 用户首次使用即可理解。
- 3 分钟内获得第一份具体价值。
- 高风险判断能够引用证据。
- 出错时诚实、可定位、可恢复。
- 真实使用能够形成结果数据飞轮。
- 至少出现一笔真实付费 POC。

### 2.3 首发商业切片

当前推荐首发切片为“刑部合同审查决策单”。

唯一主链：

```text
登录
  -> 上传或粘贴合同
  -> 补充交易背景
  -> 获取真实风险判决
  -> 查看原文证据与必改条款
  -> 用户采纳 / 打回 / 追问
  -> 导出决策单
  -> 史馆归档
  -> 回填真实结果
```

选择该切片的原因：输入清晰、价值直观、风险痛感强、结果可由专业人员复核，并天然需要证据、人工裁决和归档。

### 2.4 非目标

首发阶段不做：

- 不同时完善所有六部和所有司级页面。
- 不扩建礼部二级模块。
- 不新增只为展示技术复杂度的 Agent 或蜂群。
- 不重做冻结的大殿体验与接口。
- 不让 AI 自动执行付款、签约、发布、删除等不可逆动作。
- 不用 mock、fallback 或直连后端结果冒充 production 用户链路。
- 不以“全量测试数量很多”代替真实客户结果。
- 不在首发阶段追求架构完美；安全、正确性和真实主链之外的技术债进入上线后 backlog。

- 全量后端存在 8 个既有失败，必须维持无新增并记录准确基线。
- 合同审查首发链路尚未取得完整 production 浏览器证据和真实付费证据。

### 3.3 需要产品确认的假设

- 首发商业切片采用刑部合同审查，而非户部财务诊断或完整经营奏折。
- 本租户 admin 可以通过显式 opt-in 查看 `user_id="anonymous"` 的历史孤儿台账。
- 同租户 admin 的台账 prune 权限覆盖本租户所有用户，而不是只覆盖本人。

若这些假设发生变化，必须按第 12 节变更协议更新路线图。

其中 admin 权限语义是 `WF-02` 的硬入口条件。在产品未确认前，默认拒绝额外访问，不实现隐式 admin 例外。

## 4. 永久工程不变量

每次提交都必须维持：

1. `/dadian` 冻结边界不被无关任务触碰。
2. 前端不新增承载生产业务逻辑的 Next.js BFF、route handler 或 server action。
3. 后端拥有鉴权、租户隔离、路由、裁决、归档和运行事实。
4. LIVE / MIXED / FALLBACK / DEMO 边界必须诚实。
5. 高风险动作必须保留人工签字闸。
6. 租户私有数据不得进入公共知识库。
7. 单测、Harness、浏览器和 release gate 的证据不得相互替代。
8. 现有未跟踪的 `.playwright-*` 和 `backend/knowledge/docs/ima_archived/` 文件不纳入功能提交。
9. 所有跨线实质变更更新根级 change 记录。
10. 未实际运行的验证命令不得写成通过。
11. 每个 WF 首选最小 diff；若能修现有实现，不新建平行实现。
12. 评审必须区分“上线阻塞”“上线后技术债”和“未来产品机会”。

### 4.1 变更规模门

| 等级 | 典型范围 | 默认处理 |
| --- | --- | --- |
| S | 单文件或局部配置/测试 | 直接按 TDD 修复 |
| M | 同一业务域 2 至 5 个文件 | 给出短计划后执行 |
| L | 跨业务域、公共契约或迁移 | 必须用户批准 |
| XL | 新运行组件、框架替换、系统重构 | 首发阶段默认拒绝 |

“尽快上线”不等于跳过测试，而是拒绝与首发结果无关的改造。

## 6. 十个核心工作流与前置/子门

`WF-00` 是执行前置，不计入十项核心工作；`WF-06.GATE-A` 是 `WF-06` 的强制子门，也不单独计数。

### WF-00：建立可信基线（前置）

**目标**：让所有后续 Agent 从同一事实起点工作。

**任务**：

- 记录 branch、HEAD、git status 和未跟踪文件。
- 记录 8081、3050、3002、3001 的监听状态。
- 运行根/前端/后端 doctor。
- 运行 production build、TypeScript 和最小代表测试。
- 记录全量后端 8 个既有失败的准确用例名。
- 核对当前运行服务 commit 是否与 HEAD 一致。

**验证**：

```bash
git status --short
git log -5 --oneline --decorate
node scripts/harness-doctor.mjs
cd backend && python scripts/harness_doctor.py
cd frontend && NEXT_PUBLIC_API_MODE=real pnpm build
```

**退出条件**：基线写入根级 change 记录，所有已知风险标明证据等级和 commit SHA。

**回滚**：不得删除审计记录。通过新提交恢复引用内容，并将原 change 标为 `REVERTED` 或 `SUPERSEDED`，记录原因和替代证据。

### WF-01：修复并证明 Production API 代理

**目标**：用户只通过 3050 即可可靠访问 8081 后端。

**任务**：

- 用同一 token、method、path、query、headers 和 body 对比直连 8081与经 3050请求。
- 覆盖 GET、POST、401、403、404、422、500和流式响应。
- 查明 middleware、basePath、rewrite manifest、App Router 和代理层的真实命中顺序。
- 禁止把错误 JSON 或解析失败转换为 `success: true, data: []`。
- 增加经 3050 的生产代理契约测试。
- 如果 Next rewrite 无法稳定满足要求，使用部署层 Nginx/Caddy 代理 `/chaotang/api/* -> 8081`，不在前端承载业务逻辑。

优先级：先最小修复现有 rewrite/middleware/config；只有证明确实无法稳定修复，且用户明确批准后，才允许增加 Nginx/Caddy 等新运行组件。

**验收**：

- 3050 与 8081 的响应状态和业务 body 一致。
- Authorization、Cookie、Content-Type、query 和 body 不丢失。
- 401/403/404/500 不变成 200。
- P0-A 12 项浏览器验收全部经 3050 重跑通过。

**回滚**：代理变更必须独立提交；保留修复前后 curl/trace 证据，可单提交回滚。

### WF-02：完成 P0-B 上书房用户隔离

**目标**：任何用户不能读取或修改其他用户的 `DecisionTask`。

**任务**：

- 建立所有按 `task_id` 读写的端点矩阵。
- 覆盖列表、详情、status、confirm、transition、review、decision、archive、export 和 deepen。
- 所有真实查询使用 `tenant_id + user_id + task_id` 或经审计的等价所有权条件。
- 统一“真实不存在”和“属于别人”的响应。
- 检查关联 memorial、receipt、review 和 archive 是否形成旁路泄漏。
- 使用两个租户、每个租户两个用户先写 RED 测试。
- 在实现前由产品确认 admin 权限；未确认时采用 default-deny。
- 固定角色矩阵：匿名、普通用户、本租户 admin、跨租户 admin、已删除用户、孤儿数据。

**验收**：

- 跨租户泄漏为 0。
- 跨用户越权为 0。
- 所有上书房相关测试和全量后端测试无新增失败。
- 独立安全审查无 CRITICAL/HIGH。

**验证与证据**：端点矩阵、角色矩阵、测试文件和严重度规则写入本工作流 change；运行上书房隔离专项 pytest、全量后端 pytest、后端 doctor和根 doctor。独立审查报告必须保存到 change 的 review/handoff 文档中。

**回滚**：数据模型变化必须有 downgrade；路由过滤变化独立提交。

### WF-03：正式关闭或修复 P0-D

**目标**：`/api/intel/brief` 在正常、超时和失败场景都有明确上限和来源状态。

**任务**：

- 对 endpoint、搜索、LLM、fallback、持久化和序列化分阶段计时。
- 记录 request_id、stage、duration、provider、timeout、fallback 和 persistence result。
- 测试正常、网络失败、DNS 不可达、空结果、数据库失败五种场景。
- 检查同步调用是否阻塞 async worker。
- 不能复现时使用故障注入提供正式关闭证据。

**验收**：每种场景在规定时间内返回；fallback 不标 LIVE；日志能定位具体阻塞阶段。

**初始量化硬门**：搜索阶段硬超时 8 秒；LLM 阶段硬超时 20 秒；best-effort 持久化最多 2 秒；endpoint 总 wall-clock 硬上限 30 秒，单次不得超过 35 秒；上游失败后 fallback 必须在 5 秒内形成响应。使用 10 个并发请求、每种故障场景至少 20 次运行，要求 p95 ≤ 30 秒且无无限等待。执行 change 可以基于真实 provider 证据调整阈值，但必须在实现前获得批准，不能事后选择有利数字。

**验证入口与产物**：专项 pytest/故障注入脚本在本工作流 change 中冻结；逐阶段时序 JSON、并发统计和关闭结论保存到 `<change>/ci_result/` 与 `review-handoff.md`。未冻结入口前状态为 `NEEDS_CONTEXT`。

**回滚**：可观测字段向后兼容；超时策略独立提交并保留旧值回滚配置。

### WF-04：修复导航与最终发布 Harness

**目标**：所有正式入口存在且自动化可稳定操作。

**任务**：

- 将新事项入口统一为 `/shangshufang`。
- 将已有任务入口统一为带 taskId 的 `/junjichu`。
- 清理或迁移没有正式页面的 `/court-briefing` 引用。
- 修正资源阁按钮目标和 `final-release-harness` 稳定 selector。
- 使用 `data-testid`，避免依赖视觉文本、坐标或动画时序。
- 不触碰大殿冻结结构。

**验收**：主导航无 404、死链、循环重定向；final-release-harness 全绿。

**验证**：运行导航契约测试、相关 Playwright、production build 和 final-release-harness；证据保存到对应前端 change。

**回滚**：独立回滚导航/selector 提交，重跑旧入口健康检查和新入口 404 检查，change 保留并标记回滚原因。

### WF-05：使部署版本可证明

**目标**：健康服务就是当前发布提交，而不是陈旧进程。

**任务**：

- 前后端 health 返回 version、commit、buildTime 和 environment。
- 启动脚本终止旧进程、从当前 repo build 并记录 SHA。
- release gate 对 SHA 不一致、`version: unknown` 或 `sameRepo: false` 直接 STOP。
- 记录 migration revision 和数据库 schema version。

**验收**：3050、8081、当前 HEAD 和数据库 revision 能形成同一发布身份。

**验证**：启动当前构建后读取前后端 health JSON，断言 commit/version/environment/schemaRevision 一致；再运行 prod-doctor。

**回滚**：版本字段保持向后兼容；回滚启动脚本后仍必须返回旧版本身份，不能退回 `unknown`。

### WF-06.GATE-A：刑部合同切片只读差距审计

**目标**：在写代码前区分已实现、未接通、DEMO、本地双轨和完全缺失能力。

**入口条件**：`WF-02` 已通过；执行者已读取刑部前后端入口、API 契约、史馆契约和当前 root change。

**输出**：端点/页面/数据/权限/归档差距矩阵，必填当前证据、缺口严重度、首发是否必须、owner、建议修改路径、验证入口和延期风险。只读审计不得重做页面或新增部门。

**验证**：引用具体前端调用、后端 route、测试和浏览器网络证据；输出到根 change 后等待用户批准范围。

**状态**：`AUDIT_COMPLETE` 表示矩阵完成；`SCOPE_APPROVED` 表示用户批准 `WF-06` 范围；`BLOCKED` 表示发现 P0/关键产品歧义。未达 `SCOPE_APPROVED` 不得进入 `WF-06`。

**回滚/修正**：审计记录不删除；错误结论标记 `SUPERSEDED` 并链接替代证据。发现新安全问题时按第 12 节插入 P0，停止后续开发。

### WF-06：收口刑部合同审查收费主链

**目标**：新用户无需理解朝堂架构即可完成一次高价值合同裁决。

**任务**：

- 审计刑部前端是否仍存在本地 `clause-risk` 与后端 verdict 双轨裁决。
- 后端成为唯一裁决事实源。
- 接通上传/粘贴、交易背景、风险判决、修改建议、人工裁决、导出和史馆归档。
- 户部/工部作为后台参审，不增加用户操作负担。
- 清理死按钮、假 LIVE 和无后端能力入口。

实现必须复用现有刑部工作台和后端 verdict，不为首发另建一套页面或裁决服务。

**输出契约**：

```text
verdict
executive_summary
evidence_quotes
risks
mandatory_changes
acceptable_risks
missing_information
next_action
owner
human_signoff_required
source_label
task_id / archive_id / trace_id
```

**验收**：10 秒内知道第一步；3 分钟内得到首份结果；5 分钟内完成裁决；刷新后可召回。

**验证**：后端合同专项测试、前端 transport/component 测试、production build、经 3050 的 Playwright 主链和史馆召回测试。

**回滚**：前端接线、后端契约和数据迁移分提交；回滚后不得重新启用未标 source label 的本地裁决。

### WF-07：建立高质量输出契约和 Golden Cases

**目标**：质量由可重复规则和案例保证，而不是模型临场表现。

**任务**：

- 建立至少 30 个合同案例：10 常见、10 高风险、5 缺证、5 红队诱导。
- 每个高风险结论必须引用原文。
- 缺证时只能 advisory、blocked 或 abstain。
- 禁止虚构合同条款、法律结论和客户事实。
- 记录人工修正、误报、漏报和最终结果。

**核心指标**：

- 高风险条款引用率：100%。
- 虚构条款：0。
- 缺证显式标记率：100%。
- 人工裁决留痕率：100%。

**验收**：Golden cases、法律红队和御史门禁全部通过，失败案例能定位到具体版本和阶段。

**判定协议**：每个案例记录来源授权、司法辖区、语言、期望标签、条款引用、模型/prompt/provider 版本。条款引用与法律结论分开评分；自动 scorer 只做初筛，高风险案例由两名具备合同经验的复核者独立标注，分歧进入人工仲裁。非确定性模型至少连续运行 3 次并记录波动。

**验证**：运行 golden case runner、legal-redteam 和 yushi gate；输出逐案例 JSON，不只记录总分。

**回滚**：模型或 prompt 回滚到上一通过版本，保留失败案例和评测记录，不删除坏样本。

### WF-08：安全、隐私与数据生命周期门

**目标**：真实合同进入付费内测前，完成数据流、威胁和客户删除能力验证。

**必须覆盖**：

- 文件类型/大小限制、压缩炸弹、宏和恶意文件、文件名/路径安全。
- 传输加密、静态加密、租户级对象存储隔离、预签名 URL 权限和有效期。
- 日志、trace、prompt、provider 请求中的合同正文和个人信息脱敏。
- 第三方模型的数据保留、训练使用、跨境处理和供应商故障边界。
- 数据保留期、客户删除、备份删除、离职撤权、token/session 失效。
- 下载/导出授权、审计、限流、配额、成本滥用和拒绝服务。
- AI 不替代律师的服务边界和专业人员复核流程。

**验证**：编写数据流图和威胁清单，运行恶意上传、越权下载、过期 URL、撤权 session、限流、删除和审计测试。独立安全审查无未解决 CRITICAL/HIGH。

**回滚**：关闭合同上传和第三方 provider 写入入口，保留只读审计；客户删除请求和安全日志不得因功能回滚失效。

### WF-09：Production 浏览器、发布和灾难恢复闭环

**目标**：用真实 production 路径证明用户成功，并证明失败时可恢复。

**环境**：

- 真实 8081 后端。
- 真实 3050 production frontend。
- `NEXT_PUBLIC_API_MODE=real`。
- 真实用户和数据库。
- 禁止以直连 8081作为最终证据。

**验证**：

- 登录、合同提交、判决、裁决、导出、归档、刷新召回。
- 双用户、双租户隔离。
- console、network、trace 和截图证据。
- production build、TypeScript、相关测试、全量后端、doctor、release gate、true-chain、final harness。
- migration upgrade/downgrade、数据库备份、服务回滚演练。
- 在隔离环境从备份实际恢复，校验租户隔离和审计链。
- 验证 admin/用户撤权后的 token/session 失效、密钥轮换、provider 熔断与配额耗尽降级。

**Go 条件**：

- 未解决 P0/P1 安全问题为 0。
- production 主链无 mock。
- 浏览器与 release gate 全绿。
- 运行版本可证明。
- 数据可备份、迁移和回滚。

**灾备指标**：付费内测前先采用 `RPO ≤ 24h`、`RTO ≤ 4h` 的初始目标；若客户合同要求更严格，以客户协议为准。恢复演练必须记录数据截止点、恢复耗时、回滚期间新写入处理和租户隔离校验。

**验证命令包**：production build、TypeScript、相关前后端测试、全量后端、根/前端/后端 doctor、prod-release gate、true-chain、final harness、Playwright、migration upgrade/downgrade和恢复演练脚本。实际命令由执行 change 固定，不得只写范围。

**回滚验证**：回滚后重新执行 health/version、数据库 revision、租户隔离和最小合同读取；新写入使用预先声明的只读窗口、队列重放或人工对账策略。

### WF-10：五客户付费内测与结果飞轮

**目标**：用真实客户和付款证明产品价值。

**计划**：

- 首轮限定同一种合同类型、同一司法辖区、中文、约定页数上限和中低业务复杂度；不满足者进入候补，不临时扩功能。
- 每人带一份真实合同。
- 记录首份结果时间、采纳内容、专业人员纠正、再次使用和付费意愿。
- 建议 3 个月 POC，1.5 万至 3 万元，明确人数/合同量、隐私、删除、人工签字和服务边界。

**商业退出条件**：

- 至少 5 个真实客户使用。
- 至少 3 个愿意再次使用。
- 至少 1 个明确询价。
- 至少 1 笔真实付费 POC。
- 真实失败样本进入 Golden Cases。

**扩部门解锁条件**：只有满足上述条件，且客户明确提出第二高频需求，才决定扩户部、兵部或工部。

**数据退出与实验终止**：客户可撤回、导出和删除数据；退出时撤销账号/token、按协议删除在线数据并安排备份到期删除。若 5 位客户中少于 2 位愿意再次使用且无人询价，停止扩功能，回到问题访谈和切片选择。

**回滚**：关闭新客户准入但保留现有客户只读导出、删除和支持能力；商业实验终止不影响安全与数据生命周期义务。

## 7. 用户故事包

### US-01：老板快速获得合同判决

作为企业老板，我希望上传合同后快速看到是否可签、最高风险和必须修改项，以便在不阅读长篇 AI 分析的情况下作出决定。

验收：首屏显示一句话结论、前三风险、原文证据和下一步。

### US-02：合同负责人追溯风险依据

作为合同负责人，我希望每个高风险结论都能定位到原条款，以便验证判断并与对方谈判。

验收：每个 high/critical 风险都有原文引用；无法定位则不能输出确定性红灯。

### US-03：老板保留最终裁决权

作为老板，我希望采纳、打回或追问 AI 建议，而不是让 AI 自动签约或作出不可逆承诺。

验收：所有高风险结果进入人工裁决状态；未经签字不能进入 execution allowed。

### US-04：企业管理员保证数据隔离

作为企业管理员，我希望本企业数据与其他企业完全隔离，并能审计本企业的历史孤儿数据。

验收：双租户测试无泄漏；admin 例外显式、可审计、不跨租户。

### US-05：运营人员定位失败

作为运营人员，我希望通过 trace ID 判断任务失败在哪一层，以便快速恢复客户服务。

验收：5 分钟内定位到代理、鉴权、模型、搜索、数据库或前端展示中的具体阶段。

## 11. 反模式清单

- 健康检查绿就宣称业务跑通。
- 用直连 8081 的结果证明 3050 用户体验。
- 用 mock 或 fallback 证明 LIVE 质量。
- 只修一个端点，遗漏同一资源的其他读写路径。
- 为了按期上线降低租户隔离或人工签字门。
- 给模型回答做主观打分，却不记录真实误报、漏报和结果。
- 同时扩多个垂直，导致没有一个场景达到付费标准。
- 用新抽象掩盖现有死路由和双轨裁决。
- 在同一提交中混入无关清理或用户未授权的文件。
- 把历史调查假设写成永久事实，不标记 superseded。
- 看到局部 bug 就提出重写模块。
- 为了统一代码风格扩大 diff。
- 在现有 rewrite 可修时先引入新的反向代理组件。
- 为首发合同切片另建与刑部并行的新产品入口。

### 11.1 延后到上线后的事项

以下事项只有在不影响安全、数据正确性和首发主链时才能延期，并写入 backlog：

- 低风险一致性重构。
- 未被首发链使用的部门接线。
- 礼部二级能力。
- 页面视觉统一与非关键动效。
- provider/plugin 通用化。
- 不影响当前容量的性能优化。
- 历史 alias 的集中清理。

## 12. 计划变更协议

- 发现新 P0 安全问题：立即停止当前阶段，在依赖图中插入 P0，并更新 change 记录。
- 发现普通 bug：纳入当前阶段最小修复，不扩大相邻模块。
- 发现产品语义冲突：列出 2 至 3 个选项、影响和推荐，等待用户拍板。
- 假设被证伪：保留历史证据，标记 superseded，更新当前结论。
- 阶段需要拆分：每个子阶段必须有独立验证和退出条件。
- 阶段需要跳过：必须记录理由、风险、批准人和重新触发条件。
- 任何失败门禁不得通过文档措辞降级为“非阻塞”。

## 14. 最终上线判定

| 发布形态 | 判定标准 |
| --- | --- |
| 本地开发演示 | production build + 基础 API 可用 |
| 内部陪同演示 | 关键链路可用，已知限制明确披露 |
| 合成/脱敏数据封闭内测 | `WF-01` 至 `WF-07` 通过；不得输入真实客户合同 |
| 真实合同封闭内测 | `WF-01` 至 `WF-09` 全部通过，尤其是 `WF-08` 数据安全和 `WF-09` 恢复演练 |
| 收费 POC | `WF-00` 至 `WF-09` 全部退出条件满足，并具备客户协议、删除/退出和支持流程 |
| 公开生产 | 收费 POC 已验证价值，全部 P0/P1 清零，运营值班、事件响应、release/rollback/observability 和客户支持成熟 |

朝堂 OS 的最终成功标准不是“朝堂全部建完”，而是：

> 一个真实客户提交真实材料，通过真实 production 链路获得可信决策，作出裁决，留下结果，并愿意再次使用和付费。
