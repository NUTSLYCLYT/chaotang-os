# 下旨永远受理、如实回奏设计

## 目标

【下旨】代表用户正式发出旨意，而不是系统对材料完整性或执行成功率的预判。除空白旨意、未认证或幂等冲突等无法形成合法请求的技术条件外，系统必须受理每次下旨，创建持久化异步任务，并最终给出一条可理解的正式回奏。

## 核心契约

系统将“受理”和“办结”拆分：

- 受理成功：返回 `202`、旨意标识与任务标识；前端立即显示“已下旨，正在办理”。
- 办理完成：任务终态为 `SUCCEEDED`，回奏说明结论、建议和可用成果。
- 材料不足：任务仍属于已受理旨意，终态回奏为 `NEEDS_INPUT`，列出缺失材料和补充方式；不得伪造正常成果。
- 系统失败：任务终态为 `FAILED`，形成脱敏失败回奏并提供重试入口；不得永久停留在 `QUEUED` 或 `RUNNING`。

`NEEDS_INPUT` 从“拟旨阶段禁止下旨的状态”改为“下旨后正式回奏的一种结果”。拟旨阶段可以提示风险和缺失材料，但不得据此禁用【下旨】。

## 数据流与边界

前端提交当前旨意和幂等键，经 Next.js BFF 调用 FastAPI 受理端点。后端先持久化旨意、冻结路由快照和任务，再由 worker 执行部门办理、材料验证、模型调用与成果发布。worker 无法办理时必须将任务收敛到 `NEEDS_INPUT` 或 `FAILED`，并归档对应 `REPLY`。

ADR 0028 的丞相路由、六部/军机处办理、锦衣卫证据边界和史馆归档链保持不变。一道旨意最多归档一条最终 `REPLY`；owner 隔离、证据不可变和成果发布边界保持不变。

## 前端行为

- 非空且用户已认证时，【下旨】始终可点击。
- 拟旨的 `CLARIFYING`、`NEEDS_INPUT` 或风险提示不再构成禁用条件。
- 受理后立即进入任务视图并轮询持久化状态。
- 刷新后按 owner-scoped job ID 恢复轮询，不重复下旨。
- 三类最终回奏使用不同文案，但都结束等待状态。

## 错误处理

- 空白旨意、认证失败和无效幂等冲突在受理边界同步拒绝。
- 路由不明确、数据缺失或业务材料不足在执行阶段形成 `NEEDS_INPUT` 回奏。
- worker、模型、存储或未知异常形成 `FAILED` 回奏；错误内容必须脱敏。
- 任务租约、超时恢复和 readiness 必须防止任务无限等待。

## 测试与验收

测试覆盖：所有拟旨状态均可下旨；受理返回 `202`；重复提交保持幂等；完整材料产生成功回奏；缺失材料产生 `NEEDS_INPUT` 回奏；执行异常产生 `FAILED` 回奏；所有终态停止轮询并归档恰好一条 `REPLY`；worker 缺失时 readiness 失败。

完整前后端测试、lint、typecheck、build、四项 harness 和 `git diff --check` 首先各通过一次。最终固定验收流程对同一版本连续通过 10 轮；任一轮失败或代码、配置、验收流程变化后从第 1 轮重新计数。

## 非目标

本设计不保证每道旨意都能成功办结，不允许缺少证据时伪造成果，不改变部门职责、证据治理、owner 隔离，也不授权真实外网、生产写入、提交、推送或部署。
