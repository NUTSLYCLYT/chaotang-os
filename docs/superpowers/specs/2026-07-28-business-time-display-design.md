# 业务时间统一展示设计

## 目标

所有用户可见的业务时间统一显示为北京时间，格式固定为
`YYYY/MM/DD HH:mm:ss`。例如：

`2026-07-28T11:11:36.727253+00:00` → `2026/07/28 19:11:36`

用户界面不再直接显示 ISO8601 字符串、微秒或时区偏移。

## 范围

- 覆盖前端页面、列表、详情、状态卡片和其他面向用户的业务时间。
- API、数据库及内部领域模型继续使用现有 ISO8601 时间。
- 不修改时间排序、证据时效、存储结构或前后端契约。
- 日志、测试夹具和仅供机器处理的时间不因展示需求而改写。

## 设计

在前端公共代码中提供唯一的业务时间格式化函数。函数解析带时区的
ISO8601 输入，固定以 `Asia/Shanghai` 时区输出，并明确生成
`YYYY/MM/DD HH:mm:ss`，不依赖浏览器所在地区或操作系统时区。

所有用户可见的时间展示点改为调用该函数，不在页面内重复实现
`Date`、`toLocaleString` 或字符串截断逻辑。

## 异常处理

- 输入为空、类型错误或无法解析时，显示 `时间未知`。
- 不把无法解析的原始字符串回显给用户。
- 有效时间统一补齐两位月、日、时、分、秒。

## 测试

先为公共格式化函数编写失败测试，再实现功能。测试至少覆盖：

- UTC 时间转换为北京时间；
- 带正负偏移量的 ISO8601 时间；
- 转换后跨日、跨月或跨年的时间；
- 微秒被移除；
- 无效或缺失时间显示 `时间未知`；
- 输出不受运行测试的本地时区影响。

随后为受影响页面补充或更新展示断言，并扫描前端代码，确保用户可见位置
不再直接输出 ISO8601 时间或使用各自的时间格式化实现。

## 验收标准

1. `2026-07-28T11:11:36.727253+00:00` 在用户界面显示为
   `2026/07/28 19:11:36`。
2. 所有用户可见业务时间采用相同格式和北京时间语义。
3. API 响应和数据库时间表示保持不变。
4. 无效时间不暴露原始值，统一显示 `时间未知`。
5. 相关单元测试、前端检查和仓库 harness 验证通过。
