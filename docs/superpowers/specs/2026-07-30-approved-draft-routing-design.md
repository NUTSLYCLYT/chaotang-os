# 拟旨参与部门与实际执行路由一致性设计

## 问题

拟旨草案与正式下旨目前只通过 `version`、`fingerprint` 和自然语言 `decree_text`
建立授权关系。完整草案中的 `draft.departments` 没有进入一次性授权，也没有作为正式丞相图
的可信输入。正式下旨图会再次根据自然语言调用模型或确定性规则选择六部，因此用户确认的
参与部门可能被新增、删除、替换或重排。

现有拟旨部门结构还混淆了部级和司级层次。模型可以把 `户部会计司` 写入
`department`，而正式执行路由的 `departments` 只承认六部固定名录中的 `户部`。用户看到的
参与组织与执行结果因此无法逐项比较。

用户提供的财务报表场景必须稳定表示为：

```text
参与部门：户部
必选承办司：会计司
执行路径：丞相 → 户部 → 会计司
```

## 选定方案

采用“锁定参与部门，约束必选承办司”的授权快照：

- 拟旨确认后，参与部门的集合和顺序成为不可变授权内容。
- 正式下旨不得重新选择、增加、删除、替换或重排参与部门。
- 每个参与部门包含一个或多个必选承办司。
- 部内选司仍按 ADR 0028 由对应部执行，但选司结果必须包含全部必选承办司；可以按职责增加
  同一部内的其他真实司，并在办理结果中保留实际选择。
- 不允许跨部司、未知部、未知司或把“部+司”拼成一个部门名称。

该方案不改变 ADR 0028。单部门旨意仍由丞相交给对应六部；多部门旨意仍由军机处按顺序
串行会审；每个部仍先选司、形成司议，再形成部议。变化只在于：用户确认的拟旨路由成为
下旨时必须遵守的授权边界。

## 领域模型

`DepartmentRecommendation` 增加必填 `bureaus`：

```json
{
  "department": "户部",
  "bureaus": ["会计司"],
  "role": "主审",
  "reason": "负责财务数据提取、报表生成、校验及异常分析。",
  "responsibility": "提取总账数据，生成报表，执行校验，编写摘要，输出 Excel。",
  "expected_output": "2024年至2025年管理层综合财务报表 Excel 文件。"
}
```

约束如下：

- `department` 必须是 `MINISTRIES` 中的一个六部名称。
- `bureaus` 必须为非空、无重复、有顺序的字符串数组。
- 每个 `bureau` 必须属于 `bureau_profiles_for(department)`。
- `draft.departments` 的部门不得重复，顺序即正式执行顺序。
- 单部门草案只有一个部门；多部门草案至少两个部门。
- `DRAFT_READY` 必须通过全部部/司名录校验，否则模型获得一次结构纠正机会；连续无效则失败
  关闭。

前后端类型都显式使用 `bureaus: string[]`，页面不得再从 `department` 文本猜测司名。

## 拟旨生成与提示

拟旨系统提示和结构纠正规则明确区分：

- `department` 只能写六部名称，例如 `户部`。
- `bureaus` 只能写该部现有承办司，例如 `["会计司"]`。
- 财务报表、会计报表、科目、月结、收入、成本、费用等任务，户部的必选承办司应包含
  `会计司`。
- 只推荐完成目标所需的最小部门集合和最小必选司集合。

服务端在 Pydantic 响应模型中使用真实六部与司级名录校验，而不只依赖提示词。完整草案、
规范化自然语言正文以及规范化路由快照共同参与指纹计算。

规范化路由快照结构为：

```json
{
  "departments": [
    {
      "department": "户部",
      "required_bureaus": ["会计司"]
    }
  ]
}
```

路由快照由已验证的 `draft.departments` 在后端生成，不接受浏览器重新拼装。

## 一次性授权

拟旨 API 在 `DRAFT_READY` 时登记以下不可变内容：

- owner user id；
- draft version；
- fingerprint；
- `decree_text`；
- 规范化路由快照。

浏览器下旨请求继续只提交已存在的正文、版本和指纹，不增加可由客户端篡改的部门字段。
正式下旨 API 消费一次性授权后获得路由快照。以下任一不匹配均视为旧草案或无效授权：

- owner；
- version；
- fingerprint；
- decree text。

消费成功返回可信路由快照而不是单纯布尔值。旧格式的一次性授权不迁移；用户重新拟旨后
获得新格式授权。

如果授权消费成功但后续执行失败，该授权仍保持已消费状态，沿用现有一次性语义，不在本次
设计中增加自动重放。

## 正式执行数据流

正式下旨流程如下：

1. API 校验正文长度和版本、指纹字段。
2. API 一次性消费拟旨授权并取得可信路由快照。
3. API 构建正式丞相图，将 `decree_text` 和可信快照作为图输入。
4. 丞相路由节点验证快照仍符合当前六部与司级名录。
5. 路由节点直接采用快照中的部门集合和顺序，不再让模型重新决定部门：
   - 一个部门形成 `single` 路由；
   - 两个及以上部门形成 `multi` 路由。
6. 单部门直接进入对应部；多部门由军机处按快照顺序串行会审。
7. 每个部照常调用部内选司模型。解析选司结果后，系统检查所有
   `required_bureaus` 均已包含。
8. 若必选司缺失，部内选司获得一次固定、安全、不回显原值的结构纠正机会；仍缺失则在调用
   任何司级节点和生成业务成果前失败关闭。
9. 校验通过后按实际选司顺序执行；实际选择可以包含同一部内额外的真实司。
10. 回奏、处理路径、军机处案件和史馆归档使用实际执行结果，并保留已批准路由快照用于审计。

模型可以生成路由说明，但不得改变已批准的部门。如果保留丞相路由模型调用，它只能解释
已批准路由，不能输出新的部门集合；最小实现可以直接使用固定、可审计的批准说明，避免无
价值的模型调用。

## 失败关闭与副作用边界

以下情况必须失败关闭：

- 拟旨部门不是六部名称；
- 必选司为空、重复、未知或不属于对应部；
- 部门重复；
- 授权正文、版本或指纹不匹配；
- 授权快照在正式执行时无法通过当前名录校验；
- 部内选司连续两次没有包含全部必选司。

部门快照校验必须发生在以下动作之前：

- 通知或调用任何部级办理节点；
- 创建军机处案件；
- 创建会计报表 session 业务成果；
- 写入史馆回奏。

必选司校验发生在对应部完成选司之后、调用任何司级节点之前。此前只允许部内路由判断，不得
生成司级意见、Excel 报表或其他业务成果。

错误响应使用稳定、脱敏的既有错误映射，不回显模型原始输出或内部授权内容。前端保留已确认
草案，允许用户重新拟旨；不得静默改派。

## 前端展示

拟旨草案的每个参与组织分层展示：

- 参与部门：`户部`
- 必选承办司：`会计司`
- 角色：`主审`
- 参与原因
- 负责事项
- 预计产出

不得把 `户部会计司` 显示成一个“参与部门”。下旨后的处理路径继续显示实际路径，例如
`上书房 → 丞相（批准路由）→ 户部 → 户部·会计司 → 户部（部级补充）→ 丞相（最终汇总）`。

若户部补充选择其他司，实际路径可以显示这些司，但“必选承办司：会计司”必须出现在路径和
司级意见中。

## 测试

### 真实财务场景

使用用户原旨意构造回归：

```text
请户部会计司根据现有财务数据，生成2024年至2025年管理层综合财务报表，并交付可下载的
Excel 文件。报告需包括管理摘要、核心财务报表、科目趋势、异常分析、科目明细、校验结果和
数据来源；核对金额、同比变化及勾稽关系，列明数据缺口，不修改原始数据。
```

验收：

- 拟旨生成 `department == "户部"`、`bureaus == ["会计司"]`。
- 页面分别展示户部和会计司。
- 授权快照固定为户部/会计司。
- 即使正式路由模型建议吏部、工部或多个部门，实际参与部门仍只能是户部；推荐的最小实现不
  调用部门重选模型。
- 户部选司若首次遗漏会计司，纠正后必须包含会计司；连续遗漏则没有任何司级调用和 Excel
  产物。
- 成功路径包含 `户部·会计司`，会计司生成可下载 Excel，回奏部门为户部。

### 契约与安全

- `户部会计司` 作为 department 被拒绝。
- `department="户部", bureaus=["营缮司"]` 被拒绝。
- 空 `bureaus`、重复司、重复部门被拒绝。
- 修改完整草案、部门顺序或必选司会改变 fingerprint。
- 客户端只提交正文/版本/指纹，不能注入部门。
- 授权 owner/version/fingerprint/decree_text 任一不匹配均不能取得路由快照。
- 快照消费一次后不能重用。
- 单部门不创建军机处案件；多部门严格按批准顺序创建和办理。
- 失败路径不生成部门意见、司级意见、Excel 或史馆回奏。

### 回归验证

运行拟旨图、拟旨 API、授权、正式丞相图、下旨 API、会计报表跨层、前端拟旨展示和 BFF
测试；再运行后端与前端全量测试、类型检查、lint、build、四条 harness 与
`git diff --check`。

## 范围

允许修改：

- 拟旨领域模型、提示、图和测试；
- 一次性授权的可信路由快照；
- 正式丞相图的批准路由输入与部内必选司约束；
- 下旨 API 的授权快照传递；
- 前端拟旨类型与分层展示；
- 对应跨层测试与本次故障记录。

明确不修改：

- ADR 0028 内容及其完整性基线；
- 正式下旨正文的 2000 字限制；
- 六部与 39 个司的名录；
- 会计报表工作簿内容、Sheet 契约或下载机制；
- 锦衣卫、史馆或军机处的既有职责；
- 旧授权迁移与自动重放；
- 用户已有的其他未提交改动。
