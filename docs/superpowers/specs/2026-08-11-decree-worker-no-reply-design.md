# 下旨后永久无回奏修复设计

## 目标与范围

修复异步下旨接受路径与执行路径脱节的问题。标准后端进程必须默认启动一个作业 worker；worker 不可用时服务不得报告 ready；浏览器必须从持久化作业状态得到真实回奏或明确终态。设计不改变 ADR 0028、ADR 0039、owner 隔离、幂等归档或模型业务拓扑。

## 方案

采用应用内单 worker 的既有架构，不引入第二队列。`app.main` 在环境变量未设置时默认启用 worker，显式假值只供测试或维护关闭。`DecreeJobWorker.is_alive()` 提供无副作用存活探针，`/readyz` 在离线预检通过后仍必须确认 worker 存在且线程存活，否则返回稳定的 `503 worker_not_running`。

前端继续通过同源作业状态端点顺序轮询。`SUCCEEDED` 解析真实回奏，`FAILED`/`CANCELLED` 映射为稳定脱敏反馈，任何终态都清除 owner-scoped 活动作业并停止轮询。刷新恢复继续依赖 sessionStorage 中的 owner 隔离 job ID，不创建重复旨意。

## 错误处理与恢复

- worker 未启动或死亡：readiness 失败，阻止流量继续进入假健康实例。
- 进程重启：SQLite lease 与既有恢复规则重新领取未完成任务。
- 模型或供应商失败：作业进入明确 `FAILED`，页面停止等待；不伪造回奏。
- 归档阶段重启：以 job ID 作为 reply ID 保持一旨一条 `REPLY`。

## 测试设计

回归测试必须证明无环境开关时 lifespan 启停 worker、停止的 worker 令 readiness 返回 503、端到端异步作业能进入终态、前端轮询会在终态停止。旧基线代码对新增生命周期/readiness 测试应失败，当前实现应通过。最终固定验收组合连续执行 10 轮，期间任何实现或验收流程变化均重置计数。

## 非目标与风险

不调用真实模型，不承诺供应商一定产生成功回奏，只保证任务不会因无人消费永久等待，并且失败对用户明确可见。常驻旧后端必须重启才能加载修复。
