# DeepSeek v4 Flash 模型配置更新设计

## 背景

上书房拟旨请求已真实到达 FastAPI，但返回 `502 model_unavailable`。对当前 DeepSeek
账号执行不生成内容的模型列表查询后确认：仓库配置的 `deepseek-chat` 已不可用，账号当前
只提供 `deepseek-v4-flash` 与 `deepseek-v4-pro`。用户于 2026-08-04 明确选择
`deepseek-v4-flash`。

## 目标与范围

- 将 DeepSeek 默认模型更新为 `openai/deepseek-v4-flash`。
- 将声明的模型列表同步为当前账号可用的 v4 Flash 与 v4 Pro，避免默认值与允许列表失配。
- 不修改 ADR 0028 的下旨、六部、军机处、锦衣卫或史馆业务流。
- 不增加自动降级或运行时模型选择，避免不可预测的质量与成本变化。

## 实现设计

先增加配置契约测试，断言默认模型和允许列表使用获批的 v4 模型，并观察旧配置因仍为
`deepseek-chat` 而失败。随后只修改 `backend/config/providers.yaml` 使测试通过。

后端重启后继续沿用现有 `normalize_deepseek_model_name()`：配置中的 `openai/` 前缀会在
调用供应商前被移除，因此实际请求模型为 `deepseek-v4-flash`。无需改动客户端、拟旨图或
HTTP 契约。

充值解除供应商 402 后，真实拟旨仍在后端完成前被 BFF 取消。现有拟旨客户端默认超时为
30 秒，而后端结构化拟旨最多进行 3 次、每次最多 30 秒的模型尝试。用户于 2026-08-04
批准将拟旨专用默认超时提高为 120 秒，与正式下旨的现有服务端超时一致；自定义
`timeoutMs` 注入继续覆盖默认值，以保留确定性的短超时测试。该修订不改变模型重试、HTTP
契约、错误映射或 ADR 0028 业务流。

## 错误处理与回滚

现有 API 脱敏错误边界保持不变。若供应商再次移除配置模型，拟旨仍会安全失败为 502，
但验收流程必须先查询模型列表并核对默认模型可用性。回滚只需恢复配置并重启后端，但只有
供应商重新提供原模型时才有意义。

## 验收

1. 配置契约测试完成 RED → GREEN。
2. DeepSeek 模型列表包含规范化后的默认模型。
3. 拟旨相关后端测试与 harness 通过。
4. 重启后的后端健康检查为 `ok`，拟旨路由存在。
5. 使用现有已认证浏览器执行一次真实拟旨，响应不再是 502，并形成可展示的草案。
6. 同一最终版本按仓库规则连续完成 10 轮完整最终验收；任一轮失败或验收流程、代码、配置
   发生实质变化后从第 1 轮重新计数。

## 失败记忆

新增失败记录，明确离线测试和健康检查不能证明真实模型可用；模型供应商可用列表必须进入
诊断和验收证据。同时记录本次先将故障归因于旧进程、重启后才发现模型漂移的假绿过程。
