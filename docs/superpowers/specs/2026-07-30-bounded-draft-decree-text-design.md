# 拟旨执行正文长度闭环修复设计

## 问题

用户输入的原旨意只有 127 字。拟旨服务生成 `DRAFT_READY` 后，却把完整结构化 `draft`
以带缩进 JSON 序列化为 `decree_text`。浏览器随后把这份超过 2000 字的 JSON 作为
`decreeText` 提交，下旨端点按既有契约返回 422。

页面展示给用户确认的是自然语言 `expert_example`，实际提交的却是另一份 JSON，形成了
“所见非所执行”的契约错位。

## 选定方案

保留两个职责明确的字段：

- `draft` 保存完整结构化草案，用于页面展示参与部门和内部审计，不作为下旨正文。
- `expert_example` 是用户看到并确认的自然语言执行旨意；当状态为 `DRAFT_READY` 时，
  后端将其规范化后写入 `decree_text`。

`DRAFT_READY` 的执行正文必须满足既有下旨契约：去除首尾空白后长度为 1–2000 字。
不得静默截断。模型若不能生成合规正文，本次拟旨必须失败而不能发出可下旨版本。

## 后端数据流

拟旨图继续生成完整的结构化 `draft`。系统提示明确要求 `expert_example` 是可直接执行的
自然语言旨意且不超过 2000 字。响应模型把 `expert_example` 上限收紧为 2000 字。

拟旨图形成 `DRAFT_READY` 时：

1. 校验完整结构化草案。
2. 取规范化后的 `expert_example` 作为 `decree_text`。
3. 使用包含完整草案和执行正文的规范载荷计算指纹。
4. 拟旨 API 将相同的版本、指纹和 `decree_text` 登记到一次性授权表。

下旨 API 的 2000 字限制保持不变，且继续要求版本、指纹和执行正文完全匹配。

## 前端边界

前端严格校验拟旨成功响应。只有以下条件同时满足时才启用「下旨」：

- 状态为 `DRAFT_READY`；
- 完整 `draft` 存在；
- `decree_text` 是去空白后 1–2000 字的字符串。

若后端返回超长或空执行正文，拟旨响应按失败处理，不显示可点击的「下旨」。这只是纵深防御，
执行正文的主要正确性仍由拟旨后端保证。

## 错误处理

- 不提高下旨全局长度限制。
- 不使用用户原始输入替代已经确认的拟旨正文。
- 不截断结构化草案或自然语言执行正文。
- 不改变会计司路由、财务报表成果、史馆归档或 ADR 0028。
- 既有旧拟旨授权不迁移；用户重新拟旨即可取得新格式的执行正文和指纹。

## 测试

使用用户提供的财务报表场景构造回归：

- 原旨意为 127 字。
- 结构化 `draft` 可明显超过 2000 字。
- `expert_example` 是不超过 2000 字的自然语言执行正文。
- 拟旨响应的 `decree_text` 必须等于规范化后的 `expert_example`，不得以 `{` 开头，也不得是
  结构化草案 JSON。
- 超过 2000 字的 `expert_example` 不能形成 `DRAFT_READY`。
- 前端拒绝空白或超过 2000 字的 `decree_text`，不会发起下旨。
- 合规执行正文携带相同版本和指纹进入下旨授权校验。

完成后运行相关后端与前端测试、两端全量验证、构建、harness 检查和 `git diff --check`。

## 范围

允许修改拟旨响应模型、拟旨图和提示、对应后端测试、前端拟旨响应校验与测试，以及本次故障
记录。不得修改下旨端点的 2000 字限制、业务流基线、会计司报告契约或用户已有其他改动。
