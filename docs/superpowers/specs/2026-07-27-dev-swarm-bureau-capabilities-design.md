# dev 蜂群司级能力包集成设计

## 决策

采用“司级能力插件化”。旧 `dev` 蜂群只迁移专业业务逻辑，作为当前六部 Agent 可自动选择的司级能力；丞相、军机处、锦衣卫与史馆继续拥有唯一控制权和事实来源。

不采用两种替代方案：直接恢复 `dev` 的 `src/`、YAML 事件总线和 SQLAlchemy 运行栈会形成双控制面；仅以关键词在上层直接调用蜂群会绕过当前的丞相选部和部选司治理。

## 不变边界

`docs/decisions/0028-decree-evidence-flow-governance-baseline.md` 是不可变前提：下旨仍是唯一入口，丞相先选单部或多部，部门先选司形成司议再形成部议，多部仍由军机处串行会审，丞相回奏后史馆恰好归档一条 `REPLY`。锦衣卫仅由符合规则的司级节点发起调查，史馆仍是唯一归档真相源。

本阶段不改变现有同步 HTTP 契约；“已受理、后台完成、按 run_id 查询”作为独立的后续架构任务，不以本次能力包集成隐式引入。

## 架构

```mermaid
flowchart LR
  D["旨意"] --> C["丞相选部"]
  C --> M["部级 Agent 选司"]
  M --> R["本部司级能力注册表"]
  R --> E["能力执行器"]
  E --> O["司议：意见、产物、风险、证据引用"]
  O --> S["部级综合"]
  S --> J["军机处会审：仅多部"]
  J --> F["丞相回奏"]
  F --> A["史馆单条 REPLY"]
```

### 注册表和契约

每个能力包对应一个稳定的司级身份，而不是在司内再嵌套一个通用蜂群路由器。注册表应是代码中的不可变定义，至少声明：`id`、`department`、`bureau`、`intent_signals`、`input_contract`、`output_contract`、`risk_level`、`investigation_policy` 和执行器引用。

能力执行器使用统一接口：

```text
execute(BureauContext) -> BureauResult
```

输入仅限旨意、本部上下文、已采纳的证据快照和允许的上游产物。输出必须包含非空专业意见、结构化产物、风险项、明确采用的证据引用和来源标签。执行器不得选择其他部门、直接调用军机处、写入史馆、突破锦衣卫规则或声称现实动作已完成。

部门 Agent 先根据现有严格 JSON 契约选择本部司；只有被选择的司级能力执行。选择失败、跨部、未知、重复、空输出或能力执行失败均沿用现有脱敏错误边界失败关闭，绝不静默回退为伪造结果。

### 能力映射

| 所属部 | dev 能力下沉为司级能力 |
| --- | --- |
| 兵部 | 获客研判、项目/市场方案 |
| 户部 | 财务测算、成本报价 |
| 刑部 | 合同合规、风险审查 |
| 工部 | 产品规划、供应链寻源、PACK 研发、硬件设计、工艺制造、阶段评审、交付/售后诊断 |
| 礼部 | 品牌策略、对外内容、社媒运营 |
| 吏部 | 人才画像、筛选、面试 |
| 工具/参谋 | SDLC、代码审查、趋势推演；仅由所属部在匹配意图下选择 |

不迁入的旧模块：`court`、`swarm_orchestrator`、旧 `swarm_runs` API 与持久化、旧锦衣卫、`shiguan_archive`、旧 IMA 数据层。必要的整理或摘要逻辑可作为当前史馆内部能力，但不建立第二知识库。

## 安全与失败语义

- 合同、报价、付款、签约、对外发布、生产部署等能力只能给出建议、草案、风险和待确认项。
- 只有当前允许的司级节点可按现有规则请求锦衣卫调查；能力包不得扩展数据源、网络或凭据边界。
- 只有明确采纳的证据快照可进入最终 `REPLY`；能力包输出不是事实本身。
- 一个司失败立即使当前部门办理失败，不运行后续司、不产生半成品回奏。

## 测试策略

先为每个能力包写失败测试，再实现最小执行器。测试覆盖：注册表的部门唯一性和稳定 ID；本部选择、跨部/未知/重复拒绝；每个执行器的输入输出契约与失败关闭；单部和多部会审回归；锦衣卫调查门控；史馆只产生一条 `REPLY`；以及未选中能力包的现有旨意输出兼容。

全部测试使用注入的离线模型或确定性执行器，不访问真实模型、网络、凭据或运行态数据库。

## 分期

1. 建立注册表、统一能力契约和一条端到端测试样例。
2. 按部门顺序迁移能力：户部/刑部/工部/礼部/兵部/吏部。
3. 接入工具与参谋能力，并在每批后运行全量回归。

异步持久化办件调度、自动重启恢复和查询 API 留待独立设计与用户的基线变更授权。
