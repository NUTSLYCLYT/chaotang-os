# 上书房下旨 BFF 故障边界设计

## 目标

用户在 `/study` 的快捷栏点击“下旨”后，浏览器必须获得一个脱敏且可解析的 JSON 响应；Route Handler 内部依赖的意外拒绝不得导致浏览器 `fetch` 直接失败并被误报为“无法连接朝堂后端”。

## 已确认事实

- 已在浏览器中完成登录、填写快捷栏编辑器并实际点击“下旨”。
- 页面在约十秒内显示“无法连接朝堂后端”。
- 空旨意经 BFF 可获得 422，说明同源路由和基础后端连通性存在。
- `createPostHandler()` 对 `submitDecree()` 的正常返回值会映射为稳定 JSON，但没有捕获该依赖本身的意外 reject。

## 方案

在 `frontend/src/app/api/decrees/chancellor/route.ts` 的已验证请求体之后，将 `submitDecree()` 调用及其结果转换置于单一 `try/catch` 故障边界内。若依赖抛出，返回既有 `unknown` 类别、503 状态和既有脱敏文案；不暴露异常文本、后端地址、会话或密钥。

不改变：浏览器仅调用同源 BFF、BFF 转发会话、FastAPI 路径、下旨审批流、成功响应契约、模型调用次数或超时策略。

## 测试与验收

1. 在 `route.test.ts` 先添加一项：注入的 `submitDecree` 抛出时，handler 返回 503 JSON，`reason` 为 `unknown`，响应中不包含内部异常文本。
2. 运行该单测，确认在实现前失败。
3. 仅实现上述故障边界，运行单测确认通过。
4. 运行前端 lint、typecheck、相关测试与 harness。
5. 重新用浏览器点击“下旨”。如果真实后端仍失败，页面必须显示具体的既有类别（配置、模型、超时或未知），而不能因 BFF 未捕获异常变成传输失败。

## 风险

该改动不会使外部模型恢复可用；它保证用户和后续诊断能够收到可靠的 BFF 响应。实际模型调用继续只在用户明确点击下旨时发生。
