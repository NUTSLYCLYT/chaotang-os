# 确定性丞相拟旨降级设计

## 背景

当前拟旨图要求模型一次返回完整 `ChancellorDraftResponse`。该对象同时包含自然语言、生命周期状态、六部/司级路由和十余个数组字段。真实模型即使能够理解用户意图，也会因长响应、字段遗漏、非法司级组合或读取超时导致网页 `502`；SDK 的阶段超时也不能保证严格的请求墙钟上限。

用户已确认：不改前端，不改 ADR 0028；模型负责意图理解与文案，后端负责确定性组装和校验完整拟旨。当模型不可用但用户输入足够明确时，允许后端生成一份供用户审核的确定性草案；信息不足时返回 `NEEDS_INPUT`，不得自动补业务决定。

## 方案比较

1. **继续扩大重试和提示词**：改动小，但已经证明无法消除长响应和供应商波动，也会放大延迟与成本，不采用。
2. **模型返回小型提案，后端确定性组装；超时后按明确输入降级**：保留模型价值，同时把授权路由、Schema 和生命周期交回代码控制，采用。
3. **完全取消拟旨模型调用**：最稳定，但会失去丞相理解、改写和专家文案能力，不采用。

## 架构

新增独立的拟旨组装边界，拆分三个职责：

- `DraftProposal`：模型只可提议 `understanding`、`expert_example`、`recommendation_reason`、`assumptions`、`revision_prompt` 和可选的合法路由候选，不再生成完整 `DraftEdict`。
- `DraftIntent`：从当前用户消息中确定性提取明确出现的六部、司名、权限限制和交付要求。明确文本事实优先于模型候选；会计报表继续强制使用户部会计司。
- `assemble_chancellor_draft`：依据注册表、原始用户文本和已验证提案构造完整 `ChancellorDraftResponse`，生成版本、指纹、不可变路由快照和所有必需数组字段。

现有 `/api/v1/chancellor-drafts`、前端响应结构、一次性拟旨授权和正式下旨 Graph 均保持不变。

## 数据流

1. API 将当前用户消息和版本交给同一个丞相 `draft_decree` Runtime Skill。
2. 拟旨图先解析确定性意图，并判断输入是否足以形成可审核草案。
3. 调用模型获取小型提案；返回值必须通过严格的小型 Schema 校验，不接受自由字典。
4. 模型成功时，组装器采用其自然语言提案，但路由和权限只能来自用户原文、固定业务规则及六部/39司注册表。
5. 模型超时、供应商异常或提案非法时：
   - 若确定性意图足够明确，组装器使用用户原文和固定模板生成 `DRAFT_READY` 草案，并在 `assumptions`/`recommendation_reason` 中明确标识“确定性拟旨，待用户确认”；
   - 若目标、合法路由或权限边界不足，返回 `NEEDS_INPUT`，`draft` 与 `decree_text` 为空。
6. 用户仍必须在网页审核草案并点击“下旨”；降级绝不触发正式执行、MCP、证据调查或史馆写入。

## 确定性规则

- 用户明确写出的合法部/司必须保留，非法或跨部司组合失败关闭。
- 用户只明确“工部技术评审/质量审核”时，可依据固定职责注册表匹配工部技术司与质量司；匹配必须可由用户原文中的责任关键词解释。
- 会计报表意图继续固定为户部会计司，不接受模型改路由。
- 未明确排除项、输入材料或材料缺口时使用空数组，不发明事实。
- `objective` 与 `expert_example` 以用户原文为事实源；模板只做结构化整理，不宣称已执行或已有证据。
- `permissions_and_limits` 必须保留用户明确写出的“不修改代码”“不调用外网或 MCP”等限制。
- 降级草案必须明确是拟旨建议而非模型结论；正式执行仍遵循 ADR 0028。

## 错误与超时

- 模型调用继续禁用 SDK 隐式重试；结构化提案只允许受控、有限的修复尝试。
- 模型异常不得泄露提示词、原始输出、密钥或第三方异常文本。
- 模型失败本身不等于业务失败；只有确定性意图不足或违反路由/权限约束时才返回 `NEEDS_INPUT` 或失败关闭。
- 不在请求线程中无限等待模型。实现必须具有可测试的总调用预算；超出预算即进入上述确定性分支。

## 测试与验收

- 单元测试先覆盖：模型成功组装、模型超时降级、非法模型路由被忽略、明确非法用户路由失败、信息不足返回 `NEEDS_INPUT`、会计路由固定、权限限制保留、指纹稳定。
- API/Runtime 回归必须证明 HTTP 契约、Skill 选择、一次性授权和审计语义不变。
- 完整 Ruff、pytest、四条 harness 和 `git diff --check` 必须通过。
- 同一最终代码、配置和验收流程必须通过真实网页连续至少 10 轮；任一轮失败或代码、配置、流程发生实质变化后从第 1 轮重新计数。
- 每轮必须记录拟旨状态、正式下旨 HTTP 结果、页面正式回奏以及当前用户史馆恰好新增一份 `REPLY`。

## 范围

允许修改拟旨 Graph、拟旨模型/组装模块、DeepSeek 调用边界、对应测试、产品任务、计划和失败记录。禁止修改前端、ADR 0028、MCP 配置、正式执行治理基线和无关业务模块。
