# 丞相案例驱动拟旨流程设计

## 产品目标

把用户的一句话升维成易懂、可修改、可审计的拟旨草案；只有用户看到完整 `DRAFT_READY` 草案并点击【下旨】后，现有执行流程才生效。

## 2026-07-29 升级：保守补全、直接成旨

### 核心体验

用户点击【拟旨】后，丞相不再默认停留在“给案例、等待确认”的中间态，而是：

1. 揣摩用户真正想解决的问题；
2. 给出一份贴合当前意图、普通用户容易看懂的大神级拟旨草案；
3. 主动补齐下旨所需的目标、范围、排除项、输入、输出、部门、流程、完成标准、风险控制、权限与禁止事项；
4. 将非用户原话的补充明确标为“丞相建议”或“暂定边界”；
5. 若补充内容采用保守默认值即可安全执行，直接返回 `DRAFT_READY`；
6. 用户看到完整草案后，可以直接点击【下旨】。

大神级草案不是把用户的话写得更正式，而是替用户补上顶级专业人士会提前考虑的判断顺序、取舍、失败条件、风险边界和验收方式。

### 自动补全规则

丞相可以主动补全：

- 推荐的最小任务范围及明确排除项；
- 完成任务必需但尚未给出的输入材料；
- 最小参与部门集合及主审、协审、监察角色；
- 专业执行步骤、最终交付物与完成标准；
- 风险控制、停止条件、判断失效条件；
- 不自动执行、不代替用户决策、不扩大授权等权限边界。

自动补全必须满足：

- 不改变用户已经明确表达的目标；
- 不把推测写成用户确认事实；
- 不扩大资金、法律、账号、外部通信或现实执行权限；
- 优先使用可撤销、低风险、最小范围的默认值；
- 所有补充在下旨前完整可见并可被用户直接修改；
- 用户修改后生成新版本，旧版本立即失效。

### 何时可以直接 `DRAFT_READY`

同时满足以下条件时，首轮拟旨可以直接成为 `DRAFT_READY`：

- 用户的核心目标可以合理识别；
- 目标、范围、输入、输出、部门和完成标准已由用户信息与保守补全共同形成；
- `material_gaps` 为空；
- 没有权限、冲突或安全阻断；
- 所有丞相补充均明确可见；
- 草案不包含需要用户额外授权的高风险现实动作。

用户点击【下旨】代表接受当前可见草案及其中明确标出的暂定边界，但不构成草案之外的授权。

### 必须继续澄清或阻断

以下内容不得靠丞相猜测并直接进入 `DRAFT_READY`：

- 会改变任务本质或目标对象的选择；
- 资金金额、最大损失、法律承诺等不可安全默认的重大边界；
- 账号访问、付款、签署、发布、交易或对外联络权限；
- 缺少后无法完成核心任务的必要材料；
- 相互冲突的用户要求；
- 违法、危险或超出系统权限的要求。

分别使用：

- `CLARIFYING`：存在一个会实质改变任务方向的关键问题；
- `NEEDS_INPUT`：缺少不可替代的必要材料；
- `PARTIAL`：可以交付明确的部分结果，但无法达到完整标准；
- `ISSUE_BLOCKED`：存在权限、冲突或安全阻断。

不得为了多问一句而维持 `CLARIFYING`，也不得为了启用【下旨】而掩盖真实缺口。

### 草案展示与操作

卷轴按以下顺序展示：

1. 臣对用户意图的理解；
2. 大神级拟旨草案；
3. 丞相为什么这样补全；
4. 用户已确认内容；
5. 丞相建议与暂定边界；
6. 完整的结构化拟旨；
7. 当前状态与【下旨】按钮。

`DRAFT_READY` 时，卷轴底部【下旨】可用；其他状态下禁用并说明唯一的真实阻断原因。用户不需要再点击“确认拟旨”“继续”或填写完整问卷。

### 示例

用户输入：

> 我要炒股赚钱。

丞相应直接形成一份可读草案，例如：

> 使用一笔不影响日常生活的闲置资金研究并参与 A 股市场，在不借贷、不使用高杠杆、不自动交易、不承诺收益的边界内，先判断当前是否存在值得参与的机会。若机会不明确，应明确建议等待，不为完成任务强行推荐股票。
>
> 若适合参与，从行业前景、公司经营、估值、资金与市场情绪等方面筛选少量候选，说明每个候选值得研究的原因、主要风险、买入条件和判断失效条件。操作上采用分批验证，预先约定单只股票的最大投入、可承受损失、减仓和退出条件。
>
> 最终交付一份容易执行的研究与操作方案，包括现在是否适合买、重点研究方向、选择方法、分批参与方式、停止条件和主要亏损风险。系统只提供研究与建议，不替用户交易。

其中“闲置资金、不借贷、不使用高杠杆、不自动交易”应标为丞相提供的保守边界。若不存在必须由用户决定的金额、市场或权限阻断项，可以同时补齐完整结构化草案并返回 `DRAFT_READY`；用户不同意时直接修改上述边界并重新拟旨。

## 方案选择

采用独立拟旨 Agent。它与咨询丞相、正式下旨丞相平行：

- 咨询：非业务讨论，不产生草案。
- 拟旨：业务准备，加载 `chancellor-draft-edict`，无执行副作用。
- 下旨：唯一业务执行入口，保持 ADR 0028 拓扑。

不把 Skill 拼入正式下旨图，因为那时用户已经授权执行；不复用咨询端点，因为 ADR 0030 禁止咨询成为业务入口。

## 数据流

```text
用户自然语言
→ POST /api/drafts/chancellor
→ POST /api/v1/chancellor-drafts
→ Skill 加载与拟旨 Agent
→ CLARIFYING / NEEDS_INPUT / PARTIAL / ISSUE_BLOCKED / DRAFT_READY
→ 浏览器按 userId 保存当前草案版本
→ 用户点击【下旨】
→ 校验 DRAFT_READY + 当前版本指纹
→ 现有下旨 BFF/API
→ 六部/军机处/回奏
```

## 输出契约

拟旨响应包含：

- `status`
- `version`
- `fingerprint`
- `understanding`
- `expert_example`
- `recommendation_reason`
- `assumptions`
- `revision_prompt`
- `draft`（只有已形成草案时存在）

`draft` 包含目标、范围、不包含、输入材料、重点问题、参与部门及角色、执行流程、最终交付物、完成标准、材料缺口、权限限制和当前状态。

## Skill 加载

后端只允许加载仓库根目录下固定路径 `.agents/skills/chancellor-draft-edict/SKILL.md`。加载器解析 UTF-8、限制大小、验证 frontmatter 名称和核心锚点；失败时拒绝构建拟旨图。Skill 内容只进入拟旨系统提示，不进入正式下旨、咨询、六部或归档。

## 状态与版本

- 初始请求优先返回大神级完整草案；能够以保守默认值安全补齐时直接为 `DRAFT_READY`。
- 只有关键方向无法合理判断、必要材料缺失、只能部分完成或存在权限与安全阻断时，才分别使用 `CLARIFYING`、`NEEDS_INPUT`、`PARTIAL` 或 `ISSUE_BLOCKED`。
- 只有无材料缺口、无安全阻断且字段完整的草案能成为 `DRAFT_READY`。
- 指纹由规范化草案内容和版本确定；任一修改生成新版本与新指纹，旧指纹失效。
- 首版只在当前浏览器按认证 `user.id` 隔离保存，不写史馆或后端业务数据库。

## 安全边界

- 拟旨请求不得导入或调用下旨图、六部、军机处、锦衣卫、史馆。
- 模型只生成候选案例和草案，不能创建 Mission 或声称已经执行。
- BFF 不接受 owner ID，只从 HttpOnly session 转发 Bearer。
- 下旨前页面必须展示完整草案；状态或指纹不匹配时失败关闭。
- 错误只暴露稳定分类，不返回 Skill 路径、提示词、模型正文或异常原文。

## 验收重点

用“我要炒股赚钱”验证首轮不是问卷或仅提供案例，而是自动补齐条件与边界的完整草案，并在不存在真实阻断项时成为 `DRAFT_READY`；用用户修改暂定边界验证生成新版本且旧版本失效；用必要材料缺失、高风险授权、旧指纹、Skill 缺失和模型 schema 漂移验证失败关闭。

## 核心按钮位置

- 御前输入栏只显示一个主按钮【拟旨】，原【下旨】位置由【拟旨】替代。
- 拟旨结果在中央卷轴完整展示，不在输入栏旁提供【下旨】。
- 卷轴按“当前理解 → 专业案例 → 推荐理由 → 暂定假设 → 完整草案”顺序展示。
- 卷轴底部是唯一【下旨】按钮。非 `DRAFT_READY`、草案缺失或正在办理时必须禁用，并在按钮附近说明原因。
- 用户修改输入后旧卷轴草案立即失效，卷轴底部不得继续使用旧版本下旨。
- 不引入“确认拟旨”“继续”或“完成”等同义按钮。
