# 中央锦衣卫证据服务设计

## Status

Product direction approved — 2026-07-20

用户选择并批准“中央锦衣卫证据服务”，并要求使用自动交付实现。本文是实现前的书面规格；
按仓库规则，规格确认不自动授权提交、推送、部署、付费或任何外部现实动作。

## Product Definition

### 问题

当前六部、各司、军机处和丞相在缺少实时数据时，只能在意见中描述“数据不足”，或依赖模型
已有知识继续推演。这样会导致不同 Agent 重复查找、来源标准不一致、无法追溯事实依据，甚至
把搜索摘要或模型猜测当成事实。

### 目标

建立统一的锦衣卫数据补给能力：只有司级 Agent 在形成专业意见所必需的数据缺失、过期或
互相冲突时，提交结构化缺数单；锦衣卫按“已有史馆 → 公开 API → 公开互联网”的顺序调查，
交付可追溯证据包；原司级 Agent 基于冻结证据包继续判断。部级综合、军机处和丞相不发起
锦衣卫调查，也不因缺数而重跑。

锦衣卫只负责调查和证据质量，不替六部、军机处或丞相作业务结论。没有足够证据时必须返回
部分完成或无法确认，禁止补写、猜测或隐藏冲突。

### 首版范围

- 查询已有史馆的奏折、回奏、复盘、经验与证据。
- 查询注册表中允许的无登录公开 API。
- 通过可替换的公开搜索提供器发现公开网页，再安全抓取可读正文。
- 生成、持久化和展示调查任务及证据包。
- 用统一的两阶段协议让司级 Agent 自动请求数据并恢复执行。
- 把最终被业务采用的证据引用附着到新回奏，不新增史馆档案类型。

### 非目标

- 不登录私有系统，不读取企业内部文档、邮箱、网盘或账号数据。
- 不绕过付费墙、验证码、robots/站点条款或访问控制。
- 不联系外部人员、不发消息、不购买数据、不提交申请、不产生现实承诺。
- 不做持续监控、订阅、告警、舆情大盘或主动推送。
- 不允许模型任意构造 URL 并访问内网，不执行网页中的指令。

## Product Principles

1. **缺数才调查**：已有证据足够且仍在时效期内时不得重复联网。
2. **证据与判断分离**：锦衣卫报告事实和证据质量，业务 Agent 负责业务结论。
3. **史馆优先**：先复用内部历史，再用外部来源补缺；历史结论不能伪装成当前实时事实。
4. **逐条可追溯**：证据包中的每个已解决字段都能回到来源、发布时间和抓取时间。
5. **失败显式**：超时、限流、解析失败、来源冲突和证据不足都有稳定状态，不降级成“已解决”。
6. **一次冻结**：同一业务节点只消费一份不可变证据包，避免不同 Agent 在同一决策中看到
   不同版本的数据。

## User Experience

### 自动触发

司级 Agent 采用两阶段响应契约；其他业务 Agent 保持现有响应契约：

- `READY`：现有数据足够，直接返回业务产物。
- `NEEDS_DATA`：不返回伪结论，只返回一至五项结构化 `DataGapRequest`。

协调器收到 `NEEDS_DATA` 后调用锦衣卫，随后只重跑受影响的司级 Agent 一次，并注入冻结的
`EvidencePack`。第二次仍不足时，司级 Agent 必须返回带限制说明的结果，不得形成无限调查循环。

### 锦衣卫页面

新增只读 `/jinyiwei` 调查台，首版包含：

- 总调查数、解决率、部分完成率、来源失败率和缓存命中率。
- 调查列表：请求 Agent、问题摘要、状态、创建时间、耗时、证据覆盖率。
- 调查详情：缺数项、采用证据、冲突证据、来源等级、时间信息、仍未解决项。
- 与回奏的关联：显示哪些证据最终被哪条回奏采用。

首版不提供“代用户执行调查动作”、任意 URL 输入、编辑证据或删除记录按钮。

## Contracts

### DataGapRequest

每张缺数单至少包含：

- `request_id`：服务端生成的唯一 ID。
- `requesting_agent`：稳定的 Agent 身份。
- `question`：要解决的问题，不得包含指令注入式网页操作要求。
- `required_facts`：一至五个事实槽位；每项包含稳定键、描述、期望单位或形状。
- `decision_context`：这些事实将支持什么业务判断。
- `freshness`：允许的数据最大年龄或明确的截至时间。
- `source_scope`：固定为 `SHIGUAN`、`PUBLIC_API`、`PUBLIC_WEB` 的子集。
- `existing_evidence_ids`：调用方已持有的证据引用，避免重复调查。
- `timeout_seconds`：由系统设置的总时间预算，调用方不得无限放大。

同一 Agent、同一事实槽位、同一时效要求的请求生成稳定指纹；指纹命中有效缓存时直接复用，
但仍生成可审计的调用记录。

### EvidenceItem

每条证据至少包含：

- `fact_key`、规范化 `value`、可选 `unit`。
- `as_of`：事实对应的时间；`retrieved_at`：系统抓取时间。
- `source_url`、`publisher`、`source_type`。
- `quality`：`PRIMARY`、`AUTHORITATIVE`、`SECONDARY`、`UNVERIFIED`。
- `stance`：`SUPPORTS` 或 `CONTRADICTS`。
- 最小必要摘录与内容摘要哈希；不得整页复制受版权保护内容。
- `confidence`：基于来源与交叉核验规则计算，不由模型自由填写。

`quality` 描述证据权威性，与史馆既有 `LIVE/MIXED/FALLBACK` 来源形态是不同维度，不混用。

### EvidencePack

- `status`：`RESOLVED`、`PARTIAL`、`BLOCKED`、`UNAVAILABLE`。
- 原始请求和规范化调查计划。
- 按 `fact_key` 分组的证据项。
- `resolved_facts`、`unresolved_facts`、`conflicts`。
- 使用过和失败过的来源列表、调查时间与缓存信息。
- 明确的 `do_not_infer`，告诉下游哪些结论不能从现有证据推出。

事实槽位达到以下任一条件才可标记已解决：一个官方/原始来源直接支持，或至少两个相互独立
的权威来源一致支持。存在未消解冲突时不得标记 `RESOLVED`。

## Architecture

### 组件边界

1. **Data Gap Protocol**：仅供司级 Agent 使用的两阶段输出模型与最大一次恢复规则。
2. **Investigation Coordinator**：校验、去重、缓存、预算、来源编排和状态机；不抓网页。
3. **Shiguan Source**：复用史馆召回，但保留历史时间语义，不把旧回奏当实时数据。
4. **Public API Registry**：只调用代码和配置中显式登记的公开 HTTPS API；每个连接器负责
   查询参数、响应校验、单位与时间规范化。
5. **Public Web Source**：通过 `SearchProvider` 接口发现 URL，再由受限 Fetcher 抓取；搜索
   实现可替换，工程阶段必须用最小原型验证一个无需私有登录的默认提供器。
6. **Evidence Normalizer and Verifier**：去重、来源分级、时间检查、冲突检测和覆盖率计算。
7. **Investigation Store**：独立 SQLite 文件保存调查、证据和缓存，不改变史馆双文种 schema。
8. **Bureau Resume Adapter**：把冻结证据包注入原司级 Agent，且只重跑该司级节点一次。
9. **Jinyiwei API/BFF/UI**：只读展示调查和证据，不向浏览器暴露搜索配置或后端地址。

### 数据流

`Bureau Agent → NEEDS_DATA → Coordinator → Shiguan → Public APIs → Public Web → Verifier → EvidencePack
→ Resume same Bureau Agent → bureau opinion → adopted evidence references → REPLY`

来源按优先级尝试，但不是命中第一条就停止。史馆能直接满足时效和覆盖要求时不联网；否则只
调查仍缺失的事实槽位。外部调查按事实槽位并发受控执行，总并发、每域并发、响应体大小、重定向
次数和总时限均有硬上限。

## Public Network Safety

- 只允许 `https`，公开 API 的例外必须在代码中显式登记。
- 拒绝 localhost、私网、链路本地、云元数据地址、非 HTTP(S) 协议和 DNS 重绑定结果。
- 每次重定向重新执行地址校验；限制重定向次数、响应大小、MIME 类型和读取时间。
- 不发送 Cookie、Authorization、用户私密内容或完整业务提示词。
- 网页正文视为不可信数据；其中的“忽略规则”“调用工具”“发送信息”等文字不得成为指令。
- 搜索词只包含完成事实槽位所需的最少业务上下文，并在日志中脱敏。
- 尊重 robots、站点条款和版权；只保存最小摘录、URL、元数据与内容哈希。

## Failure Handling

- 史馆不可用：继续允许的外部来源，证据包标明内部来源不可用。
- 搜索提供器不可用：公开 API 和史馆仍可返回 `PARTIAL`，不得伪装完整。
- API 限流或超时：记录失败来源；在总预算内做有限重试，不无限退避。
- 页面不可解析：保留来源失败信息，不让模型根据标题补正文。
- 来源冲突：并列返回支持与反对证据，标记 `conflicts`，交业务 Agent 显式处理。
- 所有来源均失败：返回 `UNAVAILABLE`；原 Agent 输出缺口说明，不给无证据结论。

## Persistence and Retention

锦衣卫使用独立的本地 SQLite 数据库，至少包含调查、事实槽位、证据项、来源尝试和采用关系。
原始整页正文只在处理过程中短暂存在，不长期保存；数据库保存最小摘录和哈希。缓存 TTL 取事实
槽位的时效要求与连接器上限的较小值。

锦衣卫记录不是奏折或回奏，不写入史馆档案列表。业务流程形成回奏时，只把被采用证据的稳定
引用、来源 URL、时间和来源形态写入回奏证据；未采用的调查材料仍只留在锦衣卫调查记录中。

## First-Release Integration

首版只把两阶段协议接入现有丞相图中的司级意见节点，并采用同一共享适配器，禁止每个司
各写一套搜索逻辑。每个司级节点最多发起一次调查、最多五个事实槽位；同一丞相流程设置全局
调查次数和总时限上限。部级综合、军机处和丞相保持原契约，不调用锦衣卫。锦衣卫查数会增加
网络延迟，但不得增加 DeepSeek 调用次数超过“受影响司级节点重跑一次”的上限。最终回奏采用
司级 Agent 在恢复响应中明确选择的证据 ID 并集。

现有 HTTP 下旨成功响应继续保持业务字段兼容，不暴露内部调查对象；`processing_path` 增加实际
执行过的“锦衣卫（调查）”步骤。回奏的 `reply_process` 和证据引用必须反映真实调查行为。

## Metrics

- 缺数触发率、证据包解决率和部分完成率。
- 每个事实槽位的证据覆盖率与平均来源数。
- 史馆命中率、公开 API 命中率、网页调查命中率、缓存命中率。
- 调查 P50/P95 耗时、超时率、限流率和解析失败率。
- Agent 恢复后仍报告不足的比例。
- 无证据事实进入最终回奏的数量，目标必须为零。

## Testing and Acceptance

- 模型测试：缺数单、证据项、证据包严格字段、未知字段拒绝和状态一致性。
- 来源测试：使用本地 fixture/stub 覆盖史馆、公开 API、搜索、网页抓取、超时、限流、重定向、
  私网阻断、超大响应和提示注入文本；自动化测试不得依赖真实互联网。
- 编排测试：史馆足够时不联网；不足时只补缺口；同指纹复用；冲突不得 resolved；最多恢复一次。
- Agent 测试：`READY` 不调查，`NEEDS_DATA` 调查后只重跑原节点，二次不足明确降级。
- 归档测试：调查采用的证据进入单条 `REPLY`，未采用材料不污染史馆类型。
- API/BFF/UI 测试：列表和详情严格映射，后端异常脱敏，页面显示状态、来源和冲突。
- 至少完成一次经用户知情的无副作用 live smoke：查询稳定的公开 API 和公开网页，只读且不触发
  真实下旨；无法联网时必须记录为未运行，不能用 stub 冒充 live。
- 后端 lint/test、前端 lint/typecheck/test/build、harness、`git diff --check` 全部通过。

## Rollout

首版以 feature flag 默认关闭真实外部网络，但史馆来源和全部离线测试始终可用。完成公共来源
live smoke、SSRF 防护和预算验证后，在本地开发环境开启。任何公开部署、认证、多用户隔离、
付费搜索提供器或内部数据源都需要新的产品决定。
