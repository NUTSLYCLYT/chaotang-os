> 状态：用户已批准产出设计蓝图；本文是实施前的产品与架构规格，不代表代码已完成
> 日期：2026-07-18
> 目标：让用户用一句话下旨，得到一套可验证、可下载、可继续执行的完整成果，而不是一堆互相重复的 Agent 文本
> 适用主链：上书房 → 丞相 → 门下省 → 军机处 → 各部/专署/蜂群 → 御史 → 丞相回奏 → 皇上裁决 → 史馆

> 实施原则：先复用现有 canonical task、outbox、事件账本、正式奏折与史馆主链；首期不引入 LangGraph
> 文档关系：本文是 [`朝堂 OS 产品定型融合蓝图`](chaotang-os-product-definition-convergence-blueprint-2026-07-18.md) 的详细输入 A；不再单独承担产品定型口径。当前产品字段事实源始终是 `docs/product/PROJECT_PRODUCT.md`

## 1. 一句话结论

朝堂 OS 可以实现“去美国看世界杯决赛”与“一门生意要不要做”这类复杂任务，但当前版本只能证明已有可靠任务主链和部分部门能力，尚不能诚实宣称会自动交付完整、实时、可购买的旅行方案或全维度商业决策包。

目标产品不是“六个部门都说一遍”，而是：

```text
一句话目标
  → 只追问一个真正会改变方案的问题
  → 展示可修改的办事计划、预算和交付清单
  → 按能力动态组建任务班子
  → 并行采证、分析、交叉验证
  → 对冲突、过期数据和缺口显式封驳
  → 形成一个可裁决的结论
  → 交付报告、表格、清单、日历、证据包等附件
  → 用户批准后才执行购买、预订、发送或签约等副作用
  → 结果归档并在未来任务中复用
```

北极星体验是：**一旨一案、一案一包、一包可行动、每个结论可追溯。**

## 2. 用户真正购买的不是 Agent，而是结果

### 2.1 用户目标

用户不应该理解模型、prompt、部门关键词、蜂群数量或工作流框架。用户只需要：

1. 说清楚想得到什么；
2. 回答一个必要问题；
3. 审批计划和高风险动作；
4. 收到可直接使用的成果包；
5. 在事实变化时一键刷新关键部分。

### 2.2 产品承诺

| 承诺 | 用户能感知到的结果 | 系统保证 |
| --- | --- | --- |
| 听懂 | 丞相复述目标、约束和交付物 | 不把关键词命中当成完整理解 |
| 办成 | 给出下一步可执行成果 | 不以“生成了一段文字”冒充完成 |
| 可信 | 关键结论有来源、时间和置信度 | LIVE / MIXED / FALLBACK / NO_DATA 诚实标记 |
| 可控 | 计划可改、过程可停、高风险需批准 | 模型无权自行购买、付款、签约、发布 |
| 可复用 | 报告、表格、清单和历史偏好能继续使用 | 结果、反馈和真实 outcome 进入史馆 |

### 2.3 “上瘾”的正确定义

本产品追求“高信任复用”，不采用延长使用时长的暗黑模式：

- 第一次使用就节省数小时；
- 用户每次回来，系统记得合法授权的偏好和旧案；
- 过程透明，随时知道“谁在办、缺什么、何时完成”；
- 结果比用户预期多一步，例如自动附带预算表、备选方案和风险清单；
- 不制造焦虑、虚假红点、无限滚动或不必要的每日签到。

核心留存指标应是“30 天内再次委托高价值任务的用户比例”，不是“页面停留时间”。

## 3. 当前系统能做到什么

### 3.1 已具备

| 能力 | 当前证据 | 判断 |
| --- | --- | --- |
| 正式任务主链 | `DecisionTask → ChancellorRouteDecision → OutboxEvent → CourtReview → FinalMemorial → EmperorDecision → ShiguanArchive` | 已具备可靠骨架 |
| 事务后异步派单 | `backend/src/execution/decree_dispatcher.py` 与 outbox worker | 已具备 |
| 幂等、事件账本和状态投影 | `DecreeExecutionEvent`、`execution_state.py`、相关测试 | 已具备重要基础 |
| 军机处 canonical 读模型 | `frontend/src/features/command-center/junjichu/model/canonical-read-model.ts` | 已具备展示骨架 |
| 门下省路由前置审议 | `backend/src/menxia_veto.py` | 已有第一版，但硬门仍需收口 |
| 丞相结构化 LLM 推荐 seam | `backend/src/chancellor_llm_recommendation.py` | 已有组件与测试，尚未完整接入正式下旨主链 |
| 证据缺口、质量门、人工确认字段 | 路由、回奏和前端模型中已有相应字段 | 部分具备 |
| 下载 UI 与基础导出 | 前端奏折下载 dock；后端目前主要导出 JSON/TXT | 只有骨架，不是完整成果包 |
| 国力、翰林薄片 | P8/P9 已进入远端基线 | 已具备局部读模型 |

### 3.2 当前不能过度宣称

1. `infer_departments()` 在零命中时仍默认派给户部、工部；旅行等任务首先依赖门下省拦截，而不是已有旅行能力。
2. `unsupported_scope` 已有独立组件，但正式 `ChancellorRoutingService` 仍主要走确定性部门推断，不能证明所有超域任务都会被统一处理。
3. 当前提交基线会把门下省封驳写入风险与人工确认字段，但正式 confirm 路径仍继续创建 outbox 派单；主工作区存在尚未提交的阻断修复，不能按已上线能力宣传。
4. 门下省第三轮存在“保留理由但准奏”的兼容规则；对于“没有真实能力”这种硬缺口，不能 fail-open。
5. 当前导出端点主要提供运行 JSON、prompt 和文本输出，没有任务级 Artifact Manifest，也没有 PDF/DOCX/XLSX/ICS/ZIP 的统一成果包服务。
6. 旅行所需的实时库存、价格、签证、票务、地图、天气、保险和预订连接器没有形成可验收的完整能力集合。
7. “生意是否要做”所需的市场、财务、法务、竞品、渠道与真实内部数据连接尚未形成同一套证据契约。
8. 用户附件目前还不是完整的企业级隔离、扫描、解析和来源可信管线。
9. 部门蜂群存在绕过普通调用预算的路径；在做广域并行研究前必须统一任务级软/硬预算门。

所以答案是：**架构方向可实现，当前产品尚未完整实现。**

## 4. 最关键的天才设计：部门治理，能力办事

如果所有新任务都强行映射到六部，会反复出现世界杯误路由。新的设计把“治理角色”和“执行能力”分开：

```text
六部/专署 = 谁负责、谁复核、谁承担风险责任
临时专案行台/蜂群 = 具体用什么专业能力把事情办完
```

例如“去美国看世界杯决赛”不是简单归户部或工部，而是临时组建一个任务班子：

| 任务能力 | 治理归属 | 具体责任 |
| --- | --- | --- |
| 官方票务核验 | 锦衣卫采证、刑部反欺诈复核 | 只认可官方或授权渠道，标识诈骗风险 |
| 入境与证件 | 刑部治理、旅行合规专员执行 | 根据国籍/护照情况给出适用路径与缺口，不代替官方裁决 |
| 航班与酒店比较 | 工部治理、旅行搜索蜂群执行 | 组合可行行程，记录价格与库存时间戳 |
| 总预算与汇率敏感性 | 户部 | 基础/舒适/保险三档预算与超支预警 |
| 城市交通与比赛日动线 | 工部 | 机场—酒店—球场—返程的时空可行性 |
| 安全、保险、退改 | 刑部 + 御史 | 最坏情形、取消路径、不可退损失 |
| 用户体验与沟通 | 礼部 | 行前手册、当地礼仪、对外沟通模板 |
| 最新信息监测 | 锦衣卫 + 钦天监 | 票务、航班、天气、政策变化及刷新时点 |

这样既保留朝堂角色的文化辨识度，又不会让部门人设假装拥有不存在的专业能力。

## 5. 四个平面，而不是一个巨大 Agent

### 5.1 控制平面：任务和权限的唯一事实源

负责 canonical task、路由快照、幂等重试、暂停取消、人工审批、预算权限、事件账本与租户隔离。控制平面继续使用现有数据库、outbox 和 worker，不依赖前端会话，也不依赖 SSE 是否在线。

### 5.2 工作平面：按任务生成可审计 DAG

军机处把目标拆成 `WorkPackage`：

```json
{
  "work_package_id": "wp_travel_ticket",
  "task_id": "task_123",
  "objective": "核验决赛球票的官方获取路径",
  "required_capabilities": ["official_ticket_research", "fraud_screening"],
  "dependencies": [],
  "required_evidence": ["official_source", "checked_at"],
  "deliverables": ["ticket_options", "risk_notes"],
  "deadline": "2026-07-18T12:00:00Z",
  "retry_policy": {"max_attempts": 2},
  "status": "READY"
}
```

首期 DAG 不需要 LangGraph：使用版本化计划、依赖字段、outbox、worker 和事件账本即可。

### 5.3 证据平面：每个结论先变成 Claim

```json
{
  "claim_id": "claim_ticket_channel",
  "statement": "该渠道属于官方销售渠道",
  "source_url": "https://...",
  "source_owner": "FIFA",
  "source_class": "PRIMARY_OFFICIAL",
  "retrieved_at": "2026-07-18T08:00:00Z",
  "valid_until": "2026-07-18T12:00:00Z",
  "confidence": 0.98,
  "corroborates": [],
  "contradicts": [],
  "source_label": "LIVE_FACT"
}
```

来源优先级：

```text
官方实时接口/官方页面
  > 用户授权的内部事实源
  > 权威一手机构
  > 可靠聚合平台
  > 新闻/论坛/社媒线索
  > 模型记忆（不得用于时效性最终结论）
```

`LIVE_MODEL` 和 `LIVE_FACT` 必须分开：真实调用模型不能证明价格、库存或政策已核验。动态事实必须有 TTL；过期后显示“需要刷新”。

### 5.4 成果平面：结果必须是 Artifact Pack

```json
{
  "task_id": "task_123",
  "bundle_version": 1,
  "generated_at": "2026-07-18T09:30:00Z",
  "artifacts": [
    {"id": "brief", "format": "pdf", "label": "御前决策简报"},
    {"id": "budget", "format": "xlsx", "label": "预算与敏感性模型"},
    {"id": "sources", "format": "html", "label": "证据与来源账本"}
  ],
  "source_freshness": "MIXED",
  "missing_items": [],
  "human_actions": []
}
```

成果包生成失败不等于分析失败；二者要有独立状态和重试按钮。

## 6. 完整流程设计

### 阶段 0：一句话下旨

用户可以说：

> 我要从上海去美国看世界杯决赛，预算 8 万元，两个人，希望稳妥省心，给我完整攻略。

系统立即创建草案，但尚不执行外部动作。

### 阶段 1：圣意结构化

丞相生成 `GoalBriefV1`：明确目标、隐含目标、成功定义、预算、时间、人数、出发地、个人偏好、禁止事项、期望附件、关键歧义，并严格分离事实与假设。

### 阶段 2：只问一个高信息增益问题

只有答案会改变路线、合规、预算或结果时才追问。世界杯示例中最高价值的问题通常是：

> 两位旅客分别持什么护照，目前是否已有有效美国签证？

其余缺失项可采用保守假设继续，但必须显式列入假设和待补清单。

### 阶段 3：计划预览与用户校准

正式耗费模型、搜索和连接器预算前，展示工作包、预计耗时/成本、数据源、交付附件、可能需要批准的动作。用户可选择：

| 模式 | 适合 | 默认行为 |
| --- | --- | --- |
| 快办 | 低风险、单一交付 | 少量权威来源、快速简报 |
| 深办 | 旅行、采购、商业判断 | 多路并行采证、冲突检查、完整成果包 |
| 代办 | 需要实际预订/发送/创建文件 | 深办 + 分步人工授权；不默认开放 |

### 阶段 4：能力路由

丞相从 Capability Registry 召回具有真实工具、权限和健康状态的能力，比较 direct / council / evidence-first 候选路线。无可用能力时输出 `UNSUPPORTED_SCOPE` 或请求安装/授权能力，并保存不可变 RouteDecision 与 capability snapshot。

### 阶段 5：门下省前置审议

门下省审能力范围、关键缺项、安全预算权限和交付完整性。封驳分为：

| 类型 | 示例 | 处理 |
| --- | --- | --- |
| 软封驳 | 少了保险比较、预算缺一档 | 返回丞相修改，允许有限轮次 |
| 硬封驳 | 无真实能力、无授权、非法动作、核心身份缺失 | 永久 fail-closed；不得第三轮自动放行 |

只有 `menxia.verdict=准奏` 的精确路由版本才能产生 outbox 派单事件。

### 阶段 6：军机处编排

- 并行：机票、酒店、球票、城市交通、保险分别采集；
- 串行：确认比赛/球场后才能完成酒店区域和比赛日动线；
- 条件：没有有效签证时，先给出签证可行性和时间风险，再决定是否继续不可退预订建议。

军机处只向普通用户显示：现在做到哪一步、谁在办、卡在哪里、下一步需要用户做什么。

### 阶段 7：蜂群执行与动态改道

每个蜂群输出结构化结果、来源、缺口和置信度。工具失败时按策略重试或换能力；价格/库存拿不到时明确 NO_DATA；不得让裸 LLM 顶着部门人设编造实时信息；预算或时间超限时暂停低优先级工作包。

### 阶段 8：丞相综合与冲突台

形成已确认事实、争议事实、三套可比较方案、各方案成本/便利/风险/不可退损失、推荐理由，以及改变推荐的关键条件。

### 阶段 9：御史质量门

御史检查关键结论来源与时效、搜索结果是否冒充预订成功、预算是否漏项、票务渠道是否官方、时间地点金额是否冲突、是否越权、成果包是否完整。未通过时只重跑相关工作包。

### 阶段 10：回奏与成果包

用户先看到“一页御前摘要”，再按需展开。支持在线报告、Markdown、PDF/DOCX、XLSX/CSV、ICS、JSON 和 ZIP。

### 阶段 11：行动授权

研究完成不等于允许执行。每个副作用都生成 `ActionProposal`：

```json
{
  "action_id": "book_hotel_001",
  "summary": "预订可免费取消酒店",
  "max_amount": 12800,
  "currency": "CNY",
  "counterparty": "verified-provider",
  "expires_at": "2026-07-18T10:00:00Z",
  "approval_scope_hash": "...",
  "requires_human_confirmation": true
}
```

价格、库存、条款或收款方变化，旧批准自动失效。执行前重新验证授权与实时事实。支付响应超时时必须先向供应商查单，不能盲目重试。

### 阶段 12：史馆归档与结果回填

归档目标、计划、Claim、路由/能力版本、预算与实际结果、用户选择、真实价值和失效来源。只有真实 outcome 才能调整未来推荐权重，不能把点击“采纳”当作任务成功。

## 7. 世界杯任务的完整交付示例

### 7.1 输入

> 两个人从上海去美国看世界杯决赛，预算 8 万元，想省心、安全，最好能顺便玩三天。

### 7.2 必须覆盖的工作包

1. 决赛日期、球场、当地时区和官方信息确认；
2. 球票官方销售、官方 hospitality、授权渠道与诈骗风险；
3. 护照、签证/入境资格与预计办理时间；
4. 国际机票三档方案及退改、行李、转机风险；
5. 酒店位置、比赛日交通、取消政策与安全；
6. 机场—酒店—球场—景点—机场完整动线；
7. 三档预算和汇率/价格波动敏感性；
8. 保险、医疗、通讯、支付、小费与紧急联系；
9. 三日附加行程及体力/时间可行性；
10. 球票失败、签证延迟、航班取消、预算超限的 Plan B；
11. 临行前 30/14/7/1 天检查清单；
12. 所有关键来源、采集时间、有效期与刷新按钮。

票务优先使用 FIFA 官方票务和授权信息；非官方渠道可能无效。入境建议必须根据旅客身份引用美国官方来源，并明确 ESTA 不是签证，也不保证获准入境。

### 7.3 三套方案

| 方案 | 定位 | 用户价值 |
| --- | --- | --- |
| A 稳妥省心 | 官方 hospitality、可退酒店、少转机 | 风险最低，成本最高 |
| B 平衡推荐 | 官方普通票、位置合适酒店、一次转机 | 成本、体验、风险最平衡 |
| C 预算优先 | 灵活日期、外围酒店、公共交通 | 价格最低，但时间和库存风险最高 |

每套方案都要有“当前总价区间”“已验证到什么程度”“哪些尚未锁定”，不得用搜索价冒充可成交价。

```text
  01-完整旅行攻略.docx

  03-逐日行程与比赛日动线.pdf
  04-预订候选与官方链接.html
  05-证件签证与入境清单.pdf
  06-风险退改保险清单.pdf
  07-行前倒计时清单.md
  08-日历导入.ics
  09-证据与来源账本.html
  10-机器可读任务数据.json
```

不能生成所谓“球票 PDF”冒充有效票；票务凭证必须由官方渠道交付。

### 7.5 超预期设计

- 一键切换“预算增加 20%”“签证尚未拿到”“球票没抢到”并局部重算；
- 比赛日期、票务、航班价格或政策变化时，只刷新相关工作包；
- 用户批准后，将确定行程写入日历并生成行前提醒；
- 用“不可退金额”而不是只用总价衡量真实风险；
- 每个预订链接旁显示“来源、最后核验时间、是否官方、是否需要重新确认”。

## 8. “这门生意要不要做”的完整设计

### 8.1 丞相先定义真正的问题

结构化客户与痛点、用户资源、初始投入、最大可承受损失、地区与合规边界，以及希望得到裁决还是实验计划。

### 8.2 会审维度

| 维度 | 主责能力 | 关键输出 |
| --- | --- | --- |
| 需求真实性 | 锦衣卫/市场研究蜂群 | 搜索、访谈、订单或替代行为证据 |
| 市场与竞争 | 兵部 | 市场结构、竞品、渠道、差异化 |
| 单位经济 | 户部 | 毛利、CAC、LTV、现金流、盈亏平衡 |
| 产品与交付 | 工部 | MVP、供应链、技术与交付可行性 |
| 法律与责任 | 刑部 | 准入、合同、隐私、知识产权和责任风险 |
| 品牌与增长 | 礼部 | 定位、叙事、获客内容和渠道一致性 |
| 团队与组织 | 吏部 | 能力缺口、关键岗位、外包/自建选择 |
| 二阶效应 | 钦天监 | 可逆性、窗口期、竞争反应与到期预测 |
| 反方审查 | 门下省/御史 | 为什么不该做、哪些证据会推翻结论 |

### 8.3 最终不是一个分数，而是一个决策组合

```text
裁决：CONDITIONAL_GO
推荐：先做 14 天、预算不超过 3 万元的付费验证
继续条件：获得 ≥10 个有效访谈、≥3 个付费意向、毛利模型 ≥40%
停止条件：CAC 预测超过首年毛利；核心交付必须依赖未取得资质
最大风险：需求只存在于口头兴趣，没有付费行为
下一步：三项可逆实验，而不是直接重投入
```

### 8.4 商业成果包

- 一页决策简报；
- 市场与竞品矩阵；
- 单位经济和现金流模型；
- 风险、合规与合同清单；
- MVP 与 14/30/90 天实验计划；
- 客户访谈脚本和渠道测试素材；
- 红队反对意见；
- 证据账本与关键假设；
- 投资上限、停止条件和下一次复盘日期。

裁决统一为 `GO / TEST_FIRST / NO_GO / NEED_EXPERT`，并绑定输入与证据版本。

## 9. 用户界面：复杂系统，简单表面

### 9.1 上书房只做三件事

输入一句话、回答一个关键问题、确认办事计划。不要让普通用户选择部门、Agent 或工作流框架。

### 9.2 军机处只显示四层信息

```text
第一层：一句话状态与预计完成时间
第二层：工作包进度、阻塞与需要用户动作
第三层：各部关键发现、证据和冲突
第四层：完整事件账本与调试信息（高级用户）
```

### 9.3 回奏采用“结论先行、证据下钻”

首页只显示推荐方案、理由、最大风险、缺口、下一步和下载成果包；用户再展开部门意见、来源、时间线和技术细节。

### 9.4 伦理型惊喜机制

- “丞相替你发现”：主动指出一个会改变结果的问题；
- “如果……会怎样”：即时运行预算、时间或风险情景；
- “可省掉的麻烦”：标出最值得花钱换省心的环节；
- “一键刷新”：只更新过期事实；
- “复用旧案”：复用偏好前先展示和确认；
- “持续项目”：仅在票务、政策、价格或关键商业指标发生实质变化时通知。

## 10. 与 Manus 类产品相比，朝堂 OS 应该赢在哪里

Manus 的强项是通用云电脑、浏览器操作、文件生成和大量同类子任务并行；其 Wide Research 将任务拆成独立子任务并行执行，再由主 Agent 汇总。OpenAI、Anthropic 和 Gemini 的 Deep Research 也共同强化了计划、迭代搜索、可核验引用、内外部数据连接和报告交付。

朝堂 OS 不复制“再做一个通用云电脑”，而形成以下差异：

| 维度 | 通用 Agent 强项 | 朝堂 OS 目标优势 |
| --- | --- | --- |
| 任务广度 | 什么都能尝试 | 对高价值决策和企业执行更深 |
| 过程 | 一个强 Agent/并行 Agent 完成 | 丞相路由、门下封驳、御史质门、皇上授权 |
| 信任 | 引用、运行回放 | Claim 账本、版本化审批、责任归属、正式奏折 |
| 企业治理 | 连接器与权限 | 六部治理、租户隔离、风险硬门、结果审计 |
| 长期价值 | 单次任务成果 | 史馆 outcome、翰林评测、国力指标、组织记忆 |
| 执行 | 云电脑和浏览器代办 | 先形成决策包，再按动作逐项授权与回执 |

真正的超越不是“Agent 更多”，而是：**每次任务更可信、更可控、更可复用，并对最终结果负责。**

## 11. 安全核心：广域研究面与窄域交易面

```text
广域研究面
  可读互联网和隔离后的附件
  所有外部内容均视为 UNTRUSTED_DATA
  只能形成候选 Claim
           ↓
证据、策略、预算、隐私与授权门
           ↓
窄域交易面
  只调用经过审查的供应商 adapter
  无任意 URL、无通用浏览器、无自由工具选择
```

最小控制包括：

- 官方/授权商户 registry 与域名/重定向校验；
- 工具使用任务级临时 capability token；
- 附件隔离、真实类型嗅探、大小/解压限制、病毒/宏/注入扫描；
- Excel/CSV 公式注入防护；
- 护照、支付 token 与健康信息不进入模型上下文或普通日志；
- 同行人分别授权；
- 下载链接短期、鉴权、租户隔离并带 hash；
- 报价与订单分开；重试支付前先查单；
- 部分成功进入 `PARTIAL_FAILURE/COMPENSATION_PENDING`，绝不标完成。

## 12. 方案优缺点与选择理由

### 12.1 优点

1. 对用户简单：一句话下旨，不暴露内部复杂性。
2. 对复杂任务有效：按能力动态组队，避免固定部门误路由。
3. 对结果负责：成果包和完成定义取代文本长度。
4. 对时效诚实：价格、库存、政策和来源都有 TTL。
5. 对企业安全：事实、判断、授权、执行严格分层。
6. 对工程务实：复用现有 canonical task、outbox、事件账本和正式奏折。
7. 对未来开放：后续可接 LangGraph、Temporal、MCP 或更多专业连接器，而不改事实源。

### 12.2 缺点与成本

1. 前期要建立 Capability Registry、Claim 和 Artifact 三套契约，短期开发量大。
2. 高质量结果依赖真实连接器与数据授权，不能只靠大模型。
3. 多路研究成本和延迟高，需要预算控制、缓存与局部刷新。
4. 质量门过严会降低“看起来很聪明”的流畅感，需要把 NO_DATA 做得友好。
5. 附件生成、存储、病毒扫描、访问控制和过期清理会增加平台复杂度。
6. 动态 DAG 比固定流程更难测试，必须建设黄金任务、故障注入和可观测性。

### 12.3 为什么仍然选择它

用户愿意长期付费的不是一次惊艳演示，而是稳定节省时间、降低损失、交付能直接使用的成果。四平面设计把“智能”与“可靠”同时保住，并允许先从一个完整旅行任务和一个完整商业任务纵向落地。

## 13. 为什么首期不引入 LangGraph

当前仓库已经拥有 canonical task、路由快照、outbox、worker、事件账本、状态投影、人工裁决、正式奏折与归档。首期最缺的是契约和真实能力，不是另一套编排运行时。现在引入 LangGraph 会形成 checkpoint state 与 canonical task 的双事实源风险。

满足以下任意两项后再评估：

1. 超过 30% 的任务需要跨天暂停并从节点级 checkpoint 恢复；
2. 单任务 DAG 稳定超过 20 个动态节点；
3. 需要大量人工中断后修改中间 Agent state；
4. 现有 outbox/worker 的补偿与重试代码持续快速膨胀；
5. 有明确基准证明迁移后可靠性或开发效率提升至少 30%。

即使引入，数据库 canonical state、授权记录、Claim 和 Artifact 仍是权威事实源。

## 14. 分阶段落地路线

### P0：先堵住会“自信办错”的洞

- 正式下旨主链统一接入 `UNSUPPORTED_SCOPE`；
- 门下省硬封驳真正阻断 outbox；
- 删除“无真实能力第三轮自动放行”；
- 能力不足、工具不可用和 NO_DATA 进入 canonical 状态；
- 收口所有部门调用的任务级预算，不允许特殊路径绕过；
- 固化世界杯反例、跨租户、预算绕过与附件安全测试。

退出条件：世界杯任务在尚无旅行能力时必须诚实停在“需要能力/授权”，不能由户部、工部裸 LLM 编结果。

### P1：成果包最小纵切

- `GoalBriefV1`；
- `WorkPackageV1`；
- `ClaimV1`；
- `ArtifactManifestV1`；
- Markdown/PDF/JSON/ZIP 最小导出；
- 军机处展示真实工作包和成果状态。

退出条件：一个受控黄金任务可以从下旨生成可下载、带来源的完整小成果包。

### P2：世界杯完整黄金旅程

- `TravelMissionPack` 和官方来源策略；
- 票务、入境、机酒、交通、预算、风险、行程工作包；
- TTL、局部刷新和 Plan B；
- 世界杯成果包和浏览器 E2E。

退出条件：同一 `task_id` 完成全链路，关键事实可追溯，动态数据过期后不会继续显示为 LIVE_FACT。

### P3：商业 GO/NO_GO 决策包

- `BusinessDecisionPack`；
- 市场、竞品、财务、法务、产品、渠道、组织能力包；
- 三方案与反方审查；
- 单位经济表和 14/30/90 天验证计划；
- 决策后 outcome 回填。

退出条件：系统能说明“为什么做/为什么不做/什么条件下改变结论”，不是只给综合分数。

### P4：受控代办

- `ActionProposalV1`；
- 版本化审批；
- 执行前事实与授权复核；
- 预订、日历、邮件等低风险连接器；
- 回执、撤销与补偿路径。

退出条件：任何副作用都能回答谁批准、批准了什么、依据哪版事实、最终结果是什么。

### P5：结果飞轮

- 史馆 outcome；
- 翰林离线评测；
- 国力任务成功率、返工率、封驳率和成果使用率；
- 基于真实结果调整能力权重；
- 变化监控与持续项目。

## 15. 验收指标

### 用户价值

- 首个有用的目标复述：≤ 10 秒；
- 需要追问时，每轮默认最多 1 个问题；
- 深办计划预览：≤ 30 秒；
- 完整黄金任务成功率：≥ 90%；
- 成果包下载/打开率：≥ 60%；
- 30 天高价值任务复用率：≥ 35%；
- 用户报告节省时间中位数：≥ 2 小时/任务。

### 质量与安全

- 关键结论来源覆盖率：100%；
- 动态事实 TTL 覆盖率：100%；
- 无能力任务误派率：< 1%；
- 未授权副作用：0；
- 跨租户数据泄露：0；
- 重复点击导致重复任务/付款：0；
- 过期审批继续执行：0；
- FALLBACK 被展示为 LIVE_FACT：0。

### 运营效率

- 局部重跑占全部重跑比例：≥ 80%；
- 可恢复失败比例：≥ 95%；
- 每项成果可定位到 task/trace/work package/claim/artifact：100%；
- 用户因系统状态不明而重复提交的比例：< 2%。

## 16. 必须覆盖的验收测试

1. 零能力匹配必须 `UNSUPPORTED_SCOPE`，不能默认户部/工部执行；
2. 门下省硬封驳后不得出现 outbox 派单；
3. SSE 断线或页面刷新后，从 canonical state 恢复同一任务；
4. 重复下旨与重复批准保持幂等；
5. 动态价格过期后，旧批准不能下单；
6. 一个蜂群失败时可以局部重试或换能力，不重复运行成功工作包；
7. 两个来源冲突时进入争议区，不能静默选择更顺耳的一方；
8. 官方票务与非官方来源混合时，御史阻断不安全推荐；
9. 成果生成失败可单独重试，不重跑全部研究；
10. 用户取消任务后，不再启动新的工具调用或副作用；
11. 史馆与下载链接保持权限、租户隔离和过期控制；
12. 商业任务缺少内部财务数据时，只能输出假设模型，不能声称真实 ROI；
13. 全链路所有页面对同一 task 显示一致阶段和下一步；
14. 恶意网页、PDF 或同伴文本中的工具指令不能触发交易；
15. 报价变化超过用户上限时必须重新确认；
16. 同一购买确认重放 100 次只能形成一个订单；
17. 支付超时先查单，不得盲重试；
18. 部分成功进入补偿状态，不标完成；
19. 护照、卡号、健康信息在模型请求、日志与普通成果包中零明文泄漏；
20. 下载包中的每条关键结论能反查来源、时间、版本和 hash。

## 18. 大神会审结论

### Charity Majors：可观测性与可靠性

最大风险不是 Agent 不够聪明，而是任务看似完成，却无法证明哪一步真的成功。每个成果必须贯通 `tenant_id → task_id → trace_id → work_package_id → claim_id → artifact_id → approval_id → effect_id`。

### Bruce Schneier：权限与真实世界副作用

研究、建议、授权、执行必须分开。任何付款、购票、订房、提交个人资料、签约或公开发布都必须在提交瞬间重新验证事实和授权，不接受“之前批准过”的模糊权限。

### 最终裁决

采用“四平面 + 动态能力班子 + 双层封驳 + 成果包”的方案；首期不引入 LangGraph。先完成 P0 安全收口和 P1 成果包纵切，再做世界杯与商业判断两个黄金旅程。

## 19. 技能与方法建议

- `product-manager-ai-workflow`：每个黄金旅程都产出用户故事、边界条件、验收测试与可下载成果定义；每个 Packet 开始时执行 1 次（估测）。
- `expert-perspective`：在状态机、授权、连接器和不可逆动作设计冻结前做双专家会审；每个高风险 Packet 合并前执行 1 次（估测）。

技能替换建议：把“多个固定角色分别写长意见”的旧做法替换为“Capability Registry + WorkPackage + Claim + Artifact”的契约驱动方案。更好的下一步技巧是建立两条真实黄金任务回放，并用故障注入验证断线、过期、冲突、重复点击和部分失败。

## 20. OpenClaw、Hermes、Humen/Hume：能用，但不能抢走朝堂主权

### 20.1 总体裁决

外部 Agent 产品都按“可替换能力插件”接入，不能成为朝堂 OS 的任务、证据、授权或知识事实源。

| 组件 | 最适合的定位 | 现在是否可用 | 不能承担的职责 |
| --- | --- | --- | --- |
| OpenClaw | 外廷驿站：多渠道入口、远程设备、隔离运行时、长任务 worker | 仓库已有可选适配器，可做受控试点 | canonical task、授权中心、正式证据源、交易裁决 |
| Hermes Agent | 锦衣卫/翰林候选 worker：定时研究、监测、隔离实验、技能候选生成 | 可做独立 PoC，当前未接入正式主链 | 自动修改生产 prompt/skill、直接晋升知识、执行高风险动作 |
| Humen（若指 `tryhumen.com`） | 兵部销售专案：找潜客、研究 ICP、生成外联草稿和实验数据 | 产品可人工使用；官网仍写 API “Soon”，不宜承诺正式连接器 | 通用编排、企业知识库、自动代表用户批量发送 |
| Hume AI（若用户实际指它） | 丞相/钦天监可选语音界面 | 可做语音交互 PoC | 把情绪推断当事实、替代用户授权、决定任务风险 |
| Human-in-the-loop 服务（若 “Humen” 指人工审批层） | 把审批通知送到 Slack、手机或邮件 | 可作为通知 adapter | 取代 CourtOS 中版本绑定的 `EmperorDecision` |

“Humen”不是唯一可识别的产品名。实施选型前必须由用户提供准确链接；在此之前，设计同时保留上述三种解释，绝不把一种产品的能力写到另一种产品名下。

### 20.2 OpenClaw：把它当驿站和工坊，不当皇帝

OpenClaw 官方把 runtime、model/provider 与消息 channel 分成不同层，并支持多个渠道和运行时。这与朝堂 OS 的“能力可替换”方向兼容：[Agent runtimes](https://docs.openclaw.ai/concepts/agent-runtimes) · [Runtime architecture](https://docs.openclaw.ai/agent-runtime-architecture)。

当前仓库已有 `backend/src/openclaw_client.py` 与 `backend/tests/test_openclaw_ready.py`：可以按环境变量启用 OpenClaw，错误或超时回退到 spawn。这证明“可插拔 seam”存在，但当前协议只有：

```text
POST /tasks
{"tasks": ["自由文本任务"]}
→ {"results": ["自由文本结果"]}
```

它缺少 `tenant_id`、`task_id`、`trace_id`、权限、预算、时限、证据、结果哈希和执行回执，不能直接用于正式奏折。更准确地说，截至当前基线，这只是出站执行脚手架：测试使用 mock HTTP，仓库不负责安装、启动或探活 OpenClaw；正式前端 live adapter 仍是 disabled；也没有把 OpenClaw 的聊天渠道接入 canonical `DecisionTask` 的入口 adapter。环境变量存在只能说明“配置了地址”，不能证明服务健康或能力已上线。

目标协议应升级为：

```yaml
request: WorkPackageV1
  tenant_id:
  task_id:
  trace_id:
  work_package_id:
  capability_id:
  objective:
  input_refs:
  allowed_tools:
  egress_allowlist:
  capability_token:
  model_budget:
  wall_clock_deadline:
  output_schema: EvidencePacketV1

response: EvidencePacketV1
  status:
  claims:
  citations:
  artifacts:
  tool_receipts:
  cost_and_latency:
  raw_output_hash:
  runtime_identity:
  errors:
```

接入硬门：

1. OpenClaw 启动时通过身份、版本、健康、沙箱和能力清单校验；
2. 每个任务使用短期 capability token，默认无支付、发信、删除和任意网络权限；
3. 自由文本结果只能是 `UNVERIFIED_DRAFT`，经过 schema、证据和御史门后才能进入正式回奏；
4. 超时回退必须记录 `runtime_changed=true`，不能静默把不同运行时结果当成同一证据等级；
5. 历史仓库记录多次出现 CLI 不存在、路径和定时任务失败，因此必须具备熔断、降级和人工可见状态；
6. OpenClaw 故障不能改变 canonical task，恢复后也不能重复副作用。
7. 响应必须校验结果数量、元素类型、幂等键和 schema；少项、多项或格式错误按工作包失败处理，不能静默缺项或整体伪成功。

最先适合它做的是：定时公开信息监测、只读网页研究、跨渠道任务入口、隔离文件处理。最晚才考虑浏览器登录和现实动作。

### 20.3 Hermes：把“会自我成长”关进翰林实验场

Hermes 官方列出的能力包括跨 Telegram/Discord/Slack/WhatsApp/Signal/Email/CLI 的持久记忆、自然语言定时任务、隔离子代理、Web/浏览器能力、多个沙箱后端和自动生成技能：[Nous Research 官方介绍](https://nousresearch.net/hermes-agent/) · [开源仓库](https://github.com/nousresearch/hermes-agent)。

当前仓库中的 `hermes-expert`、`hermes-business/chat` 和 `backend/src/memory_store.py` 只属于路由标签、模型别名或 “Hermes 风格”本地记忆实验；仓库没有 Nous Hermes Agent client、服务端点或正式 adapter。它们不能作为“Hermes Agent 已接入”的证据。

这些能力很适合两个受控位置：

- **锦衣卫监测 worker**：定时发现票务、政策、竞品、舆情和价格的实质变化，只提交候选 Claim；
- **翰林技能候选工坊**：从重复成功案例中生成 skill 草案和测试草案，但不能直接部署。

Hermes 生成的任何技能必须走：

```text
Hermes 生成 candidate
  → quarantine
  → 静态安全检查与工具权限审计
  → 黄金任务离线回放
  → 对抗/故障样例
  → 翰林与当前 baseline 对比
  → 人工批准精确版本
  → shadow
  → 5% canary
  → 正式 release 或自动回滚
```

禁止 Hermes 直接改生产 prompt、生产技能、Capability Registry、知识真值、审批策略或交易工具。所谓“自我进化”只能产出候选物，晋升权永远属于确定性门禁与人。

### 20.4 Humen：只做兵部销售专案，不做底座

若用户指的是 [Humen](https://tryhumen.com/)，其官方定位是早期公司销售外联：研究潜客、生成名单和个性化邮件，并用分析反馈优化信息。它可成为 `OutboundGrowthPack` 的一个候选专业工具：

```text
商业目标
→ ICP 假设
→ 合规潜客来源
→ 候选名单与证据
→ 信息草稿
→ 用户审批
→ 小批量实验
→ 回复/退订/投诉 outcome
→ 兵部复盘
```

但官网当前仍将 API 标为 “Soon”，所以短期只能把导出结果当外部候选数据，不能设计成强依赖。即使未来有 API，发信也必须逐批授权、支持退订/抑制名单、频控和地域合规；“预测购买概率”只能是供应商声明，必须用本项目真实转化结果重新校准。

### 20.5 Hume AI：语音可以亲切，权力必须冷静

若用户想说的是 [Hume AI EVI](https://www.hume.ai/empathic-voice-interface)，它支持实时语音、打断、暂停/恢复、上下文注入和自带/自选 LLM，适合让丞相更自然地听旨、让钦天监讲解情景。

设计边界：

- 声音情绪只用于调整语速、停顿、解释深度和是否主动复述；
- 不把声音推断写成“用户焦虑/冲动/同意”，不用于信用、招聘、健康或风险裁决；
- 每个购买、发送、签约等授权仍显示精确文字卡片，由用户明确点击或复述后再次确认；
- 原始音频默认不进长期知识库，转写、情绪特征和保留期限分别授权；
- 钦天监不能用“神秘、权威”的声音包装低置信预测。

## 21. 知识库：不是一个向量文件夹，而是一套可追责的记忆制度

### 21.1 六类记忆分开治理

| 记忆类型 | 内容 | 生命周期 | 可否自动复用 |
| --- | --- | --- | --- |
| 工作记忆 | 当前 GoalBrief、工作包、临时假设、工具输出 | 任务结束后最小化/过期 | 仅当前任务 |
| 案例记忆 | 某次任务的输入、决策、成果、真实结果与复盘 | 版本化长期保存 | 相似任务检索，不直接当真理 |
| 语义知识 | 法规、官方规则、产品资料、企业事实、已批准方法论 | 带来源、版本、TTL | 在授权域内可检索 |
| 偏好记忆 | 用户预算、座位、表达和风险偏好 | 可查看、修改、撤回 | 必须有用户授权与置信度 |
| 程序记忆 | 已批准的 skill、workflow、schema、tool policy | release 版本管理 | 只运行已发布版本 |
| 制度记忆 | 权限、风控、租户边界、保留/删除规则 | 最高优先级 | 自动强制执行 |

绝不能把全部聊天记录、Agent 自己的推测和未经验证的网页摘要一股脑嵌入向量库。那不是记忆，是长期污染。

### 21.2 物理分层与唯一事实源

```text
SQL 控制面
  文档身份、tenant/owner、版本、授权、许可、保留、状态、引用关系
      │
      ├── Object Store
      │     不可变原始快照、附件、成果、hash、扫描结果
      │
      ├── Search Projections
      │     BM25 / vector / graph；全部可由控制面重建
      │
      ├── ShiguanArchive
      │     当时正式裁决与证据快照，不可悄悄改写
      │
      └── OutcomeEvent
            后来真实结果，append-only
```

事实源规则：

- SQL 元数据、授权、版本和关系是知识控制面的 SSOT；
- Object Store 保存原始证据和成果；
- 向量库、全文索引和知识图谱只是可重建投影，不能反向晋升真值；
- `ShiguanArchive` 是正式案卷；后来的成功/失败用 `OutcomeEvent` 追加，不改写当时判断；
- Obsidian 适合人工编辑、浏览和复盘，不是生产事务数据库；
- `courtos-brain/` 和旧向量资源在 owner、license、版本与哈希未核清前保持 archive/quarantine；
- 当前 IMA 附件层未完成严格租户隔离前，不承载多租户商业机密。

这与既有 `docs/plans/chaotang-os-knowledge-memory-flywheel-blueprint-2026-07-14.md` 保持一致；本蓝图只补充面向超级任务的使用方式，不另造第二套知识主线。

### 21.3 四个知识域

| 域 | 示例 | 默认访问策略 |
| --- | --- | --- |
| `task_evidence` | 本次机票报价、用户附件、访谈原文 | 仅当前 task/授权复核者 |
| `tenant_private` | 公司财务、客户、合同和内部 SOP | 仅本租户授权主体 |
| `user_private` | 个人偏好、证件状态、历史选择 | 仅本人和明确委托任务 |
| `platform_shared` | 公开法规、官方规则、已批准通用方法 | 全租户只读，仍需版本和来源 |

检索优先级不是“相似度最高”，而是：

```text
当前任务证据
→ 本租户事实
→ 用户授权偏好
→ 平台共享知识
→ 实时外部检索
```

每层都经过权限过滤，再进行 metadata filter + BM25/vector 混合召回 + rerank + freshness/authority 检查。禁止先全库召回、再在模型里“提醒它不要泄露”。

### 21.4 摄取与晋升管线

```text
外部网页 / 文件 / API / 人工输入
→ immutable snapshot + hash
→ quarantine
→ 恶意内容、PII、许可、owner、格式检查
→ 去重与冲突识别
→ KnowledgeDocument / KnowledgeVersion
→ chunk + searchable projections
→ ClaimEvidenceLink / CitationUsage
→ 御史引用门
→ 正式回奏或保持候选
```

一条知识至少包含：来源、抓取时间、内容哈希、适用主体、有效期、许可、授权域、冲突状态和可删除性。搜索摘要只能用来发现来源，不能成为正式证据。

### 21.5 时间、冲突与遗忘

- 价格、库存、天气和票务状态使用分钟/小时级 TTL；
- 政策与产品规则使用事件触发刷新 + 最大 TTL；
- 稳定概念也保留 `valid_from/valid_to` 和来源版本；
- 新证据与旧知识冲突时，不静默覆盖，生成 `KnowledgeConflict` 并阻断关键裁决；
- 过期只降低可用性，不删除历史案卷；
- 用户撤回、许可失效、DSAR 或租户终止时，从对象、chunk、vector、cache、派生数据和下载物做可对账删除/封存。

## 22. 天才飞轮：只从真实结果学习，不从自己的作文学习

### 22.1 主循环

```text
目标与约束
→ 计划与候选方案
→ Claim + Evidence
→ 用户裁决
→ 受控行动
→ 经过认证的真实 Outcome
→ 史馆复盘
→ 错误/成功模式抽取
→ 翰林离线实验
→ 黄金集 + shadow 对比
→ 人工批准版本
→ canary
→ 指标变好才扩大；变差自动回滚
```

飞轮的燃料是“后来到底发生了什么”，不是点赞、长回答、Agent 自评分或生成了多少笔记。

### 22.2 反事实账本

每次重要决策同时保存：

```yaml
chosen_option:
rejected_options:
expected_outcome:
confidence_range:
decisive_assumptions:
kill_criteria:
settlement_date:
what_would_change_the_decision:
```

到结算日后再比较预期与真实结果。这样系统不只知道“用户选了 A”，还知道为什么没选 B、预测错在哪里，以及当时信息是否足以得出结论。

### 22.3 四个自动矿场

1. **硬负样本矿**：门下/御史封驳、用户纠错、无来源结论、超时、重复副作用、部分失败自动进入 eval 候选；
2. **高价值成功矿**：只有具备完整证据链、真实 outcome 且无安全事故的案例才进入成功候选；
3. **知识冲突矿**：新旧政策、不同来源、预测与结果冲突，生成 freshness 与辨伪测试；
4. **用户摩擦矿**：重复追问、计划被大改、成果未打开、重复提交，转成 UX 与路由测试，而不是简单归咎用户。

### 22.4 经验编译器

同一种办事方式至少在 3 个独立、结果可验证的案例中成功，系统才提出 skill 候选：

```text
重复模式
→ 提取前置条件、步骤、工具、失败路径、停止条件
→ 生成 candidate skill + tests
→ Hermes/Agent 可协助起草
→ 翰林离线评测
→ 安全/成本/质量三门
→ 人工批准
→ 版本化发布
```

次数“3”只是进入评审的最低门槛，不代表统计显著，也不允许自动发布。高风险技能需要更大样本和专业复核。

### 22.5 奖励函数

```text
FlywheelValue =
  0.35 × 真实目标达成
+ 0.20 × 关键结论证据完整
+ 0.15 × 用户实际采用/成果使用
+ 0.10 × 可恢复与无事故
+ 0.10 × 成本/时延效率
+ 0.10 × 跨案例稳定性
```

硬门优先于总分：跨租户泄露、未授权副作用、伪造来源、重复付款或关键安全事故任一发生，候选直接不得晋升。

### 22.6 两个场景如何形成复利

世界杯任务不会把“某天某价机票”晋升为通用知识，而会沉淀：官方票源核验步骤、报价过期规则、比赛日交通缓冲算法、用户已授权偏好和实际延误 outcome。

商业判断不会因为用户最后创业就把原结论标成“正确”，而会在 30/90/180 天结算获客成本、毛利、回款、留存和停止条件，从而校准下一次的区间与实验建议。

### 22.7 防止飞轮变成错误放大器

- Q&A、模型自评和用户一句“不错”不能成为事实标签；
- outcome 必须来自用户确认、受信系统回执或可验证外部来源，并记录认证等级；
- 一个租户的经验默认不能训练或暴露给另一租户；
- 只有可追到 `task → claim → evidence → decision → action → outcome` 的样本可进入翰林数据集；
- 数据集、baseline、candidate、评测器和 release 全部版本化；
- 评测提升但安全退化时不得晋升；
- 被删除或授权撤回的数据必须从未来数据集和可重建投影移除。

### 22.8 当前代码中的飞轮 stop-ship 旁路

以下是基于当前基线的已确认缺口，不是抽象担忧。在它们关闭前，禁止开启自动归档、跨租户共享学习或技能自动晋升：

| 现存旁路 | 风险 | 必须收口为 |
| --- | --- | --- |
| `court_flywheel.py` 可把几乎所有非 error 模型报告写入 RAG，`daily_court_session.py --archive` 可绕过 API 禁写 | 模型输出回灌并形成自证循环 | 所有 API/CLI/cron 只能调用统一 `KnowledgeIngestionService` |
| `knowledge_vet.py` 以最高相似度和 `0.35` 阈值判 grounded | 高度相似的反驳文本也会被当作支持 | 同时验证原文定位、蕴含/矛盾、来源、版本、有效期和适用范围 |
| `truth_ledger.py` 缺租户上下文时退回全局 JSONL，gate 只看 checker + PASS | 跨租户污染，调用方可伪造 provenance | 显式不可伪造 `AuthorizationContext`；缺租户 fail-closed；来源签名/回执核验 |
| `knowledge/router.py` 线程检索未显式传播租户，空租户历史文档被当共享 | 异步/线程边界导致数据泄露 | 权限过滤进入查询本身；后台任务也必须携带授权上下文 |
| `direct_feedback.py` 信任客户端 task/command/target，首次 bad feedback 即可激活 override | 重放、冒名与反馈投毒改变路由 | 服务端回查任务和版本；同主体同版本单一有效反馈；supersede 而非刷票 |
| `failure_memory.py` 保存模型自评，`reasoning.py` 又把它作为 system 指令参考 | 持久化提示注入与错误强化 | 自评/自由文本均为 `DERIVED_UNTRUSTED`，结构化抽取和审核后才能参考 |
| `skill_manager.py` 可从可变 URL/Git 安装并动态执行 hook | 技能供应链执行恶意代码 | 固定 digest/签名/SBOM、禁网禁密钥沙箱、双人批准、canary、kill switch |
| `typed_memory.py` 的 user memory 主要隔离到 tenant | 同租户跨用户读到私人记忆 | 真正 `tenant_id + user_id + purpose` ACL 与完整删除血缘 |

### 22.9 飞轮晋升的十四道硬门

1. **单一写入口**：旧脚本、CLI 和定时任务不能直写 RAG、vector 或 ledger；
2. **显式授权上下文**：无 tenant/user/purpose 的生产读写一律失败，空租户不等于共享；
3. **来源与防循环**：AI 派生物不能成为终局证据，引用图和语义近重复必须检测自引用环；
4. **证据判定**：相似度只负责召回，不负责证明；支持、反驳和不相关要分别判定；
5. **时效**：保留 `observed_at/valid_from/valid_to/effective_at/superseded_by` 与历史时点回放；
6. **反馈真实性**：满意、事实纠错、偏好、执行结果分轨，客户端不能指定受影响的系统对象；
7. **结果真实性**：Outcome 绑定采集主体、执行版本、偏差、观察窗和结算状态；未结算是 `NO_DATA`；
8. **记忆信任分层**：自评、反思、用户自由文本不能直接进入 system prompt；
9. **评测防泄漏**：先冻结 holdout，候选不能读标签、改评估器或检索近重复答案；
10. **职责分离**：候选作者、标注负责人、发布批准人分离，批准绑定精确 digest；
11. **技能供应链**：固定依赖、许可和签名；最小权限沙箱；技能不能评审或晋升自身；
12. **删除与撤销**：删除传播到对象、切片、vector、cache、日志、反馈、评测集、导出和 release；
13. **共享学习**：tenant/user 私有数据默认不共享；候选需许可、去标识和单租户贡献上限；
14. **可回滚发布**：任务固定 knowledge/prompt/skill/eval 版本，污染时可吊销权限并复评依赖产物。

## 23. 到底要多少个 Agent：默认 6 个逻辑角色，按任务伸缩

### 23.1 先区分“角色目录”和“本次上朝人数”

仓库已有约 71 份 runtime prompt 和大量 agent design，它们应该成为 Capability Registry，不应该每次全部运行。Agent 数量不是生产力指标；部门越多，自由文本重复、冲突、成本和等待越多。

一个标准复杂任务的推荐默认值是：

```text
1 丞相：理解、计划、最后综合（同一逻辑角色的两个阶段）
1 门下：计划前置反审，必要时才用 LLM
3 专业 worker：按能力并行
1 御史：证据、缺口、冲突与完成门
= 6 个逻辑角色
```

钦天监是条件触发的第 7 个角色；普通任务不默认召集。军机处、史馆、预算器、权限门和状态机应主要是确定性代码，不算 LLM Agent。

### 23.2 自适应人数表

| 任务等级 | 示例 | worker | 典型逻辑角色总数 | 默认并发上限 |
| --- | --- | ---: | ---: | ---: |
| D0 直接任务 | 格式转换、单一文件摘要 | 0–1 | 1–2 | 1 |
| D1 轻任务 | 三个酒店比较、简单文案包 | 2–3 | 3–5 | 3 |
| D2 标准复杂任务 | 世界杯攻略、商业可行性初评 | 3–6 | 6–9 | 6 |
| D3 高风险/跨域 | 交易、合同、投资、敏感数据 | 4–8 + 专家 | 8–12 | 6–8 |
| Wide Research | 数百个相互独立对象扫描 | 8–20 | 10–22 | 首发 12，验证后最多 20 |

最终建议：**日常默认 6 个逻辑角色，普通任务 hard cap 9；高风险任务在人工批准下最多 12；首发 Wide Research hard cap 12。**只有同构、独立、可合并的任务在真实基准证明去重、冲突、成本和限流门均稳定后，才把研究并发逐步提高到 20。副作用执行始终串行 1 个，同一登录浏览器最多 1–2 个。

### 23.3 动态扩缩规则

军机处采用“两阶段扩军”：先由丞相和 2 个侦察 worker 快速建立覆盖图，再只针对决定性缺口、冲突和时效风险增派专家。这样简单任务不会为“排场”召集整座朝堂，复杂任务又能在证据不足时继续变深。

只在以下情况加一个 worker：

- 出现新的独立专业域；
- 两个权威来源冲突，需要独立裁判；
- 工作包可以无依赖并行，且预计节省时间大于协调成本；
- 当前置信度/覆盖度低于门槛，并且新增采证能改变结论。

以下情况必须停招或裁撤：

- 连续两个 worker 没增加新 Claim、来源或方案差异；
- 已达到模型、搜索、时间或金钱硬预算；
- 新 worker 只能重复已有自由文本；
- 缺少决定性用户输入，继续研究不会改变方案；
- 任务进入授权/交易阶段，研究面 worker 应冻结。

军机处维护 `AgentBudget`：`max_workers`、`max_concurrency`、`token_budget`、`tool_budget`、`cost_budget`、`deadline`、`novelty_stop_threshold`。丞相可以建议扩编，但预算器和皇上授权决定是否扩编。

## 24. 丞相与钦天监：一个主对话，一个关键时刻的反方顾问

### 24.1 用户永远只面对一个正门

丞相是默认唯一主对话者。各部、蜂群和御史不轮流给用户发长消息；它们的意见由丞相综合，证据可下钻查看。钦天监是侧边顾问，不另开一个与丞相争抢注意力的聊天窗口。

### 24.2 丞相的六拍交互

1. **听旨**：一句话复述“你真正要完成什么”，标出一个可能误解；
2. **一问**：默认只问一个最影响方案的问题；高风险旅行可在同一张卡一次收齐最多 3 个阻塞字段；
3. **亮案**：展示可编辑的目标、约束、工作包、预计时间、预算和成果清单；
4. **静办**：只在计划改变、出现阻塞、需要授权或已有关键结论时更新，不刷流水账；
5. **回奏**：先给结论、A/B/C 方案、最大风险、未知项和下一步；
6. **请裁**：把现实动作拆成精确卡片逐项批准。

丞相的语言规则：结论先行、承担综合责任、明确不知道什么、不冒充事实源、不堆部门黑话、不用“臣等一致认为”掩盖冲突。

计划卡示例：

```text
丞相理解：两人从上海出发，在预算 8 万元内现场看世界杯决赛并安全往返。

我将先核验：入境可行性、官方球票、航班与住宿、比赛日交通、总预算和失败预案。
预计 12 分钟形成三套方案，并附 PDF、预算表、日历与证据清单。
目前只研究，不会替你购买或提交资料。

[开始办理] [修改目标] [查看高级设置]
```

### 24.3 钦天监什么时候出现

只有钦天监能提供“会改变选择的增量”时才出现：

- 时间窗口即将关闭；
- 关键事实很可能在审批前失效；
- 存在明显二阶效应或不可逆路径；
- Base/Upside/Downside 的结果差异足以改变决定；
- 预测到了结算日，需要复盘。

用户也可主动说：“让钦天监反过来想”“看时机”“做最坏情景”“什么会让这个结论改变”。

钦天监卡片固定为：

```text
天时判断：现在适合锁定可退酒店，不适合购买不可退机票。
概率区间：签证在出发前完成的估计区间为 X–Y（不是保证）。
关键假设：递交日期、领区处理时间、材料完整度。
改变判断的信号：官方状态更新 / 票价超过上限 / 时间少于 N 天。
复核日期：YYYY-MM-DD。
```

钦天监不拥有封驳权和执行权，不宣称预言。它的每个预测都必须有假设、区间、时间窗和结算日。

变化提醒采用 `影响程度 × 可信度 × 新颖度` 门槛；默认进入每日摘要，只有安全事件、硬截止期和用户主动设置的关键价格阈值才即时提醒。

### 24.4 丞相与钦天监意见不同时

不做人格争吵，而展示一张“分歧台”：

```text
共识：目标可行，但时间紧。
丞相建议：方案 A，当前综合效用最高。
钦天监异议：若签证延迟超过 7 天，A 的不可退损失最大。
决定性未知：签证进度与机票退改价差。
最低成本验证：先锁可退房，48 小时后复核。
由你决定：[按 A 办] [先验证] [换保守方案]
```

### 24.5 语音交互

语音模式下，丞相负责自然听取、复述和讲解；钦天监只在被召唤或重大时机变化时插入一张短卡。用户随时可打断、切回文字、查看转写和删除录音。所有关键数字、来源和授权仍同时落在屏幕文字上。

## 25. 用户体验：让用户依赖价值，不依赖刺激

### 25.1 “一旨、一卡、一包”

- **一旨**：用户先说自然语言目标，不选 Agent；
- **一卡**：系统用一张计划卡完成理解校准；
- **一包**：最终交付一个可行动、可下载、可刷新、可追证的成果包。

这是普通模式。专家模式再展开依赖图、预算、模型、来源策略和逐条 Claim。

### 25.2 三层信息架构

| 层 | 用户第一眼看到什么 | 目标 |
| --- | --- | --- |
| 结果层 | 结论、推荐方案、预算、最大风险、下一步 | 30 秒做决定 |
| 推理层 | A/B/C 对比、假设、冲突、情景和为什么 | 5 分钟理解 |
| 证据层 | 来源、时间、原始快照、hash、完整事件与调试信息 | 专业复核与审计 |

默认收起深层内容，不能把“透明”误做成信息轰炸。

### 25.3 真进度，不演戏

进度由 canonical work package 状态驱动：已完成什么、正在等什么、哪项失败、是否局部重试、哪个事实会过期。禁止用虚假思考动画、编造“正在召集 100 位专家”或固定百分比制造能力感。

### 25.4 六个超预期时刻

1. 用户只说目标，系统自动给出成果清单，而不是追问一串表单；
2. 丞相主动发现一个用户没想到但会改变结果的约束；
3. 成果包自动附带预算表、日历、清单、Plan B 和证据包；
4. 改一个预算/日期，只重算受影响部分并显示差异；
5. 结论旁直接显示“什么会让它改变”和下次刷新时间；
6. 任务结束后量化“节省约 N 小时、避免约 N 风险、哪些成果已采用”。

### 25.5 伦理型持续使用

- 只在价格、政策、库存、风险或业务指标有实质变化时通知；
- 用户选择通知阈值、渠道、安静时段和自动停止日期；
- 复用偏好前展示来源和允许一键忘记；
- 不用虚假倒计时、恐惧文案、无限红点、人格依恋或“只有我懂你”诱导；
- 不把用户停留时长当北极星，改看成果采用率、真实任务成功率、节省时间和 30 天高价值复用率。

### 25.6 最小反馈动作

每份回奏只问四类可计算反馈：

```text
[已采用]
[事实有误]
[条件变了]
[没帮助]
```

“事实有误”进入御史错误样本池；“条件变了”使旧结论失效并局部刷新；“没帮助”只说明体验/匹配失败，不可自动当成事实标签；“已采用”也只有真实 outcome 回填后才算成功。

## 26. 扩展实施顺序与验收闸

### E0：冻结边界与名词

- 用户确认 “Humen” 的准确链接；
- 把 OpenClaw/Hermes/Humen/Hume 全部登记为 external capability，不设为事实源；
- 冻结 6 类记忆、4 个知识域和 AgentBudget。

退出条件：任何外部组件下线都不影响 canonical task、授权、案卷和核心回奏读取。

### E1：先做最小知识闭环

- 打通 `task → claim → evidence → memorial → archive → outcome`；
- SQL 控制面、对象原文、可重建检索投影；
- 当前任务证据与租户/用户/平台知识权限先过滤后召回；
- 给世界杯与商业任务建立黄金案例和硬负样本。

退出条件：每条正式结论可追到原始快照，A 租户永远检索不到 B 租户内容，删除可对账。

### E2：丞相/钦天监体验纵切

- 一句话听旨、单问题卡、计划卡、安静进度、三层回奏；
- 钦天监按条件触发，带区间、假设和复核日；
- 普通/专家双层界面和最小反馈动作。

退出条件：普通用户无需理解部门或 Agent 即完成黄金任务；专家能下钻到证据和事件。

### E3：OpenClaw Adapter V2

- 用 `WorkPackageV1/EvidencePacketV1` 取代纯字符串契约；
- 加入身份、健康、权限、预算、沙箱、证据和运行时变更记录；
- 先开放只读监测和公开研究。

退出条件：OpenClaw 超时/崩溃/恶意结果不会污染任务状态，不会重复执行，降级对用户可见。

### E4：Hermes 翰林沙箱

- 用历史只读任务生成技能候选；
- 建立 quarantine、黄金回放、对抗集、shadow/canary 与自动回滚；
- 禁止直写生产 registry 和知识库。

退出条件：关闭 Hermes 后系统仍可运行；未获人工批准的候选永远不可生产调用。

### E5：按准确产品做 Humen/Hume PoC

- 若是 Humen：先做 ICP/外联草稿与小批量、人工批准实验；
- 若是 Hume AI：先做可打断的丞相语音，不接交易授权；
- 若是人工审批层：只做通知与回跳，裁决仍写入 `EmperorDecision`。

退出条件：PoC 有真实用户价值增量，且没有新事实源、授权源或隐私旁路。

### 26.1 新增必测场景

1. OpenClaw 返回没有来源的漂亮答案，只能进入草稿，不能形成 LIVE_FACT；
2. OpenClaw 超时后 spawn 回退，结果明确标注 runtime 变化且不重复副作用；
3. Hermes 自动生成高权限 skill，必须被 quarantine 阻断；
4. 被用户删除的知识无法再从 vector/cache/eval dataset 检索或复原；
5. A 租户的成功案例不能出现在 B 租户的 prompt、检索或飞轮训练集中；
6. 模型自己给自己高分不能触发技能晋升；
7. 用户点“已采用”但没有 outcome，不能把任务标成真实成功；
8. 普通任务不会召集 71 个角色，超过 AgentBudget 时停止扩编；
9. 钦天监低置信预测必须显示区间、假设、结算日，不能阻断任务；
10. 语音推断到用户急躁时只能缩短回答，不能视为同意购买；
11. 丞相和钦天监分歧时显示决定性未知与最低成本验证；
12. Humen 批量外联在用户未批准、命中退订名单或超过频控时不得发送；
13. AI 输出回灌后引用自身或改写版本时，引用循环门必须阻断；
14. 高相似但语义矛盾的材料不得被判为 supporting evidence；
15. 同一反馈重放 100 次只保留一个有效事件，伪造他人 task/version 被拒绝；
16. 缺 tenant 的子线程、后台任务、CLI 与 cron 全部 fail-closed，不能落入全局/共享库；
17. 候选平均分提升但任一安全关键分群退化时不得晋升；
18. 删除后在线检索、缓存、评测集和新任务均为零命中，备份恢复不会复活 tombstone 数据；
19. 恶意 skill 的可变依赖、越权 hook、联网和读取密钥行为均在隔离区被阻断；
20. 没有足够、已结算且可信的 outcome 时，系统保持 `NO_DATA`，不得宣称飞轮已改善。

## 27. 扩展会审裁决

从产品角度，最强体验不是让用户看见更多 Agent，而是丞相替用户隐藏复杂度、钦天监只在关键时刻提供反事实、最终多交一份真正能用的成果。

从工程角度，最有价值的“技能洞察”是把角色 prompt 库降级为能力目录，把 `WorkPackage + Claim + Evidence + Artifact + Outcome` 升级为主协议。OpenClaw 与 Hermes 因此可以随时接入或替换，而不会夺走任务、知识和授权主权。

从安全角度，任何自我成长都必须是“候选生成 → 离线证据 → 人工晋升”，任何语音情绪都不能成为授权，任何外部 worker 都不能越过研究面触碰交易面。

最终建议保持不变：**首期不引入 LangGraph；日常默认 6 个逻辑角色；先做可信知识闭环和丞相体验，再升级 OpenClaw，最后在隔离区试 Hermes 与准确识别后的 Humen/Hume。**
