# 司补齐 · 集体方案(跨司骨架 + 兵部获客 + 刑部应用)2026-06-28

> 核心:**同一副骨架 × 不同本命算法**。加一个司 = 接一个真数据底座 + 写一个本命引擎,不重造轮子。

## 〇、跨司骨架(所有司复用,已大半建好)
```
真数据底座(库)  →  dept-agent引擎(LLM+接地校验,已有)  →  本命算法(各司不同)
     ↑                                                          ↓
reference-class(史馆base rate·先外后内,已建)  ←  交付物(可下载,已建)  ←  人工门(L0-L4,已有)
```
共用件已就绪:`dept-agent` / `reference-class` / `deliverable` / 证据管线 / `human-approval-gate`。
**每加一个司,只需:① 接真数据底座 ② 写"本命算法" ③ 配 role prompt。**

## 一、三司本命对照(别都做成户部)
| 司 | 领域 | 本命算法 | 真数据底座 |
|---|---|---|---|
| 户部 | 财务 | **定量**(NPV/IRR/回收期) | 采购价库(H盘526条真台账) |
| 兵部 | 销售/竞争 | **概率+反身性**(成交概率/竞品胜率/对手反制) | 线索库(上传+公开工商+锦衣卫核实) |
| 刑部 | 合规/风控 | **规则匹配+风险评分**(条款扫描/缺证/合规) | 法规库+制度库+史馆判例 |
> 财务天生定量、销售天生博弈、合规天生规则——**各走本命,强行统一=假精确**。

## 二、兵部 · 获客方式(合法-by-design,灵魂)
```
锦衣卫公开情报(招标/扩张/痛点)
 → 兵部AI备战:ICP评分 + 成交概率(reference-class史馆base rate) + 草拟开场白 + 找钩子
   ★只草拟·不抓个人数据·结构上无auto-send(prospect-qualify已这么设计)
 → 人扳机:人审+点发(L0-L4门,合法渠道)
 → 成交回填史馆 → reference-class让成交预测越来越准(飞轮)
```
三差距:① 真线索库(常驻,不现传) ② 概率博弈引擎(非NPV) ③ 获客飞轮(AI做苦活·人扳机合规)。
**合法不靠自觉,靠结构**:无抓取选项、无自动发。

## 三、刑部 · 应用(比兵部更顺:结构化、无外联雷)
- **真数据底座**:法规库 + 内部制度库 + 史馆判例(法规公开合法;合同客户端解析按混合架构,原文不上云)
- **本命引擎**:条款风险扫描(违约金/独家/无限责任/自动续约陷阱)+ 缺证检查 + 合规评分
- **行动**:合规审查报告 + 一票否决高风险(已有 legal gate)+ reference-class:"你历史上这类条款踩坑 N 次"

## 四、执行方案(谁做什么·序)
| 序 | 做什么 | 归属 | 撞车? |
|---|---|---|---|
| **A(现在)** | **刑部本命:条款风险扫描引擎**(纯函数+测试) | 架构方(我) | ✅ 独立不撞 |
| B | 刑部接 reference-class(踩坑 base rate)+ 法规库底座 | 我/协调 | 低 |
| C | 兵部本命:成交概率引擎(接 reference-class) | **协调主工头**(他地盘) | 中 |
| D | 兵部线索库底座(三合法源沉淀) | 主工头 | 中 |
| E | 兵部获客飞轮(AI备战→人扳机) | 主工头(按其第4步专门设计) | 中 |

**原则**:刑部相对独立,架构方先建(A/B);兵部在主工头地盘,设计给他、协调实施(C/D/E)。共用骨架谁都别重造。

## 五、红线
- 兵部获客:不抓个人数据、不自动发、人扳机(PIPL/铁律9)。
- 刑部:合同原文客户端解析不上云(混合架构),只上脱敏结论。
- 三司本命各异,禁强行统一成定量。
- reference-class 样本<5 只给类比不给假概率(对成交/踩坑预测同样适用)。
