## 1. 正确定义

产品主体不是“铭硕项目”，也不是“朝堂模拟器游戏”。

产品主体是 **先知和导师（Oracle & Mentor）**：帮助用户用 AI agent 解决实际问题的产品。

当前朝堂 OS / 三省六部 / 蜂群体系，是这个产品的表达方式和执行架构：

```text
用户真实问题
  -> 先知：判断现在最该问什么、做什么、为什么
  -> 导师：把问题拆成可执行路径、预算、风险、验收
  -> 三省六部：治理、会审、裁断、归档
  -> 客户自配蜂群：按行业和业务场景执行
  -> 史馆：沉淀证据、复盘、下一次建议
```

一句话：

```text
先知和导师 = AI agent 时代的实战问题解决操作系统。
```

## 2. 铭硕的角色

铭硕只是第一个客户和最佳实践样板，不是产品主业。

铭硕电池 8 蜂群的正确位置是 reference implementation：

- 证明“客户自配蜂群”可以落到真实行业问题。
- 证明三省六部不是古风 UI，而是治理和执行框架。
- 形成可复制样板：从电池售后/产品/市场/项目管理，复制到下一个客户的业务蜂群。

因此不存在“铭硕 vs 朝堂 OS”的二选一。

正确关系是：

```text
先知和导师（产品）
  -> 朝堂 OS（三省六部治理框架）
    -> 铭硕电池 8 蜂群（第一个客户样板）
```

## 3. 需要重构的旧判断

旧判断：“6-04 聚焦铭硕。”

在本决策下应重构为：

```text
先聚焦铭硕这个真实样板，把一个客户问题做透；
但产品叙事、架构边界、销售对象，必须服务“先知和导师”这个通用产品。
```

也就是：

- 不把铭硕做成定制外包项目。
- 不把朝堂 OS 做成只适配铭硕的内部系统。
- 不用没有真实客户的抽象平台推翻铭硕样板。
- 用铭硕证明可复制方法论，再抽象为行业模板和客户自配蜂群。

## 4. 北极星不变，但主语改清楚

沿用 `docs/NORTHSTAR_REAL_LOOP_V1_PRD.md` 的真闭环原则：

```text
让 1 个真实用户，用先知和导师真做成 1 件实际问题，并愿意说“这帮我了”。
```

当前最小样板可以继续用铭硕或老板的真实经营决策，但验收话术要避免写成“铭硕专用系统”。

验收标准：

- 用户提出一个真实问题。
- 系统能指出关键前提、缺口、风险和下一步。
- 三省六部/蜂群能产出可执行任务或奏折。
- 用户能采纳、打回、追问或派遣。
- 史馆留下证据链和复盘，下一次建议能引用。

## 5. 接下来会审方式

后续产品会审按这个框架进行：

1. 先问：这是“先知和导师”的通用能力，还是铭硕样板里的行业配置？
2. 再问：它能不能帮助用户解决一个实际问题，而不是增加页面？
3. 再问：它是否有证据、成本、风险、验收和复盘？
4. 最后问：这个能力能否从铭硕复制到第二个客户？

如果不能回答第 2 点，先不做。

## 6. 最小有用交付

当前最小交付不是再铺部门页，而是做一条可复用样板链路：

```text
用户真实问题
  -> 先知识别问题类型和关键缺口
  -> 导师生成行动路径
  -> 三省六部会审
  -> 蜂群执行/产出
  -> 史馆归档
  -> 下一次引用
```

铭硕样板可作为第一条链路：

```text
铭硕真实问题
  -> 电池/财务/市场/项目上下文
  -> 三省六部会审
  -> 8 蜂群分工执行
  -> 形成客户可读的最佳实践案例
```

但产品命名、文档、演示和销售材料必须回到：

```text
先知和导师：帮用户用 AI agent 解决实际问题。
```
