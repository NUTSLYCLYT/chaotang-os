## 一句话定位

军机处不是报表页，也不是纯展示页。军机处是朝堂 OS 的 AI 指挥塔：把一条圣旨或建设任务转成可执行、可观察、可追责、可归档的行动。

用户进来后只需要回答四个问题：

1. 现在处理哪件事？
2. Agent 和部门正在做什么？
3. 卡在哪里，谁来处理？
4. 我现在应该点哪一个动作？

## 用户与成功标准

| 项目 | 定义 |
| --- | --- |
| 核心用户 | 非技术用户、产品负责人、项目总管、需要看懂 AI 工作流的人 |
| 次级用户 | 开发者、审核者、运营者、需要追溯证据和日志的人 |
| 情绪钩子 | 一进来像进入最高指挥室，看到中间沙盘和正在运转的决策系统 |
| 价值钩子 | 不读日志也能知道当前任务、执行状态、阻塞、下一步 |
| P0 成功标准 | 3 秒内看懂当前任务和下一步；30 秒内能进入证据、工部、史馆或执行层 |
| P1 成功标准 | 真任务可显示实时 Agent 路径、阻塞原因、审批记录和归档状态 |

## 面板职责边界

### 1. 圣旨原文

职责：只回答“原始输入是什么”。

不应该承担：

- 不展示执行状态。
- 不展示大段解释。
- 不塞多个历史任务。

下一步优化：

- 真任务时显示来源：上书房、大殿、工部、API。
- 增加“复制原文”小按钮。
- 长文超过三行时折叠，保持画面干净。

### 2. Agent 工作图

职责：只回答“谁在工作，卡在哪里”。

四条主线：

| 线 | 含义 | 小白文案 | 必备状态 |
| --- | --- | --- | --- |
| 待命 | 等待派发或等待下游 | 还没开始 | count、队列名 |
| 执行中 | Agent/部门正在跑 | 正在处理 | runId、开始时间、进度 |
| 阻塞 | 需要人或系统处理 | 需要你处理 | blocker reason、owner、deadline |
| 已交付 | 有结果可看 | 已有结果 | artifact、evidence、report |

下一步优化：

- 接入真实 SSE 事件，而不是 demo 进度。
- 每条 lane 可点击打开 Agent run 详情。
- 阻塞必须显示 owner 和建议动作，不能只显示数字。

### 3. Quick Review 军机接单

职责：只回答“当前最重要任务是什么，下一步点哪里”。

当前合理做法：

- 默认只展示最新一条任务。
- 把完整证据放到详情抽屉。
- 只保留三个主动作：复核、补证、复盘。

不应该承担：

- 不做完整任务表格。
- 不展示所有部门的所有数据。
- 不把证据链全部堆在第一屏。

下一步优化：

- 增加“为什么是这条任务”的排序理由。
- 增加风险标签：缺证据、缺 owner、缺预算、缺验收标准。
- 与工部台账统一状态机。

### 4. 任务详情抽屉

职责：只回答“证据和追责在哪里”。

必须包含：

- 任务编号。
- 状态和评分。
- 下一步建议。
- 证据列表。
- 推荐会审部门。
- 最近审计记录。
- 史馆/工部入口。

不应该承担：

- 不替代主页面。
- 不自动打开。
- 不挡住用户的默认判断路径。

下一步优化：

- 补充时间戳格式化。
- 审计记录显示 from/to 状态。
- 增加“复制任务上下文”按钮，方便发给 Codex/Claude Code。

### 5. 大臣会审

职责：只回答“多方意见倾向是什么”。

当前 P0 展示：

- 支持 3。
- 谨慎 2。
- 反对 0。
- 一句结论。

未来 P1 展示：

- 主要分歧点。
- 反对理由。
- 置信度。
- 证据缺口。

不应该承担：

- 不展示长名单。
- 不把会审变成聊天记录。
- 不让用户在第一屏读长文。

### 6. 最终奏折

职责：只回答“建议采用什么方案，为什么，现在做什么”。

P0 结构：

| 区块 | 内容 |
| --- | --- |
| 推荐 | 稳中求进 |
| 方案 | 先做最小可验收路径 |
| 理由 | 收益、风险、证据 |
| 现在 | 呈报、退回、进入执行 |

下一步优化：

- 真任务时绑定最终 report artifact。
- 呈报按钮需要权限、审计、确认弹窗。
- 如果证据不足，按钮应变成“退回补证”，不能假装可批。

### 7. 执行路径

职责：只回答“从决策到落地经过哪些阶段”。

P0 可保持静态，用于情绪和结构理解。

P1 必须真实化：

- 每阶段 owner。
- 每阶段开始/截止时间。
- 当前阻塞。
- 对应部门入口。
- 验收证据。

### 8. 任务总览胶囊

职责：全局只回答“当前模式、当前任务、当前阻塞、下一步 CTA”。

设计原则：

- 永远可见。
- 不遮中间沙盘。
- CTA 只有一个主按钮。
- DEMO/LIVE/MIXED 必须清楚，避免把演示当真实能力。

### 9. 工部建设案草稿

职责：把“建议”变成“可下旨任务”。

价值：

- 连接上书房建议、工部建设、户部预算、史馆归档。
- 是从想法到任务的关键入口。

下一步优化：

- 下旨前显示验收命令和回滚口径。
- 下旨前检测是否已有重复建设案。
- 增加预算/风险未齐时的提示。

### 10. 作战流浮板

职责：让真任务运行过程可见。

必须展示：

- 拆解阶段。
- Agent/部门开始与结束。
- 错误和阻塞。
- 产物和证据。
- 最终 report。

下一步优化：

- 与 Agent 工作图使用同一份事件源。
- 所有事件进入审计/史馆。
- 错误必须有 owner 和恢复建议。

## 信息层级

第一眼只看：

1. 中间沙盘和军机处标题。
2. 当前任务。
3. Agent 工作图。
4. 最终推荐。
5. 下一步按钮。

第二眼再看：

1. 圣旨原文。
2. 大臣会审。
3. Quick Review 评分。
4. 执行路径。

需要追责时才看：

1. 任务详情抽屉。
2. 证据。
3. 审计记录。
4. 史馆/工部入口。

## 状态模型

| 状态 | 页面表现 | 用户动作 |
| --- | --- | --- |
| DEMO | 明确显示 DEMO，使用演示数据 | 回上书房立真案 |
| MIXED | 有 taskId 但部分数据未回写 | 等待、查看执行层 |
| LIVE | 后端真实任务和事件流已连接 | 处理阻塞、查看证据 |
| BLOCKED | 有阻塞原因和 owner | 补证、改派、重试 |
| DONE | 已交付 report/evidence | 去史馆复盘 |
| ARCHIVED | 已入史馆 | 查看复盘和学习沉淀 |

## 当前缺口

| 缺口 | 风险 | 建议 |
| --- | --- | --- |
| Agent 工作图仍有 demo 数据 | 用户可能误以为是真实 Agent 状态 | P0.5 接 SSE/任务 API |
| 大臣会审是静态摘要 | 会审价值还未真实闭环 | P1 接 council review artifact |
| 最终奏折是静态方案 | 呈报按钮暂时像装饰 | P1 接最终 report 和权限闸 |
| 执行路径是固定时间线 | 无法反映真实项目阶段 | P1 接 milestone 数据 |
| 401 请求仍存在 | 运行环境会产生噪音 | 单独修登录/API 轮询权限 |

## 上线口径

P0 可以上线为“军机处指挥界面雏形”，但必须明确：

- Agent 工作图含 demo 边界。
- 真任务由 `taskId` 和 `BattleStream` 承接。
- 决策按钮还不是完整审批系统。
- 证据和归档入口已经可作为工部/史馆联动基础。

P1 才能宣称为“真实 AI 指挥塔”：

- Agent lane 接真实事件。
- 会审接真实多角色评审。
- 奏折接真实 report。
- 阻塞接 owner、恢复建议、审计。
- 所有关键动作写入史馆。

## 天才设计

把军机处从“页面”升级成“任务指挥协议”：

每个面板都必须输出同一种 `CommandSignal`：

```ts
type CommandSignal = {
  taskId: string;
  panel: 'decree' | 'agent' | 'review' | 'memorial' | 'path' | 'ledger';
  status: 'demo' | 'live' | 'blocked' | 'done' | 'archived';
  owner?: string;
  blocker?: string;
  nextAction: {
    label: string;
    href?: string;
    action?: string;
    requiresConfirm?: boolean;
  };
  evidenceRefs: string[];
  updatedAt: string;
};
```

这样前端、后端、史馆、工部、Claude/Codex 工作流都能围绕同一协议协作。以后不是每个面板各自写死文案，而是每个面板都向用户发出一个清晰信号：现在发生了什么，谁负责，下一步是什么。
