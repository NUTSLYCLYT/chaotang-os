## 1. 产品概述

### 1.1 产品一句话

先知和导师是一套面向老板和业务负责人的 AI 决策操作系统: 用户提出真实经营问题，系统帮助识别关键缺口、组织多角色会审、生成可裁决方案，并把结果沉淀为下一次判断的经验。

### 1.2 产品不是

- 不是古风角色扮演游戏。
- 不是单纯的 AI 聊天窗口。
- 不是只服务铭硕电池的定制系统。
- 不是展示很多部门页面的导航站。

### 1.3 产品是

```text
真实问题输入
-> 系统判断该问什么、谁来参与、缺什么证据
-> 多角色/蜂群会审
-> 输出一份可读、可裁、可追问、可归档的决策报告
-> 用户采纳、打回或追问
-> 系统沉淀证据和复盘
-> 下一次建议更准确
```

## 2. 背景与问题

### 2.1 背景

当前系统已有前端朝堂 OS 和后端 jiqun_ai 蜂群能力，包含上书房、军机处、史馆、三省六部、业务蜂群、运行记录和任务持久化。

但产品当前的主要风险是: 页面很多、概念很多，用户不一定知道“我现在该做什么”，也难以判断哪些能力是真实可用，哪些是演示或 fallback。

### 2.2 用户痛点

| 痛点 | 说明 |
|---|---|
| 决策入口不清 | 老板不想管理 agent、部门、蜂群，只想知道今天该判断什么 |
| AI 输出难以信任 | 不知道结论来自真实模型、样板数据还是静态文案 |
| 缺少裁决动作 | AI 给了建议，但用户无法明确采纳、打回、追问 |
| 缺少证据链 | 决策背后的依据、风险、缺口没有被结构化保留 |
| 经验无法复利 | 上一次决策结果没有影响下一次建议 |

### 2.3 产品机会

把“AI 聊天”升级为“AI 决策闭环”:

- 用户只看到一个清晰入口和一份结果。
- 系统把复杂的 agent/蜂群编排隐藏在后台。
- 结果必须带来源、证据、风险、下一步。
- 用户每次裁决都沉淀为下一次判断的燃料。

## 3. 北极星目标

### 3.1 北极星

让 1 个真实老板，用朝堂 OS 真做成 1 件经营决策，并愿意说“这帮我了”。

### 3.2 MVP 目标

先跑通一条最小真闭环:

```text
上书房提出真实问题
-> 军机处组织会审
-> 输出圣旨/奏折
-> 用户裁决
-> 史馆归档
-> 后续可引用
```

### 3.3 本期不追求

- 不追求所有部门页完整上线。
- 不追求所有蜂群都前台可见。
- 不追求复杂权限系统一次到位。
- 不追求多行业同时展开。

## 4. 目标用户

### 4.1 核心用户

| 用户 | 典型诉求 | 成功体验 |
|---|---|---|
| 老板/CEO | 快速判断一个经营问题是否推进 | 3 分钟内读到一份有证据、有风险、有下一步的决策建议 |
| 业务负责人 | 把模糊想法变成可执行任务 | 系统能自动拆出责任部门、任务状态和阻塞 |
| 项目负责人 | 跟踪任务推进和结论 | 能看到任务从输入到报告再到归档的状态 |
| 产品/运营团队 | 复盘和复用经验 | 能从史馆找到旧案、结论和下次建议 |

### 4.2 第一批目标用户

优先服务一个真实业务老板或经营负责人。当前铭硕电池业务可作为首个 reference implementation，但产品表达必须是通用的“先知和导师”。

## 5. 典型场景

### 场景 A: 判断一个合作机会是否推进

用户输入:

```text
请判断厦门 AI 公司合作是否值得推进，重点看投入边界、股权风险、招商话术和 90 天执行路径。
```

系统输出:

- 当前建议: 准奏、补证、复核或驳回。
- 户部视角: 投入、ROI、现金风险。
- 刑部视角: 股权、合同、合规风险。
- 礼部视角: 对外表达和招商话术。
- 90 天行动路径。
- 需要老板裁决的问题。

### 场景 B: 判断储能项目是否推进

用户输入:

```text
判断 100MWh 冷库储能项目是否推进。
```

系统输出:

- 是否值得进入方案阶段。
- 还缺哪些报价、交期、BOM、客户承诺证据。
- 是否需要人工签字。
- 是否进入史馆归档旧案对比。

### 场景 C: 复盘一次被打回的决策

用户输入:

```text
上次这个报价为什么被打回？这次应该怎么避免？
```

系统输出:

- 上次被打回原因。
- 触发条件。
- 本次需要补齐的证据。
- 建议的最小补救动作。

## 6. 产品范围

### 6.1 本期 In Scope

| 模块 | 范围 |
|---|---|
| 上书房 | 作为主入口，展示今日建议、待裁决问题、发起下旨 |
| 军机处 | 接收用户问题，组织会审，生成结果 |
| 圣旨/奏折 | 统一结果形态，包含结论、分奏、证据、风险、下一步、质门 |
| 用户裁决 | 支持采纳、打回、追问 |
| 史馆 | 保存决策结果、证据、复盘入口 |
| 真实性标识 | 明确展示 LIVE、MIXED、FALLBACK、DEMO |
| 任务持久化 | 用户发起的问题和结果刷新后仍可查询 |

### 6.2 本期 Out of Scope

| 不做 | 原因 |
|---|---|
| 扩展所有部门完整页面 | 会稀释第一条真闭环 |
| 让用户手动选择 18 个蜂群 | 用户不该理解后台复杂度 |
| 自动替用户做不可逆决策 | 高风险决策必须人工确认 |
| 未标注来源的 mock 展示 | 会破坏信任 |
| 多客户多行业模板同时展开 | 先证明一个样板可用 |

## 7. 用户旅程

### 7.1 首次使用

1. 用户进入上书房。
2. 系统展示今日建议或待处理经营问题。
3. 用户选择一个问题或输入自己的问题。
4. 系统把问题整理为可执行旨意。
5. 用户确认发起。

### 7.2 决策生成

1. 军机处接收旨意。
2. 系统判断需要哪些视角参与。
3. 后台调用对应模型/蜂群/部门。
4. 系统合成一份圣旨/奏折。
5. 输出包含来源、证据、风险和下一步。

### 7.3 用户裁决

1. 用户阅读结果。
2. 用户选择采纳、打回或继续追问。
3. 若是高风险事项，系统提示必须人工确认。
4. 裁决结果写入记录。

### 7.4 归档与复利

1. 系统将本次问题、结果、证据和裁决归档到史馆。
2. 后续同类问题出现时，系统提示历史镜鉴。
3. 用户能看到“这次建议为什么和上次不同”。

## 8. 主要交互流程

### 8.1 交互总览

产品主流程必须围绕一条决策闭环展开:

```text
进入上书房
-> 看到一号问题或主动输入问题
-> 丞相拟旨
-> 用户确认发起
-> 军机处会审
-> 生成圣旨/奏折
-> 用户裁决
-> 史馆归档
-> 下次同类问题引用旧案
```

用户在任何阶段都应该清楚三件事:

- 当前系统正在做什么。
- 还缺什么信息或需要谁确认。
- 用户下一步唯一最重要的动作是什么。

### 8.2 流程一: 进入上书房并选择一号问题

目标: 让用户进入产品后 10 秒内知道今天最值得处理的问题。

| 步骤 | 用户动作 | 系统反馈 | 页面产出 |
|---|---|---|---|
| 1 | 用户进入上书房 | 展示今日一号问题、待裁决事项、历史未完成任务 | 上书房首页 |
| 2 | 用户浏览推荐问题 | 标注问题来源、紧急程度、建议处理原因 | 今日建议卡片 |
| 3 | 用户点击“处理” | 进入问题确认区 | 待拟旨问题 |
| 4 | 用户不接受推荐 | 可直接输入新的经营问题 | 自定义问题输入框 |

关键规则:

- 首页只允许一个最突出的主动作，避免用户在多个入口之间犹豫。
- 推荐问题必须说明“为什么现在处理”，不能只给标题。
- 如果当前没有真实建议，必须显示“暂无真实建议”或“样板建议”，不能伪装成真实经营洞察。

### 8.3 流程二: 一句话下旨与丞相拟旨

目标: 把用户的模糊表达整理成系统可执行、用户可确认的决策任务。

| 步骤 | 用户动作 | 系统反馈 | 页面产出 |
|---|---|---|---|
| 1 | 用户输入一句话问题 | 系统保留用户原文 | 原始问题 |
| 2 | 用户点击发起 | 系统生成拟旨版本 | 拟旨卡片 |
| 3 | 用户查看拟旨 | 系统展示问题类型、目标、约束、期望输出 | 可执行任务摘要 |
| 4 | 用户修改或确认 | 系统更新拟旨并等待最终确认 | 确认发起按钮 |
| 5 | 用户确认发起 | 任务进入军机处会审 | 任务生成成功提示 |

拟旨内容必须包含:

- 要判断的问题。
- 用户希望得到的结果类型，例如准奏、补证、复核、驳回。
- 已知信息。
- 明显缺口。
- 需要参与的业务视角。

异常分支:

- 如果问题过短或不可判断，系统要求用户补充背景。
- 如果问题涉及高风险事项，系统提前提示后续可能需要人工确认。
- 如果用户取消，草稿保留在当前页面，不自动归档为正式任务。

### 8.4 流程三: 军机处会审与过程反馈

目标: 让用户知道问题正在被处理，并理解系统为什么需要时间。

| 步骤 | 用户动作 | 系统反馈 | 页面产出 |
|---|---|---|---|
| 1 | 用户确认发起后等待 | 展示任务状态为“会审中” | 会审进度区 |
| 2 | 用户查看会审过程 | 展示参与视角，例如财务、销售、法务、交付、风险 | 参审视角列表 |
| 3 | 系统发现缺口 | 提示缺少的关键证据 | 补证提示 |
| 4 | 系统发现分歧 | 展示分歧双方和分歧原因 | 冲突摘要 |
| 5 | 会审完成 | 生成圣旨/奏折 | 结果页入口 |

过程反馈要求:

- 不展示后台复杂编排细节，只展示用户能理解的业务视角。
- 预计耗时超过 10 秒时，必须有明确的进行中状态。
- 预计耗时较长时，允许用户离开页面，任务完成后可从任务列表或史馆找回。

### 8.5 流程四: 阅读圣旨/奏折并做裁决

目标: 让用户从“看 AI 输出”变成“做经营裁决”。

| 步骤 | 用户动作 | 系统反馈 | 页面产出 |
|---|---|---|---|
| 1 | 用户打开结果 | 首屏展示圣裁、可信度、下一步主动作 | 圣旨/奏折头部 |
| 2 | 用户阅读分奏 | 展示各视角意见和关键证据 | 分奏区 |
| 3 | 用户查看风险 | 展示风险、缺口和不可逆事项 | 风险区 |
| 4 | 用户选择裁决 | 可选采纳、补证、复核、驳回、追问 | 裁决操作区 |
| 5 | 用户提交裁决 | 系统记录裁决并提示后续动作 | 裁决结果 |

裁决按钮规则:

- “采纳”: 用户认可建议，进入归档和执行跟踪。
- “补证”: 用户认为信息不足，系统生成补证清单。
- “复核”: 用户要求更深一层会审。
- “驳回”: 用户否定当前建议，必须记录驳回原因。
- “追问”: 用户围绕当前结果继续提问，不创建完全无关的新任务。

### 8.6 流程五: 打回、补证与追问

目标: 让一次不满意的结果仍然能推动决策前进，而不是结束对话。

| 场景 | 用户动作 | 系统反馈 | 后续状态 |
|---|---|---|---|
| 结果不够具体 | 点击“追问”并输入问题 | 系统基于当前奏折继续回答 | 追问中 |
| 证据不足 | 点击“补证” | 系统列出缺少的材料和负责人建议 | 待补证 |
| 结论有误 | 点击“驳回”并填写原因 | 系统保存驳回原因并进入复盘 | 已驳回 |
| 需要更严谨 | 点击“复核” | 系统提示预计耗时并重新会审 | 复核中 |

关键规则:

- 打回必须捕捉原因，否则无法形成产品复利。
- 追问必须继承当前任务上下文，避免用户重复输入背景。
- 补证结果回来后，用户应能从原任务继续，而不是重新发起新任务。

### 8.7 流程六: 高风险事项人工确认

目标: 防止系统替用户完成不可逆决策。

触发条件包括:

- 涉及股权、合同、法律责任、重大付款或不可逆承诺。
- 涉及对外正式报价、客户承诺或供应商锁定。
- 系统证据不足但用户尝试直接采纳。
- 多个关键视角存在明显冲突。

| 步骤 | 用户动作 | 系统反馈 | 页面产出 |
|---|---|---|---|
| 1 | 用户尝试采纳高风险建议 | 系统弹出人工确认提示 | 风险确认弹窗 |
| 2 | 用户查看确认项 | 系统列出需要确认的风险和缺口 | 确认清单 |
| 3 | 用户选择继续或取消 | 继续则要求填写确认说明，取消则回到结果页 | 人工确认记录 |
| 4 | 用户完成确认 | 系统标记“已人工确认”并归档 | 可追溯裁决记录 |

验收标准:

- 高风险事项不能被一键静默采纳。
- 人工确认记录必须和最终裁决一起保存。
- 后续复盘时能看到当时确认了什么、忽略了什么风险。

### 8.8 流程七: 史馆归档与历史镜鉴

目标: 让每一次决策成为下一次判断的资产。

| 步骤 | 用户动作 | 系统反馈 | 页面产出 |
|---|---|---|---|
| 1 | 用户完成裁决 | 系统提示已进入归档 | 归档状态 |
| 2 | 用户进入史馆 | 展示任务、结论、裁决、来源、时间 | 归档详情 |
| 3 | 用户补充复盘 | 可填写实际结果、教训、后续动作 | 复盘记录 |
| 4 | 用户再次提出类似问题 | 系统提示可参考旧案 | 历史镜鉴 |
| 5 | 用户查看差异 | 系统说明本次建议与旧案差异 | 对比摘要 |

归档必须保存:

- 原始问题。
- 拟旨后的任务。
- 最终奏折。
- 用户裁决。
- 来源标识。
- 人工确认记录。
- 复盘结论。

### 8.9 流程八: 异常、降级与恢复

目标: 即使依赖不可用，也要让用户知道发生了什么，并保护信任。

| 异常场景 | 系统表现 | 用户可做动作 |
|---|---|---|
| 生成时间过长 | 显示任务仍在处理中，并允许稍后查看 | 返回上书房或查看任务列表 |
| 真实能力不可用 | 明确标注 FALLBACK 或 DEMO | 等待恢复、继续样板查看、取消任务 |
| 结果生成失败 | 展示失败原因和重试入口 | 重试、修改问题、保存草稿 |
| 页面刷新 | 恢复任务状态和已有结果 | 继续查看或裁决 |
| 证据不足 | 不给确定性结论，提示补证 | 上传或补充关键信息 |

信任底线:

- 降级可以发生，但必须明示。
- 失败可以发生，但不能丢任务。
- 缺证可以继续推进，但不能包装成确定结论。

### 8.10 主状态模型

任务在产品层面的状态应保持简单:

| 状态 | 用户理解 | 可用操作 |
|---|---|---|
| 草稿 | 问题还没正式发起 | 修改、取消、确认发起 |
| 待确认 | 系统已拟旨，等待用户确认 | 修改、确认发起 |
| 会审中 | 系统正在生成建议 | 查看进度、离开页面 |
| 待裁决 | 已生成奏折，等待用户决定 | 采纳、补证、复核、驳回、追问 |
| 待补证 | 需要用户补充材料 | 补充信息、取消、继续追问 |
| 复核中 | 用户要求更深会审 | 查看进度、等待结果 |
| 已采纳 | 用户接受建议 | 归档、复盘、执行跟踪 |
| 已驳回 | 用户否定建议 | 记录原因、复盘 |
| 已归档 | 任务进入史馆 | 查看、复盘、作为旧案引用 |

## 9. 核心页面需求

### 9.1 上书房

定位: 最终用户主入口。

核心功能:

| 功能 | 优先级 | 说明 |
|---|---|---|
| 今日经营建议 | P0 | 展示最值得处理的一号问题 |
| 一句话下旨 | P0 | 用户输入真实问题 |
| 丞相拟旨 | P0 | 把模糊问题改写为可执行任务 |
| 真实性标识 | P0 | 展示 LIVE/MIXED/FALLBACK/DEMO |
| 历史引用 | P1 | 引用史馆旧案作为建议依据 |

验收标准:

- 用户 10 秒内知道可以做什么。
- 页面只突出一个主动作。
- 发起后能看到生成中的状态或结果。
- 结果刷新后不丢失。

### 9.2 军机处

定位: 决策执行与会审中心。

核心功能:

| 功能 | 优先级 | 说明 |
|---|---|---|
| 接收上书房任务 | P0 | 从上书房进入任务 |
| 会审过程展示 | P0 | 展示哪些视角参与 |
| 阻塞提示 | P0 | 告诉用户缺什么证据 |
| 冲突展示 | P1 | 展示不同部门分歧 |
| 生成奏折 | P0 | 输出可裁决报告 |

验收标准:

- 用户能看懂任务正在被谁处理。
- 出现冲突时不强行平均成一个结论。
- 输出结果有明确下一步。

### 9.3 圣旨/奏折

定位: 产品最核心输出物。

必须包含:

| 字段 | 说明 |
|---|---|
| 圣裁 | 准奏、补证、复核、驳回 |
| 分奏 | 各角色/部门意见 |
| 证据 | 来源、时间、材料、假设 |
| 风险 | 不可逆风险、缺证风险、成本风险 |
| 后令 | 下一步唯一主动作 |
| 质门 | 是否通过、是否需人工确认 |
| 来源 | LIVE/MIXED/FALLBACK/DEMO |

验收标准:

- 非专业用户能读懂。
- 每个结论都能看到依据或缺口。
- 高风险事项明确显示“需人工确认”。

### 9.4 史馆

定位: 证据、复盘和经验沉淀。

核心功能:

| 功能 | 优先级 | 说明 |
|---|---|---|
| 归档任务结果 | P0 | 保存输入、输出、裁决 |
| 查看证据链 | P0 | 能看到结果从哪里来 |
| 保存复盘 | P1 | 成功/失败/教训 |
| 相似旧案召回 | P1 | 后续同类问题可引用 |
| 标注合成记录 | P0 | synthetic/fallback 不伪装成真实复盘 |

验收标准:

- 用户能从一次结果跳到归档。
- 归档记录包含任务、结果、来源、时间。
- fallback 或 synthetic 记录有明确标识。

## 11. 真实性与信任规则

### 11.1 结果来源展示

所有关键结果必须展示来源:

| 标签 | 用户解释 |
|---|---|
| LIVE | 真模型或真后端运行 |
| LIVE_SWARM | 后端真实蜂群运行 |
| MIXED | 有真实链路，但包含 dry_run 或 fallback |
| FALLBACK | 当前依赖不可用，系统使用兜底 |
| DEMO | 样板展示，不作为真实判断依据 |

### 11.2 禁止行为

- 禁止把 DEMO 写成 LIVE。
- 禁止把 fallback 结果作为最终决策依据。
- 禁止隐藏高风险结果的人工确认要求。
- 禁止在没有证据时生成“确定性”结论。
- 禁止让用户理解后台 18 个蜂群才能使用产品。

## 12. 指标体系

### 12.1 北极星指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 有用决策数 | 用户明确表示可用或采纳的决策数 | MVP 阶段先达成 1 个 |

### 12.2 过程指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 首次行动时间 | 用户进入到发起第一道旨的时间 | 小于 60 秒 |
| 报告生成时间 | 发起到可读报告出现 | dry_run 小于 5 秒，live 小于 3 分钟 |
| 结果可读率 | 用户无需解释即可理解结果 | 人工访谈确认 |
| 裁决完成率 | 报告生成后用户采纳/打回/追问的比例 | 持续提升 |
| 归档完成率 | 有结果的任务进入史馆的比例 | P0 达 80% 以上 |
| source 标注率 | 关键结果有来源标签的比例 | 100% |

### 12.3 质量指标

| 指标 | 定义 |
|---|---|
| 缺证阻断率 | 因证据不足被要求补证的比例 |
| 人工确认触发率 | 高风险事项触发 human signoff 的比例 |
| fallback 暴露率 | fallback 被明确标注的比例 |
| 复盘复用率 | 后续报告引用历史归档的比例 |

## 13. MVP 交付定义

MVP 成立条件:

```text
一个真实用户
提出一个真实经营问题
系统生成一份带来源、证据、风险、下一步和质门的报告
用户完成一次采纳/打回/追问
系统保存任务和结果
史馆能看到归档或复盘入口
```

MVP 不以页面数量验收，以一条可复用闭环验收。

## 14. 里程碑计划

## 15. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 页面太多导致主线不清 | 用户不知道该点哪里 | 主导航只突出上书房、军机处、史馆 |
| AI 结果被误认为真实 | 用户信任受损 | 强制 source 标签 |
| live 深度参审耗时长 | 用户以为卡死 | 明确异步进度和耗时预期 |
| 后端依赖不稳定 | 报告生成失败 | fallback 诚实标注，不作为最终决策 |
| 决策无法复利 | 产品退化成聊天 | 裁决和归档作为 P0/P1 闭环要求 |
| 高风险自动通过 | 业务风险 | human signoff 强制门 |

## 16. 产品决策

### 16.1 默认使用模式

默认使用 dry_run / MIXED 路径，保证快速和稳定。  
深度 live 参审作为显式动作，必须提示预计耗时和成本。

### 16.2 前台只呈现一道结果

用户前台不选择蜂群，不管理 agent。系统只输出一道圣旨/奏折。

### 16.3 分歧不隐藏

多视角意见冲突时，不强行合成一个平均结论，而是告诉用户冲突在哪里、需要谁来裁决。

### 16.4 史馆是学习回路

史馆不是静态档案页，而是让下一次判断更准的经验系统。

## 20. 最终判断

当前最重要的产品动作不是继续增加页面，而是把第一条真闭环做成:

```text
能发起
能生成
能判断真伪
能裁决
能归档
能复用
```

当一个真实用户通过这条链路完成一次真实经营判断，并认可“这帮我了”，本阶段 PRD 即验收通过。
