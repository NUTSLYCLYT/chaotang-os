# 锦衣卫「密报卷轴三栏」实施方案

## 1. 方案结论

锦衣卫详情页采用与六部详情页一致的朝堂三栏视觉骨架，但不复制六部业务结构，而是围绕锦衣卫真实职责重组为：

> 左栏找证据，中栏呈密报，右栏判真假与去向。

页面核心从“情报仪表盘”调整为“一份可核验、可追溯、可归档的密报”。产业看板与世界地图保留为辅助视图，不再占据默认核心舞台。

正式路由：`/zhuanshu/jinyiwei`。

## 2. 后端事实源

### 2.1 锦衣卫职责

以后端部门协议为准：

- 工作：外部信号、开源项目、竞品、风险情报。
- 拥有能力：`open_source_signal`、`external_signal`、`risk_intel`。
- 输入来源：史馆、钦天监。
- 结果流向：
  - 绿灯：钦天监。
  - 黄灯：御史。
  - 红灯：锦衣卫继续补证。
  - 黑灯：刑部。

### 2.2 真实执行链

后端现有执行链为：

1. 真实联网检索，或接收调用方提供的证据链。
2. 对每条声明执行确定性可信度核验。
3. 判定一手、二手多源、二手单源或未证实。
4. 给出入库、待核或拒绝结论。
5. 生成锦衣卫 `court_doc`。
6. 将可归档结果写入真值台账。

真实入口：`POST /api/intel/brief`。

请求：

```json
{
  "query": "核查某开源项目近期安全风险与官方处置"
}
```

也可以提交调用方已取得的证据：

```json
{
  "query": "核查某项目漏洞声明",
  "findings": [
    {
      "claim": "项目官方发布了安全公告",
      "sources": [
        {
          "name": "项目官网安全公告",
          "url": "https://example.com/security"
        }
      ]
    }
  ]
}
```

页面必须展示并区分：

- `LIVE_SEARCH`：后端真实联网检索。
- `CALLER_FINDINGS`：调用方提供证据链。
- `FALLBACK`：没有取得可核情报，禁止冒充真实结果。

## 3. 产品目标

### 3.1 用户进入页面后应立即明白

- 锦衣卫能查什么。
- 当前情报来自哪里。
- 哪些声明可信，哪些需要补证，哪些应拒绝。
- 当前密报能否进入决策流程。
- 下一步应该交给谁。

### 3.2 用户完成一次核心任务

用户输入一个需要核查的项目、竞品、风险或外部信号，锦衣卫返回一份带公开来源、可信度裁决、补证要求和归档信息的密报。

### 3.3 非目标

- 不把 mock、fixture 或无来源摘要包装为实时情报。
- 不在前端复制后端可信度算法。
- 不提供后端尚未实现的正式自动派发、付款、交易或对外承诺能力。
- 不让世界地图成为没有决策结论的装饰性大屏。

## 4. 页面信息架构

桌面端采用三栏布局：

```text
┌────────────────┬─────────────────────────────┬──────────────────┐
│ 左栏：耳目采证   │ 中栏：密报卷轴                │ 右栏：核验处置     │
│                │                             │                  │
│ 核查目标输入     │ 锦衣卫总判                   │ 可信度硬门         │
│ 真实采证按钮     │ 事实声明                     │ 来源等级           │
│ 数据源状态       │ 公开来源与时间                │ 入库/待核/拒        │
│ 待核任务         │ 影响与风险                   │ 补证要求           │
│ 后端实装能力     │ 归档编号与来源标签             │ 下一步流向          │
└────────────────┴─────────────────────────────┴──────────────────┘
```

建议桌面宽度比例：`300px / minmax(620px, 1fr) / 340px`。

## 5. 左栏：耳目采证

### 5.1 核查目标

提供一个清晰的自然语言输入框：

- 项目或开源仓库风险。
- 竞品近期动作。
- 政策、监管或市场异动。
- 某项外部声明是否可信。

主按钮文案：“启动锦衣卫真实采证”。

执行期间显示明确状态：

- 正在联网检索。
- 正在进行可信度核验。
- 正在生成密报。
- 正在归档结果。

首期后端不能提供细粒度进度事件时，只展示“正在检索并核验”，不得模拟虚假阶段进度。

### 5.2 真实数据状态

只展示可以从接口结果或真实数据源计算的指标：

- 主库状态：Turso / 不可用 / 兜底。
- 真实信号数。
- 带公开 URL 的来源数。
- 急报与预警数。
- 最近一次真实采证时间。

当主库接口不可用时必须显示“兜底”，并将真实信号数显示为 `0/N`，不能把 fixture 数量当成真实数量。

### 5.3 后端实装能力

以能力清单形式展示：

- 联网采证：Tavily 或调用方证据链。
- 确定性核验：一手、二手多源、二手单源、未证实。
- 可信度裁决：入库、待核、拒。
- 归档存证：真值台账与归档编号。

能力状态只能使用：

- 已接通。
- 当前不可用。
- 需要配置。

不能使用无法验证的“运行正常”或“实时在线”。

## 6. 中栏：密报卷轴

### 6.1 默认舞台

中栏默认展示“锦衣卫密报卷轴”，一次聚焦一份核验任务，不默认展示产业看板。

卷轴结构：

1. 卷首：锦衣卫印、密报编号、来源标签、生成时间。
2. 总判：后端 `headline` 与红黄绿黑灯。
3. 奉查事项：用户原始 `query`。
4. 事实声明：逐条 `items`。
5. 证据：公开来源、来源类型、发布日期。
6. 可信度：一手、二手多源、二手单源、未证实。
7. 裁决：入库、待核、拒。
8. 补证：后端 `fix`。
9. 挡门结果：后端 `shielded`。
10. 卷尾：归档编号、确定性门状态、来源标签。

### 6.2 空态

首次进入时显示：

> 请在左栏输入需要核查的项目、竞品、风险或外部信号。

后端返回 `FALLBACK` 且没有条目时显示：

> 未获取到可核情报。锦衣卫未形成事实结论，也没有编造条目。

空态不能显示绿灯。

### 6.3 辅助视图

卷轴顶部或底部提供次级切换：

- 密报卷轴（默认）。
- 本产业情报。
- 世界地图。
- 情报队列。

地图和产业板只负责浏览与选择情报。选中一条情报后，页面应回到卷轴或在卷轴中展开详情。

## 7. 右栏：核验处置

### 7.1 可信度硬门

显示后端确定性规则的结果，不在前端重新计算结论：

- 是否包含一手来源。
- 是否有多源印证。
- 是否包含数字、认证、唯一性等硬声明。
- 是否允许入库。
- 是否需要人工核验。

### 7.2 下一步流向

根据后端部门协议展示建议流向：

| 灯色 | 含义 | 下一步 |
| --- | --- | --- |
| 绿 | 情报可信，可进入判断 | 钦天监 |
| 黄 | 可参考但需要复核 | 御史 |
| 红 | 情报不可信或缺证 | 锦衣卫继续补证 |
| 黑 | 重大风险或不可逆风险 | 刑部 |

首期只展示“建议流向”。只有后端提供正式派发接口并返回非 `FALLBACK` 凭证后，才能开放“正式转派”按钮。

### 7.3 处置动作

首期允许：

- 返回情报详情。
- 查看公开来源。
- 复制密报编号。
- 重新采证。

暂不允许：

- 假装生成证据包。
- 通过兼容接口伪装正式派发。
- 将无来源情报标记为已核实。

## 8. 响应式设计

### 8.1 桌面端

- 保持三栏同时可见。
- 中栏拥有最大宽度和视觉权重。
- 左右栏内部允许纵向滚动，但页面主舞台不横向滚动。

### 8.2 平板端

- 中栏置顶。
- 左栏与右栏组成下方双列。
- 采证按钮始终可见。

### 8.3 手机端

采用顺序：

1. 核查输入。
2. 密报卷轴。
3. 核验处置。
4. 数据状态与能力说明。
5. 地图、产业板和队列。

## 9. 前端组件拆分

建议将当前锦衣卫页面拆分为：

```text
features/intel/
├─ JinyiweiPage.tsx
├─ components/
│  ├─ JinyiweiEvidenceRail.tsx       # 左栏
│  ├─ JinyiweiBriefScroll.tsx        # 中栏卷轴
│  ├─ JinyiweiVerdictRail.tsx        # 右栏
│  ├─ JinyiweiSourceStatus.tsx       # 真实数据状态
│  ├─ JinyiweiCapabilityList.tsx     # 后端能力
│  ├─ JinyiweiBriefItem.tsx          # 单条声明与证据
│  ├─ JinyiweiNextRoute.tsx          # 红黄绿黑去向
│  └─ JinyiweiAuxViews.tsx           # 产业板、地图、队列
├─ hooks/
│  └─ use-jinyiwei-brief.ts          # POST /api/intel/brief
└─ lib/
   ├─ jinyiwei-brief-contract.ts     # court_doc 前端类型
   └─ jinyiwei-view-model.ts         # 纯展示映射，不做可信度裁决
```

`JinyiweiPage.tsx` 只负责页面状态与三栏编排，不继续堆叠所有展示实现。

## 10. 状态模型

页面应维护以下状态：

```ts
type BriefPhase =
  | 'idle'
  | 'collecting'
  | 'ready'
  | 'empty'
  | 'error';
```

关键状态：

- `query`：当前核查目标。
- `brief`：后端返回的 `court_doc`。
- `sourceLabel`：真实来源标识。
- `selectedSignalId`：辅助视图选中的历史信号。
- `activeView`：卷轴、产业、地图或队列。

## 11. 分阶段实施

### 阶段一：建立卷轴主舞台

- 将中栏默认内容切换为密报卷轴。
- 把当前产业板、地图和队列移入辅助视图。
- 建立首次进入、加载、空结果、错误和完成状态。

验收：用户不操作时看到明确采证引导，不再默认面对复杂看板。

### 阶段二：拆分左右栏

- 左栏拆成采证、数据状态和能力三块。
- 右栏拆成可信度门、来源、裁决和建议流向。
- 删除所有没有后端凭证的动作。

验收：左右栏展示内容都能追溯到接口或后端定义。

### 阶段三：接通真实密报

- 抽出 `useJinyiweiBrief`。
- 完整映射 `court_doc`、`sourceLabel`、`items`、`shielded` 与 `provenance`。
- 展示逐条证据和补证要求。

验收：`LIVE_SEARCH`、`CALLER_FINDINGS`、`FALLBACK` 三种结果均正确展示。

### 阶段四：响应式与体验收口

- 完成桌面、平板和手机布局。
- 增加键盘操作、焦点状态、加载状态与长文本折行。
- 检查卷轴在 1366×768 和 1440×900 下的可用高度。

验收：核心输入、卷轴结论和核验处置无需横向滚动即可完成。

## 12. 验收标准

### 12.1 功能验收

- 左栏可以提交真实采证请求。
- 中栏默认展示密报卷轴。
- 右栏展示后端核验结论和下一步建议。
- 公开来源可点击并显示来源名称。
- `FALLBACK` 结果不会显示为真实情报或绿灯。
- 无公开 URL 的信号不能显示为已核实。

### 12.2 视觉验收

- 桌面端三栏稳定，不遮挡全局顶栏和底栏。
- 卷轴是页面视觉中心。
- 左右栏信息密度低于中栏，不抢主结论。
- 红黄绿黑只表达后端裁决，不作为装饰色滥用。

### 12.3 技术验收

- TypeScript 通过。
- Next.js production build 通过。
- 锦衣卫 agent、endpoint、vet 测试通过。
- 增加 `useJinyiweiBrief` 的成功、空态和错误测试。
- Playwright 覆盖三栏、真实来源标签、空态、卷轴和辅助视图。
- frontend harness doctor 通过。

## 13. 已知接口缺口

当前后端有真实 `POST /api/intel/brief`，但前端使用的 `GET /api/court/intel/signals` 在当前运行环境可能返回 404。因此：

- 真实主动采证以 `/api/intel/brief` 为主。
- 历史情报列表不可用时必须显示 fallback 状态。
- 若需要正式历史密报队列，应由后端新增可审计的列表接口，至少返回 `sourceLabel`、来源 URL、可信度裁决、归档编号和时间。
- 在正式列表接口落地前，不得把 fixture 队列升级为“真实情报中心”。

建议后续后端契约：

```text
GET /api/intel/briefs
GET /api/intel/briefs/{case_id}
POST /api/intel/briefs/{case_id}/route
```

其中正式转派接口必须返回真实任务 ID、目标部门、来源标签、执行状态和可追踪链接；返回 `FALLBACK` 时前端不得显示“正式转派成功”。

## 14. 完成定义

本方案完成的标准不是“页面看起来像三栏”，而是：

1. 用户知道锦衣卫正在查什么。
2. 每条结论都能看到来源与可信度。
3. 系统明确区分真实、调用方证据和空结果。
4. 中央卷轴能独立支撑一次可信决策。
5. 左右功能均与后端真实能力一致。
6. 页面不提供任何无法由后端凭证证明的成功动作。
