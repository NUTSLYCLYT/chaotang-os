- 未使用 mock；直接把真实的 `harness-doctor.mjs` 当子进程跑，验证的是最终用户会看到的实际

## 修正记录（2026-07-14，第二轮）

- 初版"制造 `src/app/api` 违规"用例的清理逻辑是 `rmSync(join(appRoot, 'api'), {recursive:true, force:true})`——
  删的是共享父目录 `src/app/api/` 整体，不是测试自己创建的子目录。如果并发进程或用户在这个目录下
  有真实的未提交内容，会被这条测试连坐删掉。Codex stop-time review 拦下并指出后已改正：清理逻辑
  改成只删测试自己创建的具体路径，父目录只在"确认是本测试创建、且现在已清空"时才顺手删除，其余
  情况一律不动。
- 已实测验证修复有效：手动在 `src/app/api/` 下放一个模拟的"别人的真实文件"，跑测试后确认该文件
  原封不动地留在原地（测试 1 因为仓库不再"干净"而按预期失败，这是正确行为，不是缺陷）；清理模拟
  文件后复跑，恢复 3/3 通过。反向验证（禁用检查逻辑）也重新跑过一遍，确认修复没有削弱测试本身
  抓 bug 的能力。

## 修正记录（2026-07-14，第三轮）

- 第二轮用 `process.pid` 拼路径名当作"唯一"标记，被指出这并不真正保证唯一——同一 PID 可能因为
  容器 PID namespace 隔离、或前一次异常退出的测试残留而复用，命名唯一性只是"大概率不撞"，不是
  保证。真正的风险不在"会不会撞名"，而在"创建前从不检查目标路径是否已经有内容，创建后又无条件
  删除"，只要撞上了就照删不误。
- 已改用 `fs.mkdtempSync`：由操作系统原子性地分配一个保证不冲突的路径，而不是自己拼一个"看起来
  应该不会撞"的名字。两处测试用例（`src/app/api/` 违规、`route.ts` 违规）都改成这个方式。
- 复跑过完整验证链：正常 3/3 通过 → 模拟"别人的文件"确认不受影响、清理后仓库无残留 → 反向验证
  （禁用检查逻辑）确认失败路径用例正确变红、恢复后再次 3/3。
