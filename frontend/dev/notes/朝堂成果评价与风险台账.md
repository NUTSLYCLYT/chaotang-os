## 二、两个黑天鹅（塔勒布：先买这两个保险）

### 🦢 #1 安全（C1/C3）——平时没事，出事=数据泄露/身份伪造
- **C1 alg:none 未验签**：后端域（前端禁验签·铁律1）→ 前端保险=所有特权写经 `backendVerifyOrReject`（已）+ `guard:auth`（实测✅无裸奔）。
- **C3 租户隔离（2026-06-28 深挖：部署=多租户·公网共享 → 地基级 blocker）**：
  guard 报的"3 端点"只是冰山——**核心表租户审计：7 张 6 张无 user_id**：
  `tasks`(主库总线·5读端点) / `shiguan_archives` / `courtos_decisions` / `hubu_projects` / `agent_decisions` / `boss_preferences` 🔴无；仅 `decision_tasks` ✅有。
  补端点 WHERE 修不了——表里没那列。**整条数据脊柱按单租户建的。**
- **真修法 = 租户化迁移（公网上线前必做，禁尾段赶工·铁律4）**：
  1. **加列**：6 张表加 `user_id`(+可选 `tenant_id`)。
  2. **写盖章**：每个写端点从 `getUserIdFromSession()` 盖 user_id（orchestrate/hubu projects/archive 写…）。
  3. **读过滤**：每个读端点 `WHERE user_id=?`，**fail-closed**（无 userId → 空，绝不全表，照 court_archives 范式）。
  4. **回归**：每表一条"跨租户读返回空"断言 + `guard:tenant` 全绿进发布硬门。
  - **做法**：逐表推进（先最关键的 `tasks` 总线），每表配 code-reviewer 独立会审（铁律4），不一次性大改。

### 🦢 #9 假 LIVE——后端挂了却给用户标 LIVE，信任崩塌
- **保险状态**：✅ **已装**——`reality-state.nodetest.ts` 6/6 锁死：
  - 只有真 LIVE 家族 → real；降级/垃圾输入 → 绝不 real（安全归 missing）；合并取最坏永不升级。
  - **已知边缘**：`worstRealityState([])` → real（乐观默认）。防线在调用方：无数据时禁传 `[]`，须传 `['missing']`。
