# 六部后端功能与逻辑梳理

日期：2026-07-02

## 代码状态

已执行 `git fetch origin`，当前本地 `master` 与 `origin/master` 对齐。

当前工作区存在未提交改动，主要集中在前端页面、组件和六部相关 UI 文件。因此：

- 后端基线代码：已同步到最新 `origin/master`
- 当前工作区：包含未提交改动，不是干净发布快照
- 本文基于当前本地后端和核心逻辑进行梳理

## 总体判断

当前六部后端成熟度并不完全一致：

- 户部、兵部、工部、刑部已经形成较完整的后端 API 与核心审议模型。
- 吏部已经有部门定义和部分业务引擎，但 API 化程度弱于前四部。
- 礼部目前更偏宣传资料、品牌内容和素材归档接口，还没有形成完整的审议部门模型。

## 户部

现代职能映射：财务、预算、报价、投资、现金流、成本、审计。

主要接口：

- `/api/court/hubu/overview`：汇总真实任务、集群任务、手工项目，识别财务事项，提取金额、ROI、审批状态、现金储备等。
- `/api/court/hubu/ask`：读取户部概览和历史冲突信号，通过 `askHubu` 生成带证据、冲突、置信度的回答。
- `/api/court/hubu/projects`：管理户部项目，支持读取和写入 `hubu_projects`。
- `/api/court/hubu/memorials/from-swarm`：从集群任务生成户部奏折，检查证据包和发布门禁。
- `/api/court/hubu/auto-raise`：将财务类机会、风险或待审事项推入部门飞轮。

核心文件：`src/core/courtos/hubu/hubu-cfo-office.ts`

户部采用 CFO Office 模型，覆盖经营复盘、合同财务条款审查、报价审查、投资评审、预算审批、现金流判断、成本毛利分析、回款账期判断、融资或借款判断、采购付款判断、招聘或组织成本判断、异常风险审计等。

输出结果包括 `准奏 / 复核 / 补证 / 驳回`、置信度、关键数字、使用证据、缺失证据、风险登记、推荐下一步动作和需要皇帝确认的问题。

## 兵部

现代职能映射：销售、客户、商机、报价策略、渠道、营收运营。

主要接口：

- `/api/court/bingbu/overview`：从真实任务里提取销售事项，识别客户、阶段、金额、预付款、交付、账期、行业，并评估风险等级。
- `/api/court/bingbu/ask`：结合兵部概览和历史决策信号，通过 `askBingbu` 输出建议、证据、风险和下一步动作。
- `/api/court/bingbu/auto-raise`：把销售风险或机会推入六部飞轮。

核心文件：`src/core/courtos/bingbu/bingbu-cro-sales-office.ts`

兵部采用 CRO / Sales / RevOps Office 模型，覆盖线索资格、商机评审、客户打法、报价策略、谈判、渠道伙伴、销售预测、赢单或输单复盘、客户成功和增长、销售组织执行。

兵部禁止自动给客户发送正式消息、自动出正式报价、自动承诺价格、折扣、交付时间或 ROI、自动签署合同、自动签署渠道或独家协议。

## 工部

现代职能映射：产品、研发、交付、BOM、供应链、验收、现场实施。

主要接口：

- `/api/court/gongbu/pack-sizing`：接收需求描述，调用 live swarm 的 `pack_rd`，返回方案摘要、发现项、缺失能力、适配器状态。

核心文件：`src/core/courtos/gongbu/gongbu-cto-cpo-office.ts`

工部采用 CTO / CPO Delivery Office 模型，覆盖存储或硬件项目、BOM 与供应链、交付承诺、排期和产能、质量与验收、现场实施、MVP 范围、技术可行性、范围变更、交付复盘。

工部禁止自动承诺固定交付日期、自动对外承诺交付、自动锁定供应商、自动下采购单、自动改变 MVP 范围、自动确认验收标准、自动确认交付完成。

## 刑部

现代职能映射：法务、合规、合同、授权、争议、劳动法、知识产权。

主要接口：

- `/api/court/legal/overview`：默认代理到集群法务服务，上游不可用时返回本地 fallback 法务概览。
- `/api/court/dept/xing-bu/legal`：刑部法务处理链路，连接法务 agent 或 legal bridge。
- `/api/court/dept/xing-bu/legal/result`：刑部法务结果读取链路。

核心文件：`src/core/courtos/xingbu/xingbu-clo-cco-office.ts`

刑部采用 CLO / CCO Office 模型，覆盖合同审查、正式报价或外部承诺、公司治理、合规审查、争议或诉讼、劳动法、IP 与保密、法务运营、付款、违约金、赔偿条款、AI agent 对外输出等。

刑部禁止自动签署合同、自动盖章、自动发送合同、自动发送正式报价、自动作出外部承诺、自动解除劳动关系、自动发送律师函、自动提起诉讼。

## 吏部

现代职能映射：人事、行政、组织、岗位、绩效、薪酬、任免、资质申报。

核心文件：`src/core/courtos/libu/libu-personnel-admin-office.ts`

吏部当前包含：

- 招录司：招聘、岗位画像、渠道、候选人筛选。
- 铨叙司：试用期、绩效、任免、晋升。
- 俸禄司：薪酬、调薪、薪酬带宽。
- 行政司：DRI、RACI、责任链、资产、会议、制度。
- 申报司：政府补贴、高企、专精特新、研发加计扣除。
- 资质司：ISO、3C、军工资质、设备资质。

状态判断：吏部已经有部门定义和部分业务能力，但后端 API 化程度仍偏弱。

## 礼部

现代职能映射：品牌、宣传、对外口径、客户案例、市场内容。

主要接口：

- `/api/court/libu/promo`：路径名为 `libu`，但从代码注释和语义看，实际对应礼部宣传资料；读取 promo snapshot，返回分类、层级、高价值数量、标题、类型等宣传资料元数据。

状态判断：礼部目前更像宣传素材、品牌内容和客户案例的资料接口，还没有看到类似户部 CFO、兵部 CRO、工部 CTO、刑部 CLO 那种完整的核心审议模型。

## 六部整体逻辑

- 户部管钱：判断能不能花、值不值得花、现金流够不够。
- 兵部管销售：判断客户、商机、报价、谈判、营收动作。
- 工部管交付：判断技术、BOM、产能、排期、验收。
- 刑部管法务：判断合同、合规、授权、争议、外部承诺。
- 吏部管人和组织：岗位、绩效、薪酬、责任链、行政资质。
- 礼部管对外表达：宣传素材、品牌内容、客户案例、市场口径。

## 后续建议

1. 为吏部补齐正式 API BFF，例如 `/api/court/libu/overview`、`/api/court/libu/ask`、`/api/court/libu/auto-raise`。
2. 为礼部建立真正的核心审议模型，例如 CMO / CCO Office。
3. 统一六部命名，避免 `libu` 同时指代吏部和礼部造成语义混乱。
4. 将各部成熟度、接口、核心 office 和前端页面建立一张可追踪映射表。
5. 为六部统一定义“能自动做什么”和“必须人工确认什么”的门禁规范。
