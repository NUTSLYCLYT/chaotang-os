## 2. InboxItem 形状（复用现有 `ChancellorItem`，只加 `origin`）

前端 SoT 在 `src/lib/contracts/shangshufang.ts` 的 `ChancellorItem`。后端每个待裁项按此返回，**新增一个 `origin` 域**标来源部门：

```ts
interface InboxItem {
  id: string;                 // 稳定唯一 id，前端据此去重(禁跨源撞 id)
  title: string;             // 一句话由头(老板一眼看懂要裁什么)
  tag: string;               // 短标签，如「军机处 · 会审待决」
  priority: "urgent" | "high" | "medium" | "low";  // ← 见 §3 由 L0-L4 映射
  origin: "junjichu" | "jinyiwei" | "libu" | "hubu" | "gongbu" | "xingbu"
        | "bingbu" | "qintian" | "chancellor";     // ← 来源徽用(SSOT 见 contracts/agent.ts 11码)
  source: "turso" | "primary" | "signal" | "ledger";  // 数据可信度来源(诚实标)
  suggestedCommand?: string; // 可预填的下旨命令
  citations?: { source: string; snippet: string }[];  // 可核验证据，禁占位文案冒充
  recommendedMinisters?: string[];
  loopTraceId?: string;      // 贯穿拟旨/会审/裁决/归档的追踪 id
}
```

**硬要求（诚实链路，铁律）**：
- 列表**只放真待裁项**；没有就返回**空数组**，禁用占位/演示项冒充（前端已有空态文案）。
- `citations` 必须是真实可核验来源，不得塞 `"示例"`/`"待补"` 冒充。
- 若某源数据不可达，用 `briefing.sourceMode` 已有的 `real|fallback|unavailable` 机制区分「今天没有」与「读不到」，**不得静默返回空当成功**。

## 3. priority 映射（风险等级 L0-L4 → 收件箱排序键）

前端收件箱按 `priority` 稳定排序、高危置顶（PRD §4，已实现）。后端若内部用 L0-L4 风险等级，请按此映射后返回，**映射在后端做，前端不猜**（铁律2 SSOT）：

| 后端风险等级 | InboxItem.priority | 前端排序 rank |
|---|---|---|
| L4 / L3（不可逆·高危：股权/合同/对外报价/供应商锁定…） | `urgent` | 0（置顶） |
| L2 | `high` | 1 |
| L1 | `medium` | 2 |
| L0（低风险/例行） | `low` | 3 |

高危词判据前端已有 SSOT（`isHighRiskMemorial`：正式报价/合同/付款/股权/对外承诺…）；若后端能给出更权威的 L0-L4，**以后端为准**，前端读它而非本地推断。

## 4. 前端拿到后怎么用（无需后端关心，仅说明闭环）

1. 合并进 `displayedSuggestions`，按 `priority` 稳定排序（已实现，`suggestionPriorityRank`）。
2. 每条渲染**来源徽**（`origin` → 部门名/官印色）+ 由头 + 风险色 + `sourceLabel`。
3. 点选 → 中栏决策卡；裁决走已上线的 `handleVerdictChoice`（高风险人工确认门 + 落库 + 锁定 + 归档回执）。
4. 军机处/锦衣卫来源的项，裁决动作可能需要**对应源的 decision 端点**（非 `shangshufang/tasks/{id}/decision`）——请后端一并告知各源的裁决落库端点，前端 `handleVerdictAction` router 加分支。

## 6. 交给后端的不是 prompt，是「schema + 金标评测集」（顶尖做法）

后端是 agent 群，待裁项是 agent 产物——但**前端不写后端 prompt**（会腐烂、违反铁律9、前端不懂 flow 上下文）。
前端交三样，后端拿去**自己写 prompt，调到能过金标、被反例拒即达标**（Karpathy：写 eval 不写 prompt；Ng：数据中心）：

**① 输出 schema**：`ZInboxItem`（`src/lib/contracts/schemas.ts`）+ `InboxItem`（`contracts/shangshufang.ts`）。

**② 边界诚实闸（已实现，前端侧）**：`src/lib/shangshufang/parse-inbox-feed.ts` —— feed 进收件箱前当场 fail-loud：
   - `sourceMode` 缺失/非法 → 判 `unavailable`，不渲染（区分「今天没有」vs「读不到」）
   - 单项形状非法 → 丢弃记因，不整批崩
   - 证据空/占位/伪造（`示例|待补|待接入|placeholder…`）→ 丢弃（锦衣卫可信度门）

**③ 金标 + 反例评测集**（`parse-inbox-feed.nodetest.ts`，7 例全绿，即 handoff fixtures）：

| 类型 | 用例 | 期望 |
|---|---|---|
| 金标 | 真实待裁项(真 id/title/priority/真 citation) | 全过、零拒 |
| 金标 | `real` + 空 items | 今天没有：0 项、不拒、不冒充 |
| 反例 | `sourceMode` 缺失 | 判 unavailable、拒渲染 |
| 反例 | 非法 origin(不在 11 码) | 丢弃该项 |
| 反例 | 占位/伪造证据 | 丢弃(可信度门) |
| 反例 | 空 snippet 证据 | 丢弃 |
| 混合 | 真项+脏项 | 真项留、脏项剔、不整批崩 |

> 「情报≠决策」这类**语义**正确性靠后端 eval（用②③的金标+反例给 agent 输出打分），不是结构校验能拦的。
> 前端守结构+诚实，后端守语义+产出。**跑法**：`npx tsx --test src/lib/shangshufang/parse-inbox-feed.nodetest.ts`。
