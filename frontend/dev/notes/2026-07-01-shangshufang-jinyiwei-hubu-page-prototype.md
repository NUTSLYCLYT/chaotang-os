范围: `chaotang-web-lyt` 前端现状，只整理页面原型，不改实现。

## 0. 当前入口总览

| 模块 | 当前路由 | 当前页面状态 | 关键文件 |
|---|---|---|---|
| 上书房 | `/court-briefing`；`/study` 重定向/合流 | 已是主入口页，三栏 + 中央卷轴 + 底部下旨 | `src/app/(dashboard)/court-briefing/page.tsx`；`src/features/shangshufang/ShangshufangPage.tsx` |
| 锦衣卫 | `/intel`；`/intel/[signalId]` | 已是独立情报页，世界地图 + 情报详情 + 派发弹窗 | `src/app/(dashboard)/intel/page.tsx`；`src/features/intel/JinyiweiPage.tsx` |
| 户部 | `/departments/finance` | 已挂载户部专属 CFO 办公厅 | `src/app/(dashboard)/departments/[code]/page.tsx`；`src/features/hubu/components/hubu-office-page.tsx`；`src/features/departments/lib/department-offices.ts` |

重要现状:

- 上书房是三者协作的总入口，锦衣卫与户部更像专业工作台。

## 1. 三者产品闭环原型

```text
用户问题 / 今日建议
  ↓
上书房 `/court-briefing`
  - 拟旨
  - 识别需要锦衣卫核情报还是户部算账
  - 展示证据、风险、裁决按钮
  ↓
锦衣卫 `/intel`
  - 公开来源巡察
  - 证据包
  - 派发户部/其他部门
  ↓
户部 `/departments/finance`
  - 财务事项队列
  - 三引擎裁决
  - 预算/ROI/现金/缺证
  ↓
回上书房
  - 合并情报可信度 + 财务确定性
  - 用户裁决: 准奏 / 补证 / 驳回 / 会审
```

页面评审建议先看这条路径:

1. 从上书房输入一个“客户说竞品低 20%，要不要降价”的问题。
2. 上书房标出“竞品低价来源缺口”和“户部测算需求”。
3. 锦衣卫展示对应情报信号，确认来源等级，派发给户部。
4. 户部展示该事项进入“今日待拍板”，给出毛利/现金/ROI/缺证裁决。
5. 上书房最终收口为一个可裁决奏折。

## 2. 上书房页面原型

### 页面定位

上书房是三者中的“总入口 + 收口页”。用户不应先选择锦衣卫或户部，而是先在这里说出经营问题。

当前页面已经是主界面:

- 左栏: 丞相辅政、建议、证据/史馆召回入口。
- 中栏: 中央卷轴，承载奏折、拟旨、回奏、教学、蜂群回执。
- 右栏: 钦天监/指导/深度问题入口。
- 底部: 下旨输入区，支持问丞相、问钦天监、发布圣旨、机密/蜂群模式。

### 建议原型结构

```text
┌────────────────────────────────────────────────────────────┐
│ 顶部: 上书房 / 今日任务数 / 待裁数 / sourceLabel             │
├───────────────┬────────────────────────────┬───────────────┤
│ 左栏 丞相辅政  │ 中央 卷轴                   │ 右栏 钦天监指导 │
│               │                            │               │
│ 今日建议       │ 当前拟旨 / 奏折              │ 问钦天监       │
│ 证据召回       │ 圣裁 / 分奏 / 证据 / 风险     │ 教学/推演      │
│ 史馆旧案       │ 缺证 / 后令 / 来源            │ 深度问题       │
│ 待补事项       │                            │               │
├───────────────┴────────────────────────────┴───────────────┤
│ 底部: 下旨输入 + 附件证据 + 模式切换 + 发送                  │
└────────────────────────────────────────────────────────────┘
```

### 上书房应强化的三个区块

1. **拟旨前置面板**
   - 展示“原问”。
   - 展示系统改写后的“拟旨”。
   - 明确推荐部门: `锦衣卫`、`户部`。
   - 明确缺口: 情报来源、报价依据、成本拆解、回款条款。

2. **三方协作条**
   - `上书房已立案`
   - `锦衣卫核情报`
   - `户部测财务`
   - `回上书房裁决`

3. **裁决区**
   - 主按钮: `准奏`
   - 风险按钮: `补证`
   - 否定按钮: `驳回`
   - 复核按钮: `发起会审`
   - 每个按钮必须显示是否需要人工确认。

### 数据绑定

当前已接:

- `GET /api/court/shangshufang/briefing`
- `POST /api/court/shangshufang/draft-edict`
- `POST /api/court/shangshufang/confirm-edict`
- `GET /api/court/shangshufang/tasks/{taskId}/status`
- `POST /api/court/shangshufang/tasks/{taskId}/decision`
- `POST /api/court/shangshufang/finance-intel-loop`

### Review 重点

- 用户是否能一眼看懂“现在是在问、拟旨、会审、补证还是裁决”。
- 锦衣卫结果与户部结果是否在中央卷轴里被分清: “事实可信度” vs “财务可行性”。
- `FALLBACK / MIXED / LIVE` 是否足够显眼，避免把演示/缺证当真。

## 3. 锦衣卫页面原型

### 页面定位

锦衣卫负责“外部事实是否可信”，不负责算钱，不负责最终裁决。

当前 `/intel` 已经是独立页面:

- 顶部: 世界情报地图标题、统计指标、数据来源提示。
- 左栏: 六部领域筛选、来源等级筛选、处理状态筛选。
- 中央: 真实 OSM 地图底图 + 情报点。
- 右栏: 情报详情、公开来源、证据硬门、处理建议。
- 底部: 情报处理队列。
- 弹窗: 派发部门，可选择户部等。

### 建议原型结构

```text
┌────────────────────────────────────────────────────────────┐
│ 顶部: 锦衣卫 · 世界情报地图 / 可见情报 / 真实来源 / 已派六部  │
├───────────────┬────────────────────────────┬───────────────┤
│ 左栏 筛选      │ 中央 世界地图               │ 右栏 情报详情   │
│               │                            │               │
│ 按六部筛选     │ 情报点                      │ 标题/地区/等级  │
│ 来源等级       │ 地图 attribution            │ 来源 URL        │
│ 处理状态       │ 选中气泡                    │ 证据硬门        │
│ 重置           │                            │ 生成证据包      │
├───────────────┴────────────────────────────┴───────────────┤
│ 底部: 情报处理队列                                           │
└────────────────────────────────────────────────────────────┘
```

### 派发弹窗原型

```text
┌──────────────────────────────┐
│ 转派旨令: 情报标题             │
│ id / region / level           │
├──────────────────────────────┤
│ 情报摘要                       │
├──────────────────────────────┤
│ 选择承办部门                   │
│ [兵部] [钦天监] [刑部]          │
│ [礼部] [户部]   [工部]          │
├──────────────────────────────┤
│ 附言                           │
│ ☑ 同时在指挥台创建关联任务       │
├──────────────────────────────┤
│ 取消              下达转派      │
└──────────────────────────────┘
```

### 当前已具备的硬门

右栏已明确:

- 至少一个公开来源地址。
- 来源可信度达到正式派发标准。
- 不是演示或兜底数据。
- 禁止直接生成交易、付款或对外承诺。

这是很好的页面纪律。建议继续保留，并把“派发户部后只能作为输入证据，不代表财务成立”写进派发回执。

### 数据绑定

当前已接:

- `GET /api/court/intel/signals`
- `POST /api/court/intel/signals/{signalId}/dispatch`
- `POST /api/court/jinyiwei/financial-sources/collect`
- `/api/court/shangshufang/finance-intel-loop` 会先采集财务来源，再派发到户部。

### Review 重点

- 地图点很多时，筛选是否足够快。
- 来源等级 `real / mixed / fallback` 是否比“可信度文案”更显眼。
- “生成证据包”和“派发六部”两个动作是否会让用户误解为已经采信。
- 派发给户部后，是否有明确回链到对应财务事项。

旧通用页曾表达户部定位:

## 5. 三页之间的跳转原型

### A. 上书房 → 锦衣卫

触发条件:

- 用户问题出现“竞品说、客户说、政策传闻、市场数据、认证、报价来源”等外部 claim。

页面动作:

- 上书房中央卷轴显示缺口: `外部情报待核`。
- 按钮: `交锦衣卫核验`。
- 跳转: `/intel?claim=...` 或创建情报任务后跳 `/intel/{signalId}`。

### B. 锦衣卫 → 户部

触发条件:

- 情报与预算、报价、融资、估值、成本、现金、ROI 相关。

页面动作:

- 锦衣卫右栏选 `派发六部`。
- 弹窗选 `户部`。
- 成功回执显示:
  - `taskId`
  - `sourceLabel`
  - `派发给户部`
  - `查看户部事项`

建议目标:

- 成功后提供按钮 `去户部查看测算`，链接 `/departments/finance?taskId=...`。

### C. 户部 → 上书房

触发条件:

- 户部给出 `补证/准奏/驳回/需人工确认`。

页面动作:

- 户部项目卡显示 `回上书房裁决`。
- 回上书房中央卷轴展示:
  - 锦衣卫事实可信度。
  - 户部财务裁决。
  - 缺证项。
  - 可选裁决按钮。

建议目标:

- `taskId` 作为三页共享主键，所有页面都能回到同一案件。

## 6. 最小改造建议

如果只做 review 原型，不碰后端，建议最小前端改造顺序:

1. **给锦衣卫派发成功回执加“去户部”链接**
   - 如果目标包含 `hu_bu`，显示 `/departments/finance` 入口。

2. **上书房中央卷轴增加“三方协作状态条”**
   - 上书房立案 → 锦衣卫核验 → 户部测算 → 上书房裁决。

3. **统一 sourceLabel 显示**
   - 三页都显示 `LIVE / MIXED / FALLBACK / DEMO`，并用同一套解释。

4. **用同一个 taskId 串三页**
   - 锦衣卫派发回执、户部事项卡、上书房奏折都显示同一 taskId。

## 7. Review 问题清单

请 review 时重点拍板这些问题:

1. 上书房是否继续作为唯一入口，还是允许用户直接从锦衣卫/户部开案？
2. 户部专属办公厅是否正式替代通用六部页，成为 `/departments/finance` 的长期入口？
3. 锦衣卫的“生成证据包”是否要真实落库，还是先只作为 UI 意图？
4. 户部卡片上的 `准奏/补证/驳回` 是否现在接真实裁决，还是保持只读/意向？
5. 三页统一主键用 `taskId`，还是引入更上层 `caseId`？
6. 外部情报 `UNKNOWN` 时，户部是否必须强制进入“情景测算”模式？
